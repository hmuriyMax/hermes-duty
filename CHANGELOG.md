# Changelog

Формат: версия → что вошла. Номер версии живёт в трёх файлах и правится только
через `bin/duty-version` (см. `docs/VERSIONING.md`).

## [0.0.4] — в разработке

**Спека дела: `duty.yaml` проверяется до запуска, а не нарушается молча**

- `docs/SPEC.md` — контракт формата: поля верхнего уровня и этапа, значения по
  умолчанию, таблица правил отказа с именами (`role`, `cycle`, `entry`,
  `reachable`, `verdict.changes`, `evidence.forbidden`, `base`, …).
- `dashboard/spec.py` — `load_spec()` и `validate_spec()`: чистые функции без БД,
  без сети и без запуска процессов. Значения читаются только `yaml.safe_load`,
  неизвестный ключ — отказ, а не «молча проглотить»; строки для `file:line`
  берутся из `yaml.compose` с тем же `SafeLoader`.
- Гейт «публикация после ревью, а не после реализации» стал ошибкой запуска:
  `verdict.changes` обязан указывать на предшественника по `needs`, иначе спека
  не читается (`verdict.changes: не предшественник`). То же — «ровно один вход»,
  достижимость всех этапов и ацикличность графа.
- `evidence.cmd`, начинающийся с `git push`, `git commit`, `rm -rf`, `sudo`, —
  отказ: это действие, а не доказательство. `timeout_sec` — не больше часа.
- `role` сверяется со снимком `~/.hermes/profiles/*` + `default` (без
  вызова `hermes profiles list`), `base` проверяется как rev через `git rev-parse
  --verify` отдельной функцией `check_base()`; репозиторий, которого нет на этой
  машине, — предупреждение, а не отказ.
- `bin/duty spec check <file> [--json]` — `OK` либо `file:line: правило: текст`;
  коды `0`/`1`/`2`. Путь на входе CLI разворачивается в абсолютный: движок
  принимает только абсолютный, иначе «откуда взялась спека» не восстановить.
- `examples/duty.yaml` (полный вид из спеки-источника) и
  `examples/duty-minimal.yaml` (два этапа, без evidence/ask), `tests/test_spec.py`
  — по тесту на каждое правило плюс happy path на обоих примерах.

**Движок, шаг первый: лизинг, дерево попытки, контракт файлом, спавн**

- `dashboard/runner.py` — один шаг движка: взял лизинг этапа (атомарно, таблица
  `leases` в той же `duty/duty.db`; TTL из `budget.minutes`, продление по
  heartbeat'у не реже TTL/3), подготовил дерево (`git worktree add` от `spec.base`
  либо каталог дела, либо ничего), записал контракт файлом, заспавнил
  `hermes chat -p <role> --query-file <контракт> --format stream-json --oneshot`
  с cwd дерева, прочитал поток и записал факты.
- Каталог попытки — `~/.hermes/kanban/boards/<board>/workspaces/<deal>-<stage>-<n>`:
  разрешённый корень `role-access` (`docs/PROBES.md`, проба 3), иначе read-only
  роль не увидит ни дерева, ни отчёта.
- Телеметрия: каждый `tool_use`/`tool_result` — событие `attempt_progress`, и
  `fold` копит его счётчиком (`progress: {tools, last_tool, last_at}`). Набор
  `kind` расширен одним словом — вместе с правилом fold 14 и тестами.
- Смерть попытки — три источника без догадок: разобранный `result.json` →
  `attempt_ended` с `outcome=done`; нет отчёта → `failed(contract)`; код выхода
  ≠ 0 → `failed(infra)`; бюджет токенов → `failed(capability)`; таймаут →
  `failed(infra)`. `status: blocked` в отчёте — вопрос через `ask()` и дело в
  `wait_human`; продолжение после ответа — резюмом сессии (`RESUME-OK`).
- `tests/test_runner.py` — 32 теста без модели (спавн подменён фейком) плюс
  живой прогон одного тривиального этапа под `@pytest.mark.live`
  (`pytest -m live` включается руками).

**Evidence-гейт: «готово» без проверяемого пакета не принимается**

- `dashboard/evidence.py` — `verify(result, stage, workdir, attempt_started_at, now)`
  возвращает `Verdict(ok, kind, details)`: схема отчёта (`status` из закрытого
  набора, для `done` — `commit`|`artifacts`, `evidence`, `summary`; лишнее поле —
  предупреждение), артефакты в дереве попытки с полным `sha256` и путём внутри
  дерева, резолв коммита через `git rev-parse --verify` и проверка, что он не был
  предком базы (предок базы = «принёс чужое готовое»), записи объявленных команд
  с `exit == must` и `started_at` не раньше начала попытки, посимвольное
  совпадение `cmd` со спекой после нормализации пробелов и бюджет токенов из
  `usage.total_tokens`. Классы: `contract` для первых пяти проверок,
  `capability` для бюджета; `infra` слой не выдаёт.
- `dashboard/runner.py` — гейт стоит после смерти процесса и **до** записи
  `attempt_ended`: `outcome=done` пишется только при принятом пакете, иначе тот же
  `attempt_ended` с `outcome=failed`, `kind` из вердикта, первыми тремя отказами в
  `reason` и полным списком в `details.verdict`. Схема отчёта уходит исполнителю
  в контракт ключом `report_schema`: о правилах узнают до работы, а не из отказа.
- `bin/duty why <board> <id> <этап>` — последняя попытка этапа из журнала: исход,
  класс отказа, причина и первые `details`; `--json` добавляет ключ `verdict`, не
  переписывая ответ роута.
- `tests/test_evidence.py` — 30 кейсов: по тесту на каждое правило отказа, оба
  happy path (с коммитом и без), предупреждение на лишнее поле, обратный тест
  «`status: done` без `evidence` при объявленных командах» — это и есть тезис P3.
- `docs/JOURNAL.md` — раздел «Evidence-гейт»: порядок проверок, имена правил и
  классы отказа; `docs/RUNBOOK.md` — разбор отказа через `duty why` и красная
  проба «отключить гейт».

## [0.0.3] — в разработке

- **«Дело» стало табом.** В навигации теперь все четыре экрана спеки в её же
  порядке: `Сейчас`, `Дело`, `Почему стоит`, `Здоровье`. Раньше экран дела
  существовал только как следствие клика по строке — со стороны это выглядело как
  «экрана №2 из спеки нет». Таб без выбранного дела показывает выбор из активных,
  последнее открытое возвращается одним правилом (`lastDeal` в десктопе,
  `localStorage: duty:last-deal` в вебе), «← к списку дел» ведёт туда же.

**Свой журнал событий: состояние считается fold'ом, а не по колонкам kanban**

- `dashboard/journal.py`: журнал `duty/duty.db` (WAL, `busy_timeout=2000`,
  `UNIQUE(idempotency_key)`, индекс `(deal_id, id)`), схема — `docs/JOURNAL.md`.
  Чужие БД по-прежнему открываются `?mode=ro`.
- `fold(events)` — чистая функция без I/O: правила 1–7, восемь состояний ожидания,
  tri-state pid (жив / мёртв / неизвестно), `human_kind` `question` против `status`.
- `POST /ingest` (и `GET /now?ingest=1`) читает kanban на чтение и дописывает
  недостающие события; повторный проход — `appended: 0`. Без флага срез ничего не пишет.
- `/now`: `waiting = fold(events)`; дело без событий считается по kanban, и
  `waiting.evidence` начинается с `journal: empty — состояние из kanban`.
- `/health`: `journal: {events, deals, drift: {empty_journal}}` — расхождение журнала
  и kanban видно числом, а не на глаз.

**Вопросы человеку — один канал: `ask()`**

- `dashboard/ask.py` — единственное место, где плагин пишет в пул
  `messaging/pool.db`: `session_key=t_<deal_id>`, `origin='duty'`, `kind='decision'`,
  краткая и полная версии, варианты ответа. Остальной код пул только читает
  (`mode=ro`): проверяется и grep-тестом по файлам, и mtime пула после чтения.
- `POST /ask/{board}/{task_id}` — задать вопрос по делу: живой вопрос по делу
  возвращается как есть (`deduped: true`), дубль в пуле не создаётся. Живой вопрос
  **чужого** продюсера (`origin != 'duty'`) подхватывается только своим id
  (`adopted: true`) и в журнал не пишется: ответ на чужой вопрос журналу не виден,
  и записанный `question_asked` висел бы в fold вечно — дело навсегда «ждало бы
  ответа» (B1 ревью W2). Событие `question_asked` пишется **после** успешной
  вставки: сбой пула (нет файла / только на чтение) не оставляет в журнале следа
  вопроса и уходит в `errors[]` (503); сбой журнала после вставки — `AskError`
  «вопрос создан, факт не записан», а не 500.
- Критичность считается по журналу: дело ждёт человека дольше `ASK_CRITICAL_SEC`
  (2 ч) — `critical=1` и вопрос без срока; иначе срок `ASK_TIMEOUT_HOURS` (24 ч).
- `sync_answers` в проходе ingest читает закрытые вопросы своих вопросов —
  `answered` **и** `expired` — и пишет `question_answered` идемпотентно (ровно один
  факт на вопрос): отвеченный вопрос и вопрос с истёкшим TTL одинаково перестают
  быть живым фактом ожидания. Истечение помечается `answered_via="expired"`.
- П.5 заметки 0.0.2 закрыт по существу: дело в `blocked`/`needs_input` без вопроса
  больше не выдаёт себя за «ждёт ответа» — у него `waiting.human_kind="status"`, а
  вопрос появляется осознанным `POST /ask` (ingest вопросов не создаёт). В шапке
  «Сейчас» (и в десктопе, и в браузере) — `N вопросов + M блокировок`.
- Тесты: `tests/test_ask.py` (29 кейсов: дедуп, критичность, два сбоя пула, маршрут,
  идемпотентность `sync_answers`, `human_kind` до и после вопроса, grep по файлам и
  mtime пула) + `node --test` на `human_kind` и строку счётчика в шейпере.

**Ожидание — распределением, а не одним числом**

- `GET /stats`: `waiting_sec` стал распределением `{p50, p90, p99, count, max}` вместо
  одного `{median_sec, samples}` — «медиана 4 минуты» не отвечает на вопрос, сколько
  ждали самые медленные. Перцентили считаются по **объединённой** выборке всех дел
  (перцентиль перцентилей не равен перцентилю объединённой выборки), метод — ближайший
  ранг без интерполяции: на наборе 1..10 `p50 = 5`, а не 5.5.
- Пустая выборка — `null` во всех перцентилях и `count: 0`: «нет данных» и «ждали
  0 секунд» — разные вещи.
- `?board=<slug>` и `?since=<unix>` считает `collect_stats()`, а не CLI: перцентиль
  подмножества не выводится из перцентилей целого, поэтому терминал и роут получают
  одни и те же числа.

**Владение делом: свой store, мутации, id `d_<hex>`**

- `dashboard/deals.py`: свой store в той же БД `duty/duty.db` — таблицы `deals`,
  `deal_links`, `comments`, `attachments`, `boards`. Контракт — `docs/OWNERSHIP.md`.
- Свои дела получают id `d_<hex>`, наблюдаемые kanban-дела остаются `t_<hex>`; префикс —
  единственный способ различить владение и наблюдение в API, CLI и на экранах. Своё дело
  идёт в тот же срез `/now` и в те же счётчики досок (`boards[].own_deals`).
- Мутации: `POST /deals`, `PATCH /deals/{id}` и восемь команд по делу — `comment`,
  `block`, `unblock`, `claim`, `complete`, `review`, `changes`, `attach`. Ответ — форма
  `/deal` плюс `mutation: {events, idempotent}`: «сделано» и «уже было» — разные факты.
- Мутация и событие пишутся **в одной транзакции**: сбой записи события откатывает
  строку дела (обратный тест есть), иначе журнал и store разъедутся.
- Гейт считается сам: `POST /deals` даёт `todo`, `ready` — когда все родители закрыты
  (`done`/`archived`; дело без родителей получает `ready` сразу). Переход пишется в
  журнал **ребёнка** (`gate_opened`/`gate_closed`) мутацией родителя, а если родители
  были закрыты уже на момент создания — самим `create` (`cause: "created"`), иначе снимок
  `created` выглядел бы как незакрытый гейт.
- Закрытость держит норма: `commented`, `attached`, `patched`, `question_answered`
  (`journal.NON_STATE_KINDS`) состояние не меняют, поэтому поздний ответ на вопрос или
  комментарий по закрытому делу остаются фактом таймлайна, а не возвратом в работу
  (норма закреплена тестом и на уровне store, и на уровне `fold`).
- `POST /ingest` доводит дело и попытку до конца: `completed` и `attempt_ended` приходят
  тем же проходом, что остальные факты, — закрытие больше не висит на ручном шаге.

**CLI `bin/duty` — те же функции из терминала**

- `bin/duty` + `dashboard/cli.py`: `now`, `deal`, `attempts`, `stats`, `why`, `watch` —
  чтение тех же роутов без браузера. Команды зовут функции бэкенда, а не ходят в HTTP,
  поэтому «терминал сказал одно, экран другое» невозможно по построению; `--json`
  печатает ответ роута дословно.
- Коды возврата — контракт: `0` — ответ получен и `errors[]` пуст; `1` — доски или дела
  нет; `2` — источники не прочитались либо вход мутации неверный. `watch` деградацию не
  превращает в падение: печатает `errors[]` и продолжает.
- Мутации своего дела из терминала: `create`, `comment`, `block`, `unblock`, `claim`,
  `complete`, `review`, `changes`, `attach`, `archive` — с тем же поведением и теми же
  кодами, что у роутов (`docs/OWNERSHIP.md`).
- В системном `python3` нет `fastapi`, поэтому `bin/duty` перезапускает себя
  интерпретатором агента (`~/.hermes/hermes-agent/venv/bin/python3`,
  `~/.hermes/bvenv/bin/python3`); явный путь — `DUTY_PYTHON`.

**`duty demo` — прогон дела по спеке на песочном корне**

- `dashboard/demo.py`: одна команда проходит дело от создания до закрытия на песочном
  корне (временный каталог; из живого `~/.hermes` берётся только DDL схем, данные не
  читаются) и печатает отчёт — шаги, журнал дела, пул вопросов, проверки и блок «чего
  ещё нет».
- Шаги: create → claim → ask → answer → gate (родитель → ребёнок) → comment/attach →
  ingest (чужие факты) → повторный ingest → `/now` → второй вопрос → complete → поздний
  ответ. Каждый шаг помечен, **кто его сделал**: `script` — сегодня это делает прогон,
  `engine` — то, что появится с движком.
- Прогон падает, если не сходится один из семи инвариантов учёта: вопрос уводит в
  `wait_human`; ответ возвращает в работу; гейт ребёнка открывается завершением
  родителя; закрытое дело уходит из `/now`; поздний ответ не воскрешает закрытое;
  повторный `ingest` не плодит событий; `kanban.db` после прогона побайтово тот же.
- Спека-образец — `examples/demo.yaml` (этапы, роли, evidence-команды, объявленные
  вопросы). Код 0.0.3 файл не читает: движка, который исполняет этапы, нет — это 0.1.0,
  и отчёт называет этот блок отдельно, а не замалчивает.

## [0.0.2] — 03.11.2026

**Четыре экрана: «Сейчас», «Дело», «Почему стоит», «Здоровье» — и в десктопе, и в браузере**

- Появился экран **«Дело»**: спецификация карточки плюс тот же факт-набор, что в
  `/now` (попытка, лизинг, последнее действие, ожидание), и таймлайн попыток рядом.
  Раньше таймлайн жил в узкой правой панели, а тела дела не было видно вовсе.
  Новый роут `GET /deal/{board}/{task_id}`: для активного дела отдаёт элемент `/now`
  плюс `body` (обрезается `DEAL_BODY_LIMIT`), для завершённого — `deal: null` и
  `terminal: true`. Состояние ожидания завершённому делу не придумывается.
- Появился экран **«Здоровье»**: доля дел, пройденных с первой попытки, медиана
  ожидания до первой попытки (`created_at` → `started_at` первого рана) и
  таксономия исходов по всем ранам. Новый роут `GET /stats`; медиана считается по
  объединённой выборке (медиана медиан не равна медиане), недоступная доска
  уходит в `errors[]` и в итог не входит, срез, упёршийся в `STATS_TASK_LIMIT`,
  помечен `truncated`.
- Экран **«Почему стоит»** перестал быть «просто группировкой»: это карточки с
  доказательством словами бэкенда (`waiting.evidence`) — чтобы причину можно было
  проверить, а не поверить.
- **Веб-версия** (новое): `http://127.0.0.1:18742/web/hermes-duty/`, а через Hub —
  `http://127.0.0.1:8360/duty`. Те же четыре экрана, тот же шейпер: страница
  импортирует `desktop/model.js`, который бэкенд отдаёт по `/web/hermes-duty/model.js`,
  — второй копии таксономии и формулировок нет. `/duty` в браузере раньше отдавал
  404: это внутренний роут десктопа, HTTP-пути у него не было.
- На главной UI Hub (`:8360`) появилась карточка **«Дела»**: счётчики «сейчас /
  ждут ответа / досок», первые пять дел с состоянием машины, доказательством в
  тултипе и возрастом последнего действия; строка ведёт в дело
  (`/duty/#/deal/<board>/<id>`), ошибки источников — в плашке карточки. Счётчик
  «all up» хаба считает её седьмой поверхностью.
- Десктопная страница перестроена под четыре экрана: табы в шапке, клик по делу
  открывает «Дело» вместо правой панели; «Здоровье» запрашивается только когда
  открыто (`STATS_REFRESH_MS` = 30 с, срез «сейчас» — по-прежнему 10 с).
- Тесты: `pytest` 42 (+8 на `/deal`, `/stats` и их деградацию), `node` 30
  (+6 на веб-сборку: маркер токена, импорт шейпера вместо копии, четыре маршрута,
  отсутствие захардкоженного адреса).

**Выбывшие доски больше не изображают из себя источник (и не шумят)**

- `kanban/boards/_archived/` — это namespace выбывших досок, а не доска. Раньше
  агрегатор видел там `kanban.db` (0 байт) и держал в `errors[]` на каждом ответе
  «empty db», хотя источника там нет вовсе. Теперь архив в срез не читается.
- Доска с камнем `board.json` и `"archived": true` тоже считается выбывшей, даже
  если её БД лежит в `boards/<slug>/`: ядро такую доску открывать отказывается
  (`_refuse_dead_board_resurrection`), значит и показывать её как живое дело нельзя.
- Архив не исчезает молча: `GET /sources` отдаёт `archived[]` с `slug`, `path` и
  `reason` (`_archived: …` / `board.json: archived`) — «доски нет» и «доска в
  архиве» остаются различимыми. `/board/<slug>/tasks` по выбывшей доске — 404.
- Форма `/sources` расширена осознанно: 19 → 23 ключа (пинено в
  `tests/test_p0_contract.py`, там же причина). `/now` не изменился: архив не
  попадает ни в `boards[]`, ни в `errors[]`.
- Тесты: три новых кейса на namespace, на камень и на 404; красная проба показана
  (снять фильтр → те же три падают).

**Протухший снимок больше не выглядит живым**

- UI не показывает замечания прошлого ответа: если последний запрос `/now` не
  прошёл, экран держит прежний снимок, но его строки «доска X недоступна» гасятся,
  а плашка прямо говорит `снимок от HH:MM:SS — обновление не удалось: …`. Иначе
  ошибка, снятая до починки кода, висит на экране и после того, как бэкенд уже
  отдаёт чистый ответ.
- Правило собрано в модели (`noticeLines(model, stale)`), а не в рендере, — на него
  есть тест: свежий ответ даёт строки, `stale` даёт пусто.
- Ответы плагина помечены `Cache-Control: no-store, no-cache, must-revalidate` —
  и успешные, и `4xx`: без этого кэш промежуточного слоя (LAN-прокси, кэш клиента)
  вправе переиспользовать вчерашнее тело и выдать его за свежее.
- Тесты: `pytest` 34 (плюс заголовки на пяти путях), `node` 24 (плюс правило
  устаревания).

## [0.0.1] — опубликована

P0: смотреть, ни на что не влияя.

**Каркас**

- `plugin.yaml` (manifest v2), `__init__.py` с `register(ctx)`-заглушкой,
  `dashboard/manifest.json`; агентная половина намеренно ничего не регистрирует.

**Backend, только чтение**

- `dashboard/plugin_api.py`: `/health`, `/sources`, `/board/{slug}/tasks` —
  источники открываются `?mode=ro`, ядро kanban не импортируется;
- агрегатор `GET /now` — активные дела всех досок (`kanban.db` + `kanban/boards/*`)
  с лизингом (`claim_lock`/`claim_expires`), попыткой (pid + `os.kill(pid, 0)`,
  возраст heartbeat), последним действием (`task_events`, heartbeat вторичен) и
  исходом последнего рана;
- таксономия ожиданий в приоритете `wait_human` > `capability` > `dead_lease` >
  `crashed` > `working` > `no_signal` > `wait_slot` > `wait_gate`: состояние
  выводится из набора фактов, каждый сработавший факт уходит в
  `waiting.evidence`; `no_signal` — дело со `status=running`, у которого нет ни
  рана, ни pid, ни heartbeat (раньше такие показывались зелёным «работает»);
- честность сигналов (ревью RV2, п. 1–11): факт про pid называет ровно то, что
  известно — `pid N жив` / `состояние pid N неизвестно` (живость не проверена:
  `os.kill` вернул чужой `OSError`) / `pid не записан` (пустой `worker_pid`);
  формулировка вынесена в одну функцию `_pid_text`, поэтому ветки `crashed` и
  `working` не разъезжаются и не печатают «pid None жив» (RV3 п. 1–2);
  `attempt.source = run|task` показывает, что часть фактов попытки
  добрана из карточки, а не из рана; `int()` по чужой схеме доски не валит роут
  (`errors[]` с типом исключения);
- фильтры `?board=<slug>` (404 на неизвестную доску) и `?state=<waiting.state>`
  (400 на состояние вне таксономии);
- `GET /duty/{board}/{task_id}/attempts` — таймлайн попыток по `task_runs` и
  привязанным к ранам `task_events`: длительность, исход, текст ошибки, события;
- деградация честная: недоступный `messaging/pool.db` (нет файла или это не БД)
  попадает в `errors[]` и в `waiting.evidence` («факт `wait_human` не проверен»), а
  не выглядит как «вопросов нет»; обрезанный пул (`QUESTION_LIMIT = 200`) и
  обрезанный срез доски (`DEAL_LIMIT = 500`) помечаются причиной, а не молчат;
  0-байтная `kanban.db` видна как `boards[].read = false` с `note = "empty db"`;
  нечитаемая доска — `boards[].read = false` + `errors[]` при HTTP 200; сбой
  вспомогательной таблицы — `boards[].warnings[]`;
- набор «падений» и порядок состояний приходят клиенту в ответе (`crash_outcomes`,
  `by_state`), поэтому UI не держит их копию;
- `/now` открывает одно read-only соединение на доску (одна транзакция-снимок) и
  ограничивает `task_links` делами среза — замер на 19 досках: 20 соединений на `/now` (по одному на БД плюс `pool.db`), а не соединение на каждый запрос среза.

**Страница `/duty` (desktop)**

- `desktop/plugin.js`: полноэкранная страница `area: 'routes'` и пункт сайдбара
  «Дела»; таблица активных дел группами по `waiting.state` в порядке ответа,
  локальные фильтры (доска, чипы состояний, поиск по `id`/заголовку с debounce),
  таймлайн попыток в правой панели, автообновление `/now` раз в 10 с с подписью

  затираются); недоступные доски, упавшие источники, обрезанный срез

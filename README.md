# Hermes Duty — плагин «Дела»: от наблюдаемости к движку (0.0.4)

Плагин к Hermes Desktop: **дело** (duty) вместо карточки, **этап** вместо подзадачи,
**попытка** вместо рана. Начиналось с наблюдения: собрать лизинги и события из живых
источников и показать, кто что держит и что делает прямо сейчас. В 0.0.3 к этому
добавились свой журнал (`state = fold(events)`), свой store дел и CLI, в 0.0.4 —
движок: спека дела, переход по журналу, попытка как процесс, evidence-гейт, классы
отказа и драйвер, который доводит дело до конца. Ядро Hermes не патчится, `kanban.db`
и `state.db` открываются только на чтение — единственная запись в чужой файл идёт
через `ask()` в пул вопросов, и только по явному запросу.

## Зачем

Kanban-ядро смешивает три ответственности (хранилище карточек, планировщик со
spawn-RPC, политику workflow). Каждый новый баг лечится новой колонкой или новым
условием записи статуса, а наблюдаемость выводится из тех же изменяемых колонок и
врёт ровно тогда, когда сломано.

Duty выводит состояние из журнала (`state = fold(events)`), а не из колонок. Этим
плагином мы начинаем с самой дешёвой части: **смотреть, ни на что не влияя**.

Дизайн целиком (7 вкладок: диагноз, модель, этап изнутри, вопросы и адресация,
наблюдаемость, варианты, фазы) — `~/.hermes/widgets/duty-model.html`,
доктрина — скилл `agent-orchestration-design` (`references/duty-model.md`).

## Что умеет 0.0.4

Одно дело идёт от спеки до закрытых этапов без ручной работы из Python. Цикл собран
из готовых слоёв, и каждый шаг принадлежит своему модулю — драйвер только спрашивает
и исполняет:

```
duty.yaml ──▶ bin/duty spec check ──▶ годна (или «file:line: правило: текст»)
                  │
                  ▼
   bin/duty create --spec … ──▶ дело d_<hex>, путь спеки в created.payload.spec
                  │
                  ▼
┌─ dashboard/driver.py: цикл ──────────────────────────────────┐
│ transit.next_stage(spec, events) → что дальше                │
│   ├─ run(stage#n) → runner.step:                             │
│   │     лизинг → дерево попытки → контракт файлом →          │
│   │     hermes chat -p <role> … → attempt_progress в журнал  │
│   │           │                                              │
│   │           ▼                                              │
│   │     evidence.verify(пакет отчёта)                        │
│   │       ├─ ok  → attempt_ended(outcome=done)               │
│   │       └─ нет → attempt_ended(outcome=failed, kind=…)     │
│   │                 │                                        │
│   │                 ▼                                        │
│   │     failures.decide_park(класс, счётчик, лимит)          │
│   │       ├─ повтор → wait(retry, retry_at)                  │
│   │       └─ исчерпан → park: вопрос ask() + blocked(parked) │
│   ├─ wait(…)  → выход, код 3                                 │
│   ├─ done     → выход, код 0                                 │
│   ├─ failed   → выход, код 1                                 │
│   └─ park     → выход, код 2                                 │
│ после каждого шага журнал перечитывается целиком             │
└──────────────────────────────────────────────────────────────┘
                  │
                  ▼
  bin/duty why <board> <id> [этап] · экран «Дело» → stages[] · /now → stage
```

1. **Спека проверяется до запуска.** `bin/duty spec check duty.yaml` — `OK` либо
   `file:line: правило: текст`; правила (включая `review-gate`: публикация не
   обгоняет ревью) — `docs/SPEC.md`. Коды: `0` годна, `1` есть отказы, `2` спека не
   читается.
2. **Дело заводится со спекой.** `bin/duty create --board <slug> --title "…" --spec
   duty.yaml` (или `POST /deals`): путь разворачивается в абсолютный и пишется в
   `created.payload.spec` — по нему экран «Дело» рисует ленту этапов. `--external-ref
   jira:RP-14080` делает «продолжить» идемпотентным: живое дело с этим именем
   возвращается как есть, закрытое не воскрешается.
3. **Движок доводит дело.** `bin/duty run d_…` — цикл «решение → шаг → перечитать
   журнал». Состояние прогона — журнал, а не память процесса: прогон, убитый после
   `impl`, при повторном запуске идёт в `verify`. `--once` — один шаг, `--max-steps N`
   — предел (по умолчанию 20), `wait` — **выход с кодом 3**, а не занятая петля.
4. **«Готово» принимается только с пакетом.** Голословное «готово» не проходит:
   гейт сверяет отчёт с деревом попытки (хеши файлов, резолв коммита, коды
   и свежесть объявленных команд, бюджет токенов), иначе пишет `attempt_ended` с
   `outcome=failed` и классом отказа.
5. **Отказ классифицируется и повторяется по политике.** Три класса (`infra`,
   `contract`, `capability`) и лимиты — в одном модуле (`dashboard/failures.py`);
   исчерпание паркует дело: вопрос человеку в пул плюс `blocked` с
   `block_kind='parked'`. Продолжает только человек — `bin/duty unblock`, со сбросом
   счётчиков класса.
6. **Каждая попытка видна в консоли.** `GET /deal` → `stages[]`, `GET /now` →
   `deals[].stage`: состояние этапа, номер попытки, время, длительность, код выхода,
   токены, инструменты, причина отказа, ожидание вопроса. Источник один — журнал, ни
   `ps`, ни `lsof`.
7. **Осиротевшая попытка закрывается движком, а не остаётся навсегда.** Попытка без
   `attempt_ended`, у которой истёк лизинг и прошёл срок (`ttl + max(60 с, ttl/3)`),
   закрывается `attempt_ended` с `kind=infra` и `reaped: true`
   (`dashboard/reaper.py`). Драйвер зовёт уборку перед каждым решением, поэтому
   `bin/duty run`, убитый снаружи во время попытки, лечится следующим запуском;
   `bin/duty reap [--dry-run]` делает то же вручную.

### Чем 0.0.4 **ещё не** является

- **P5 не сделана: канбан не в архиве.** Старые доски живут как раньше, ядро kanban
  не трогается, ingest из него продолжается. Переезд — следующая фаза, не эта.
- **Переезд новых работ пока наблюдается, а не доказан.** Гейт P4 («две недели новая
  работа идёт только через дела, канбан не растёт») — пост-релизное обязательство: в
  0.0.4 сдаётся механизм (кнопка «Продолжить» в `hermes-tickets` создаёт дело, новые
  доски не заводятся), а сам гейт закрывается наблюдением после выпуска.
- **Модель внутри движка не вызывается.** `hermes chat -p <role> --query-file …
  --format stream-json --oneshot` движок **спавнит как процесс**, но ни одного
  решения на модели в самом duty нет: «что дальше» считает `transit.next_stage`,
  класс отказа — `failures.classify`, приёмку пакета — `evidence.verify`. Модель
  работает только исполнителем контракта, внутри своей попытки.
- **Движок не закрывает дело в store.** Прогон, дошедший до `done`, закрывает этапы
  в журнале, но строка дела остаётся `running`: закрытие — бизнес-правило
  (`deals.complete_deal`), в драйвер не входит. В `/now` такое дело видно как
  `no_signal` («status=running без попытки»).
- **Нет декомпозиции.** Разбор дела на подзадачи — движок 0.1.0; это же печатает
  `bin/duty demo` в блоке «чего ещё нет». Уборка осиротевшей попытки (`reap`) в 0.0.4
  уже есть — факт `attempt_ended`, лизинг умершей попытки отпускается; дерево попытки
  уборка не трогает (`workspace: worktree` убирает сам движок при отказе попытки).
- **E2E: цепочка impl → verify пройдена живым прогоном, публикация — нет.** Живой
  прогон 04.11 (`d_a2a26b55`) прошёл `impl`, а `verify` упал дефектом: дерево этапа
  отводилось от базы дела, и второй этап не видел работу первого. После правки
  (`runner.base_of_stage` + коммит принятой работы движком) двухэтапная проба
  `d_a71a59e0` на копии кейса прошла оба этапа: `verify` получил дерево от коммита
  `impl` и нашёл его файл. Гейт P2 целиком («… → review → публикация») закрывается
  живым прогоном, где публикация требует «ок» Max.

## Что уже работает (роуты и экраны)

Роуты (монтируются под `/api/plugins/hermes-duty`; чужие источники открываются только
на чтение, пишет плагин только в свою БД `duty/duty.db` — журнал событий и store своих
дел, по требованию и по явной мутации — и в пул `messaging/pool.db` единственным
каналом вопросов `ask()`):

| роут | что отдаёт | ошибки |
|---|---|---|
| `GET /health` | версия, корень Hermes, число БД и читаемых, строки `tasks`, наличие пула, `journal: {events, deals, drift: {empty_journal}}`, `mode` | — |
| `GET /sources` | доски с размером и счётчиками, пул по `origin × status`, список профилей | — |
| `GET /board/{slug}/tasks` | сырой срез активных карточек доски (до 200) | 404 — доски нет |
| `GET /now?board=<slug>&state=<waiting.state>&ingest=1` | срез «сейчас»: лизинг, попытка, последнее действие, этап графа (`stage`: `{id, role, attempt, state, live, since}` — из журнала, `null` без попыток), таксономия ожидания; `?ingest=1` — сначала прогнать ingest в свой журнал | 404 — доски нет; 400 — состояние не из таксономии |
| `POST /ingest` | проход ingest: дописать в свой журнал недостающие события (`appended`, `events`, `deals`, отчёт по доскам, `errors[]`); в том же проходе — `answers` (ответы пула `question_answered`); повторный вызов — `appended: 0` | 503 — журнал не открылся |
| `POST /ask/{board}/{task_id}` | вопрос по делу в пул (`origin='duty'`, `kind='decision'`) + событие `question_asked`; тело `{text, text_full, options, critical}`, ответ `{question_id, created, deduped, adopted, errors[]}`; живой вопрос по делу возвращается как есть (`deduped: true`), дубль в пуле не создаётся; подхваченный чужой вопрос (`origin != 'duty'`) отличается полем `adopted: true` и в журнал не пишется | 404 — нет доски/дела; 400 — пустой `text` или `options` не список строк; 503 — пул или журнал недоступны (`errors[]`) |
| `GET /duty/{board}/{task_id}/attempts` | таймлайн попыток дела: раны, длительность, исход, ошибка, события | 404 — нет доски/дела; 503 — доска не читается |
| `GET /deal/{board}/{task_id}?spec=<абсолютный путь>` | одно дело: элемент `/now` (если оно активно), `body` спецификации, `terminal`, `comments[]`, `attachments[]`, `timeline[]`, лента этапов `stages[]` + `stages_note` (причина пустой ленты) + `spec`. Этапы считает `transit.stage_states` по журналу, попытки — из `attempt_started`/`attempt_ended`, граф читается `spec.py` из `created.payload.spec` (или `?spec=`); процессов ручка не открывает, в журнал не пишет. `id` решается префиксом: `t_<hex>` — наблюдаемое дело kanban, `d_<hex>` — своё (store) | 404 — нет доски/дела; 503 — доска или store не читается |
| `GET /stats?board=<slug>&since=<unix>` | здоровье: доля с первой попытки, распределение ожидания до неё (`waiting_sec`: p50/p90/p99, `count`, `max`), таксономия исходов по доскам и итогом; `?board=` — одна доска, `?since=` — только дела, созданные не раньше этой секунды | 404 — доски нет; — (деградация в `errors[]`, неполная выборка — в `warnings[]`) |
| `POST /deals` | завести своё дело (`status=todo`, id `d_<hex>`): `{board, title, body?, assignee?, parents?[], spec?, external_ref?, dedup_window?}`; `spec` — абсолютный путь к `duty.yaml`, по которому экран «Дело» строит ленту этапов (пишется в `created.payload.spec`); `external_ref` — внешнее имя дела (`jira:RP-14080`): живое дело с этим именем на этой доске возвращается как есть (`created: false`, `existing: true`, причина в `reason`, события не пишутся), закрытое (`done`/`archived`) не воскрешается — заводится новое (`created: true`); `dedup_window` — срок жизни имени в секундах | 400 — вход не тот; 503 — store не открылся |
| `PATCH /deals/{id}` | правка спецификации (`title`/`body`/`assignee`) или `{status: archived}`; `origin` и `id` не меняются, смена статуса — только командами | 404 — дела нет; 400 — статус мимо команды |
| `POST /deals/{id}/comment` | комментарий в своё дело: `{author, body}` | 404 — дела нет; 400 — пустой `body` |
| `POST /deals/{id}/block` | блокировка: `{kind, reason}` (`block_kind`, по умолчанию `needs_input`) | 404 — дела нет; 400 — архивное дело |
| `POST /deals/{id}/unblock` | снять блокировку | 404 — дела нет; 400 — архивное дело |
| `POST /deals/{id}/claim` | взять в работу: `{owner}` | 404 — дела нет; 400 — архивное дело |
| `POST /deals/{id}/complete` | закрыть дело или сдать в ревью: `{summary, review?, reviewer?}` | 404 — дела нет; 400 — архивное дело |
| `POST /deals/{id}/review` | сдать в ревью: `{reviewer?, summary?}` | 404 — дела нет; 400 — архивное дело |
| `POST /deals/{id}/changes` | вернуть на доработку: `{reason, reviewer?}` (причина обязательна) | 404 — дела нет; 400 — пустая причина |
| `POST /deals/{id}/attach` | приложить файл (multipart `file`): метаданные в `attachments`, копия в `duty/attachments/<id>/` | 404 — дела нет; 400 — пустой файл |

Мутации своих дел отвечают той же формой, что `GET /deal` (дело + факты + таймлайн),
плюс блок `mutation: {events, idempotent}`: повтор того же вызова не плодит событий
(`events: 0`, `idempotent: true`), а «делать нечего» — это ошибка входа с причиной.
Контракт владения — `docs/OWNERSHIP.md`, правила журнала — `docs/JOURNAL.md`.

**Два пространства id.** `t_<hex>` — дело kanban, которое плагин только наблюдает;
`d_<hex>` — своё дело, которым он владеет. Префикс — единственный способ их различить
в API, в CLI и на экранах: `d_` не ищется на доске kanban, `t_` — в своём store.
Свои дела попадают в тот же срез `/now` и в те же счётчики досок (`boards[].own_deals`),
поэтому «сколько дел» одно, а не два.

`waiting` в `/now` и `/deal` считается **fold'ом по своему журналу** (контракт
`docs/JOURNAL.md`): дело без событий считается по kanban, и `waiting.evidence`
начинается с `journal: empty — состояние из kanban`. `journal.drift.empty_journal`
в `/health` — сколько активных дел журнал ещё не подобрал; `POST /ingest` доводит
это число до нуля, `waiting.human_kind` отличает `question` (есть живой вопрос, на
него можно ответить) от `status` (человек нужен, вопроса нет). В шапке «Сейчас»
это двумя числами — `N вопросов + M блокировок`; вопрос задаётся явно,
`POST /ask/{board}/{task_id}`, и он же единственное место, где плагин пишет в пул.

Экраны (детальная форма ответа и правила таксономии — `docs/DESIGN.md`):

Четыре экрана, одни и те же в двух поверхностях — десктопе и браузере:

| экран | что показывает | откуда данные |
|---|---|---|
| **Сейчас** | таблица активных дел группами по `waiting.state`, фильтры (доска, чипы состояний, поиск по `id`/заголовку/исполнителю), автообновление 10 с, подпись «обновлено N с назад» | `GET /now` |
| **Дело** | лента этапов (имя, роль, состояние, номер попытки; у попытки — время, длительность, код выхода, токены, инструменты, причина отказа; ожидание вопроса — строкой со ссылкой на `/imsg`), спецификация карточки, факты (попытка, лизинг, последнее действие, ожидание) и таймлайн попыток рядом; таб открывает последнее дело, а без выбора — список активных | `GET /deal/{board}/{id}` (`stages[]`) + `GET /duty/{board}/{id}/attempts` |
| **Почему стоит** | карточки дел с доказательством словами бэкенда — чтобы причину можно было проверить, а не поверить | `GET /now` (`waiting.evidence`) |
| **Здоровье** | дела с первой попытки, ожидание до неё распределением (p50/p90/p99, максимум, размер выборки), таксономия исходов, срез по доскам | `GET /stats` |

Где открыть:

- десктоп — пункт сайдбара **«Дела»** (роут приложения `/duty`, это не HTTP-путь);
- браузер — `http://127.0.0.1:18742/web/hermes-duty/` напрямую или
  `http://127.0.0.1:8360/duty` через Hub (прокси-роут `~/.hermes/dashboard/serve.py`);
  на главной Hub (`:8360`) есть карточка **«Дела»**: счётчики «сейчас / ждут
  ответа / досок», первые пять дел со состоянием и доказательством в тултипе,
  ссылка в дело через `#/deal/<board>/<id>`.

Веб-страница и десктоп делят один шейпер: веб импортирует `./model.js`, который
бэкенд отдаёт по `/web/hermes-duty/model.js` из `desktop/model.js`. Второй копии
таксономии, подписей и формулировок доказательств нет — иначе две поверхности
разъезжались бы молча.

Недоступные доски и упавшие источники видны в ответе (`boards[].read`, `errors[]`)
и на экранах — жёлтой полосой и списком в пустом состоянии.

## CLI `bin/duty`

Тот же бэкенд, что у роутов, но из терминала: команды вызывают те же функции
(`dashboard/plugin_api.py`), а не ходят в HTTP и не пересчитывают состояния. `--json`
печатает ответ роута дословно — второй формы у CLI нет, поэтому «терминал сказал одно,
экран другое» невозможно по построению.

```bash
~/.hermes/plugins/hermes-duty/bin/duty now
# в профильной оболочке (HERMES_HOME=~/.hermes/profiles/<role>) досок там нет — корень задаётся явно:
HERMES_HOME=~/.hermes ~/.hermes/plugins/hermes-duty/bin/duty now
```

| команда | что делает |
|---|---|
| `duty now [--board B] [--state S]` | таблица активных дел: доска, `id`, состояние (у `wait_human` — с `/human_kind`), ожидание, возраст, доказательство |
| `duty deal <board> <id>` | карточка дела: те же факты плюс таймлайн попыток |
| `duty attempts <board> <id>` | только таймлайн попыток |
| `duty stats [--board B] [--since D]` | p50/p90/p99 ожидания, исходы ранов, доля с первой попытки, таблица по доскам; `--since` — unix, `YYYY-MM-DD` или `YYYY-MM-DDTHH:MM` |
| `duty why <board> <id>` | доказательство `waiting.evidence` словами бэкенда плюс факты, из которых оно собрано |
| `duty why <board> <id> <этап>` | то же плюс приговор последней попытки этапа: исход, класс отказа, первые `details` evidence-гейта |
| `duty run <deal_id> [--spec <duty.yaml>] [--max-steps N] [--json] [--once]` | довести своё дело: цикл «решение → шаг → перечитать журнал»; `--once` — один шаг, предел `--max-steps` (по умолчанию 20, дело при этом не меняется). Коды свои: `0` закрыто, `1` остановлено отказом, `2` припарковано, `3` ждёт (вопрос/`retry_at`/чужой лизинг/гейт — выход, а не петля), `4` предел шагов, `130` SIGINT |
| `duty spec check <file> [--json]` | спека дела **до запуска**: `OK` либо `file:line: правило: текст`; правила — `docs/SPEC.md`, ни одного процесса (кроме `git rev-parse` для `base`). Коды: `0` годна, `1` есть отказы, `2` спека не читается |
| `duty reap [--dry-run]` | закрыть осиротевшие попытки **своего** store: `attempt_started` без `attempt_ended`, лизинг истёк и возраст попытки больше `ttl + max(60 с, ttl/3)` → `attempt_ended` с `kind=infra` и `reaped: true`, лизинг умершей попытки отпускается. `--dry-run` показывает, что было бы закрыто, ничего не записывая. Живой лизинг не трогается: `ps` уборка не смотрит. Код `0` — «посчитано» (в том числе «убирать нечего») |
| `duty demo [--home DIR] [--keep]` | прогон одного дела по спеке на **песочном корне** (временный каталог): create → claim → ask → answer → gate → comment/attach → ingest → complete → late answer. Сам проверяет 7 инвариантов (вопрос уводит в `wait_human`, ответ возвращает в работу, гейт открывается завершением родителя, закрытое дело уходит из `/now`, поздний ответ не воскрешает, повторный ingest не плодит, `kanban.db` не изменился) и печатает границу «чего ещё нет до движка 0.1.0». Живые БД только читаются; `--keep` оставляет песочницу для разбора |
| `duty watch [--interval 10] [--board B] [--state S]` | тот же `now`, перерисовка в терминале (в пайпе — блоками, без escape-последовательностей) |
| `duty create --board B --title "…" [--body-file F] [--assignee ROLE] [--spec duty.yaml] [--external-ref jira:RP-14080] [--parent d_…]…` | завести своё дело; `--spec` — граф дела (путь разворачивается в абсолютный, иначе лента этапов молчит с названной причиной); `--external-ref` — внешнее имя: живое дело с этим именем не дублируется (ответ `created: false`/`existing: true`), закрытое не воскрешается; `--json` отдаёт `deal_id`, `created` и `status` для следующих команд |
| `duty comment d_… "текст" [--author …]` | комментарий в своё дело (`--author`, по умолчанию `max`) |
| `duty block d_… [причина] [--kind needs_input]` | заблокировать своё дело |
| `duty unblock d_…` | снять блокировку |
| `duty claim d_… [--owner …]` | взять в работу (владелец — `--owner`, иначе `HERMES_PROFILE`, иначе пользователь ОС) |
| `duty complete d_… [--summary …] [--review] [--reviewer …]` | закрыть дело или сдать в ревью |
| `duty review d_… [--reviewer …] [--summary …]` | сдать в ревью |
| `duty changes d_… "причина" [--reviewer …]` | вернуть на доработку |
| `duty attach d_… FILE` | приложить файл (копия в `duty/attachments/<deal_id>/`) |
| `duty archive d_…` | `PATCH {status: archived}` — архив назван командой |

`duty demo` — не роут, а прогон модели труда: одна команда проходит дело от создания
до закрытия на песочном корне (временный каталог; из `~/.hermes` берётся только DDL схем,
данные не читаются), проверяет семь инвариантов учёта и печатает отчёт — шаги, журнал
дела, пул вопросов, проверки и блок «чего ещё нет». Спека-образец — `examples/demo.yaml`
(тот же текст печатается в отчёте): этапы и evidence-команды в нём есть, но `demo`
исполняет **учёт**, а не движок: файл остался от 0.0.3 и формату 0.0.4 не отвечает
(`bin/duty spec check examples/demo.yaml` даёт отказ на `questions` и на
`verdict.approve: done`). Спеку для `bin/duty run` пишут по `examples/duty-minimal.yaml`
или по `examples/duty.yaml` — оба `spec check` проходит. Тесты прогона —
`tests/test_demo.py` (9 кейсов).

Коды возврата: `0` — ответ получен целиком и `errors[]` пуст; `1` — доски или дела нет
(404 роута); `2` — источники не прочитались (503/400 роута или непустой `errors[]`)
либо неверный вход мутации. `--json` работает и до команды, и после неё. У `duty run`
коды свои (`0/1/2/3/4/130`) — они перечислены в таблице выше и в `docs/RUNBOOK.md`:
`3` и `4` там означают «ждём» и «упёрлись в предел», а не ошибку входа.

Интерпретатор: `dashboard/plugin_api.py` импортирует `fastapi`, которого в системном
`python3` нет, поэтому `bin/duty` перезапускает себя интерпретатором агента
(`~/.hermes/hermes-agent/venv/bin/python3`, `~/.hermes/bvenv/bin/python3`). Свой путь —
`DUTY_PYTHON=/path/to/python`.

## Принципы P0

1. **Только чтение чужого.** Чужие источники открываются в режиме `?mode=ro`; плагин
   не пишет ни в `kanban.db`, ни в `state.db` (инвариант проверяется тестом по `mtime`).
   Что он пишет — только своё: БД `duty/duty.db` (журнал событий и store своих дел —
   по явному `POST /ingest`/`GET /now?ingest=1` и по явным мутациям `/deals…`) и пул
   вопросов `messaging/pool.db` — и пул только через `ask()` (`dashboard/ask.py`), по
   явному `POST /ask/{board}/{task_id}`.
2. **Источники не смешиваются с истиной.** Консоль не пересчитывает статусы карточек
   и не пытается «угадать» состояние — она показывает лизинг, процесс и последнее
   действие, как они записаны в источниках.
3. **Честная таксономия.** `wait_human`, `capability`, `dead_lease`, `crashed`,
   `working`, `no_signal`, `wait_slot`, `wait_gate` — восемь взаимоисключающих
   состояний по приоритету, а не «blocked»; каждый факт показывается
   доказательством, а дело без живого сигнала не выдаётся за работающее.
4. **Деградация вместо 500.** Недоступная доска или пул вопросов попадают в
   `errors[]` при HTTP 200, а не превращаются в падение роута.
5. **Ничего не автозапускается.** Все процессы — внутри существующего жизненного
   цикла Hermes (бэкенд dashboard) и только по явной команде человека
   (`bin/duty run`), никаких новых launchd-джоб и своих планировщиков: движок не
   крутится в фоне и не поднимает попытку сам.

## Установка

Плагин ставится как обычный пользовательский плагин из каталога:

```bash
hermes plugins enable hermes-duty     # или Capabilities → Plugins в десктопе
```

Данные — вне плагина (`~/.hermes/`), при переустановке не теряются.

## Проверка

Из каталога плагина (`cd ~/.hermes/plugins/hermes-duty`):

```bash
~/.hermes/hermes-agent/venv/bin/python -m pytest tests/ -q  # 555 passed, 1 skipped
node --test tests/model.test.mjs tests/web.test.mjs        # 49 pass (37 + 12)
bin/duty-model-sync --check                                # OK
bin/duty-version check                                     # OK
HERMES_HOME=~/.hermes bin/duty now                         # таблица дел, код 0
HERMES_HOME=~/.hermes bin/duty demo                        # 7 проверок OK, код 0
HERMES_HOME=~/.hermes bin/duty spec check examples/duty.yaml  # OK, код 0
```

Живой рендер смотрится в приложении (после включения плагина) и в браузере —
`http://127.0.0.1:8360/duty`. Пошаговая проверка руками (включая «страница
пустая» и «доска недоступна») — `docs/RUNBOOK.md`.

Десктопная половина грузится как **ES-модуль**: загрузчик берёт `desktop/plugin.js`,
подменяет импорты и делает `import(blob)`. Поэтому файл нельзя проверять как
CommonJS — `node --check plugin.js` пропускает то, что валит парсер модуля (так в 0.0.3
плагин на день выпал из приложения из-за висячей запятой). Синтаксис проверяет
`tests/test_frontend_syntax.py`: он копирует `desktop/plugin.js` и
`dashboard/web/app.js` в `.mjs` и разбирает их парсером модуля.

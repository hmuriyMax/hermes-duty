# Hermes Duty — плагин «Дела»: дело вместо карточки, видимая работа и её конец (0.1.0)

Плагин к Hermes Desktop: **дело** (duty) вместо карточки, **этап** вместо подзадачи,
**попытка** вместо рана. Начиналось с наблюдения: собрать лизинги и события из живых
источников и показать, кто что держит и что делает прямо сейчас. В 0.0.3 к этому
добавились свой журнал (`state = fold(events)`), свой store дел и CLI, в 0.0.4 —
движок: спека дела, переход по журналу, попытка как процесс, evidence-гейт, классы
отказа и драйвер, который доводит дело до конца. Ядро Hermes не патчится, `kanban.db`
и `state.db` открываются только на чтение — единственная запись в чужой файл идёт
через `ask()` в пул вопросов, и только по явному запросу.

## Зачем

Kanban-ядро смешивает три ответственности (хранилище карточек, планировщик со
spawn-RPC, политику workflow). Каждый новый баг лечится новой колонкой или новым
условием записи статуса, а наблюдаемость выводится из тех же изменяемых колонок и
врёт ровно тогда, когда сломано.

Duty выводит состояние из журнала (`state = fold(events)`), а не из колонок. Этим
плагином мы начинаем с самой дешёвой части: **смотреть, ни на что не влияя**.

Дизайн целиком (7 вкладок: диагноз, модель, этап изнутри, вопросы и адресация,
наблюдаемость, варианты, фазы) — `~/.hermes/widgets/duty-model.html`,
доктрина — скилл `agent-orchestration-design` (`references/duty-model.md`).

## Что умеет 0.0.4

Одно дело идёт от спеки до закрытых этапов без ручной работы из Python. Цикл собран
из готовых слоёв, и каждый шаг принадлежит своему модулю — драйвер только спрашивает
и исполняет:

```
duty.yaml ──▶ bin/duty spec check ──▶ годна (или «file:line: правило: текст»)
                  │
                  ▼
   bin/duty create --spec … ──▶ дело d_<hex>, путь спеки в created.payload.spec
                  │
                  ▼
┌─ dashboard/driver.py: цикл ──────────────────────────────────┐
│ transit.next_stage(spec, events) → что дальше                │
│   ├─ run(stage#n) → runner.step:                             │
│   │     лизинг → дерево попытки → контракт файлом →          │
│   │     hermes chat -p <role> … → attempt_progress в журнал  │
│   │           │                                              │
│   │           ▼                                              │
│   │     evidence.verify(пакет отчёта)                        │
│   │       ├─ ok  → attempt_ended(outcome=done)               │
│   │       └─ нет → attempt_ended(outcome=failed, kind=…)     │
│   │                 │                                        │
│   │                 ▼                                        │
│   │     failures.decide_park(класс, счётчик, лимит)          │
│   │       ├─ повтор → wait(retry, retry_at)                  │
│   │       └─ исчерпан → park: вопрос ask() + blocked(parked) │
│   ├─ wait(…)  → выход, код 3                                 │
│   ├─ done     → выход, код 0                                 │
│   ├─ failed   → выход, код 1                                 │
│   └─ park     → выход, код 2                                 │
│ после каждого шага журнал перечитывается целиком             │
└──────────────────────────────────────────────────────────────┘
                  │
                  ▼
  bin/duty why d_… [этап] · экран «Дело» → stages[] · /now → stage
```

База этапа — это **не** база дела: дерево отводится от того, что произвёл предшественник,
а принятую работу движок коммитит сам: коммит появляется в дереве попытки и закрепляется веткой дела `duty/<deal_id>` — ветки человека (`main`, `release/*`) движок не двигает.

```
spec.base (origin/master)
    │
    ▼
impl   попытка 1 ── дерево от spec.base ──────▶ evidence ok ──▶ движок коммитит
    │                                                            attempt_ended.commit = c1
    ▼
verify попытка 1 ── дерево от коммита impl ────▶ файлы impl на месте ──▶ evidence ok
    │
    ▼
review попытка 1 ── дерево от коммита verify ──▶ … ──▶ все этапы done
```

1. **Спека проверяется до запуска.** `bin/duty spec check duty.yaml` — `OK` либо
   `file:line: правило: текст`; правила (включая `review-gate`: публикация не
   обгоняет ревью) — `docs/SPEC.md`. Коды: `0` годна, `1` есть отказы, `2` спека не
   читается.
2. **Дело заводится со спекой.** `bin/duty create --title "…" --spec duty.yaml
   [--repo <путь>]` (или `POST /deals`): путь разворачивается в абсолютный и пишется в
   `created.payload.spec` — по нему экран «Дело» рисует ленту этапов; `repo` — то, по чему
   дело группируется на всех поверхностях (по умолчанию `repo` из спеки, иначе «без
   репозитория»). `--external-ref
   jira:RP-14080` делает «продолжить» идемпотентным: живое дело с этим именем
   возвращается как есть, закрытое не воскрешается.
3. **Движок доводит дело.** `bin/duty run d_…` — цикл «решение → шаг → перечитать
   журнал». Состояние прогона — журнал, а не память процесса: прогон, убитый после
   `impl`, при повторном запуске идёт в `verify`. `--once` — один шаг, `--max-steps N`
   — предел (по умолчанию 20), `wait` — **выход с кодом 3**, а не занятая петля.
4. **Этап отводится от коммита предшественника.** У этапа без `needs` база —
   `spec.base`; у следующего — коммит последней успешной попытки предшественника
   (`runner.base_of_stage`). Принятую работу движок фиксирует сам
   (`runner.commit_tree`: `git add -A` и коммит `duty: <дело> <этап> attempt <n>` в
   дереве попытки, detached HEAD) и пишет sha в `attempt_ended.payload.commit`;
   фактическая база едет в `attempt_started.base`/`attempt_ended.base`. Что это значит
   для автора спеки: `base` — база **только первого этапа**, а `verify` после `impl`
   видит файлы `impl`, потому что его дерево отведено от коммита `impl`. Этап с
   `needs` по умолчанию получает `workspace: worktree`; «дерево не нужно» пишется
   явно (`workspace: none`), иначе `bin/duty spec check` отказывает.
5. **Отчёт попытки — файл, а не текст в ответе.** Движок пишет входной контракт
   (`<workdir>/.duty/in-<этап>-<попытка>.json`, передаётся процессу `--query-file`) и
   кладёт в него адрес результата: `report_to` = `<workdir>/.duty/result.json`. Отчёт
   пишется инструментом `write_file` по `report_schema`, которую гейт и проверяет; текст
   в ответе модели движок не читает. Поэтому read-only роль (`reviewer`) пишет **только**
   этот файл и ничего больше: право записи выдаёт контракт попытки, а не имя роли
   (`role-access`), shell у read-only роли нет вовсе. Нет файла — `failed(contract)` с
   причиной `result.json нет: <путь>`. Права ролей целиком — `docs/PROBES.md`.
6. **«Готово» принимается только с пакетом.** Голословное «готово» не проходит:
   гейт сверяет отчёт с деревом попытки (хеши файлов, резолв коммита, коды
   и свежесть объявленных команд, бюджет токенов), иначе пишет `attempt_ended` с
   `outcome=failed` и классом отказа.
7. **Отказ классифицируется и повторяется по политике.** Три класса (`infra`,
   `contract`, `capability`) и лимиты — в одном модуле (`dashboard/failures.py`);
   исчерпание паркует дело: вопрос человеку в пул плюс `blocked` с
   `block_kind='parked'`. Продолжает только человек — `bin/duty decide <дело>
   continue` (он же `bin/duty unblock`), со сбросом счётчиков класса; ответ в пуле
   решением не является.
8. **Каждая попытка видна в консоли.** `GET /deal` → `stages[]`, `GET /now` →
   `deals[].stage`: состояние этапа, номер попытки, время, длительность, код выхода,
   токены, инструменты, причина отказа, ожидание вопроса. Источник один — журнал, ни
   `ps`, ни `lsof`. Тот же таймлайн из терминала — `bin/duty attempts d_…`
   (этап, номер, исход и длительность, `base`/`commit`, pid, число событий прогресса).
9. **Осиротевшая попытка закрывается движком, а не остаётся навсегда.** Попытка без
   `attempt_ended` закрывается `attempt_ended` с `kind=infra` и `reaped: true`
   (`dashboard/reaper.py`), если истёк лизинг и прошёл срок (`ttl + max(60 с, ttl/3)`)
   **или** умер её pid (`os.kill(pid, 0)` → `ProcessLookupError`): воркер, убитый
   рестартом движка, не висит «попытка идёт» до конца лизинга. Свой pid спрашивается
   только у своего дела и не раньше минуты жизни попытки, `PermissionError` считается
   живым (чужой namespace), чужой живой лизинг не трогается. Драйвер зовёт уборку перед каждым решением, поэтому
   `bin/duty run`, убитый снаружи во время попытки, лечится следующим запуском;
   `bin/duty reap [--dry-run]` делает то же вручную.
10. **Ответ человека двигает дело без ручного синка.** Драйвер перед каждым решением
    (и в `--once`) дочитывает пул (`ask.sync_answers`): закрытый вопрос становится
    фактом `question_answered`, блок `needs_input` снимается, этап получает новую
    попытку. Ошибки разбора (`errors[]`) не глотаются — они строкой `! ответы пула: …`
    в выводе и ключом `answers_errors` в `--json`.
11. **Закрытие дела — факт журнала, а не строка вывода.** «Все этапы закрыты» пишется
    одной транзакцией: `completed` с `cause='all_stages_done'` и списком этапов плюс
    строка дела (`deals.close_stages_done`), тем же путём, что `bin/duty close`. Итог
    прогона печатается **по записи**: повторный `bin/duty run` второго `completed` не
    пишет и отвечает «дело уже закрыто» с причиной и временем, а дело, которое держит
    человек (`blocked`, `review`, `archived`), движок не закрывает и говорит об этом
    прямо. Человек закрывает дело двумя командами с разными причинами:
    `bin/duty decide <дело> stop` → `cause='stopped_by_human'` (причина — текст ответа
    из пула) и `bin/duty close <дело> --reason "…"` → `cause='closed_by_human'`.

### Чем 0.0.4 **ещё не** является

- **Канбан — не источник (0.0.6).** Доск в модели данных больше нет: дело адресуется
  своим `d_<hex>`, группируется по `repo`, а журнал — единственная правда о ходе дела.
  Наблюдение за карточками kanban осталось одним отдельным роутом `/cards`, который
  читается только по вызову и не участвует ни в срезе `/now`, ни в `/stats`.
- **Переезд новых работ пока наблюдается, а не доказан.** Гейт P4 («две недели новая
  работа идёт только через дела, канбан не растёт») — пост-релизное обязательство: в
  0.0.4 сдаётся механизм (кнопка «Продолжить» в `hermes-tickets` создаёт дело, новые
  доски не заводятся), а сам гейт закрывается наблюдением после выпуска.
- **Модель внутри движка не вызывается.** `hermes chat -p <role> --query-file …
  --format stream-json --oneshot` движок **спавнит как процесс**, но ни одного
  решения на модели в самом duty нет: «что дальше» считает `transit.next_stage`,
  класс отказа — `failures.classify`, приёмку пакета — `evidence.verify`. Модель
  работает только исполнителем контракта, внутри своей попытки.
- **Дело закрывает только факт, а не «все этапы прошли» само по себе.** Движок пишет
  `completed` (`cause='all_stages_done'`) и строку дела одной транзакцией и печатает итог
  по записи (W21); но дело, которое держит человек — открытый `blocked`, `review`,
  `archived`, — движок не закрывает и говорит «все этапы закрыты, но дело не закрыто»
  с причиной. Уборка сирот (`reap`) закрывает **этап**, а не дело: дело после неё остаётся
  `running` с ожиданием `no_signal`, пока его не закроют прогоном или командой человека.
- **Нет декомпозиции.** Разбор дела на подзадачи — движок 0.1.0; это же печатает
  `bin/duty demo` в блоке «чего ещё нет». Уборка осиротевшей попытки (`reap`) в 0.0.4
  уже есть — факт `attempt_ended`, лизинг умершей попытки отпускается; дерево попытки
  уборка не трогает (`workspace: worktree` убирает сам движок при отказе попытки).
- **E2E: `impl → verify → review` пройдена живым прогоном, публикация — нет.** Живой
  прогон 04.11 (`d_6e764042`) прошёл три этапа подряд (99 с / 73 с / 135 с по журналу,
  `bin/duty attempts`) и закрылся фактом `completed cause=all_stages_done` — включая
  `review` под read-only профилем, где ревьюер написал отчёт файлом. До этого цепочка
  дважды ломалась: `d_a2a26b55` уронил `verify` (дерево этапа отводилось от базы дела, и
  второй этап не видел работу первого — правка `runner.base_of_stage` плюс коммит
  принятой работы движком), `d_221d021a` — вторая половина той же дыры (`verify` не
  объявлял `workspace` и работал в каталоге попытки, поэтому умолчанием этапа с `needs`
  стало `worktree`, `c3a5d77`). Не проверено живьём: этап публикации (в прогоне его в
  спеке не было) — публикация требует «ок» Max, и такого прогона в 0.0.4 ещё не делали.

## Цепочка 0.0.5: команда, вопрос и публикация как этапы дела

0.0.5 (в разработке) добавляет к делу три вещи, которых не было в 0.0.4: **этап-команду**
(`kind: shell`), **этап-вопрос** (`kind: gate`) и **потолок на дело целиком** (`budget` в
корне спеки). Цепочка из примера `examples/duty.yaml` читается сверху вниз — она же
фикстура: `bin/duty spec check examples/duty.yaml` проверяет ровно этот файл (в нём есть
и шестой этап `docs` с `parallel_with`, и комментарии к полям — здесь оставлены пять
шагов цепочки).

```yaml
duty: sx-widgets-tristate
repo: ~/GolandProjects/sx-widgets-api
base: origin/master

stages:
  - id: impl                              # agent: процесс профиля (умолчание вида)
    role: implementer
    workspace: worktree                   # отдельное дерево, чужое не трогаем
    evidence:
      - {cmd: "go build ./...", must: 0}
      - {cmd: "go test ./widget/...", must: 0, timeout_sec: 600}
    retry: {max: 2, on: [infra, contract]}
    budget: {tokens: 200000, minutes: 30}

  - id: verify                            # agent: проверяющий видит дерево impl
    role: tester
    needs: [impl]

  - id: review                            # agent: приговор, возврат на доработку
    role: reviewer
    needs: [verify]
    verdict: {approve: next, changes: impl, max_rounds: 2}

  - id: gate                              # gate: спрашивает человека, ничего не исполняет
    kind: gate
    needs: [review]
    ask: {q: "Публикуем этот коммит?", options: ["публиковать", "не публиковать"]}
    allow: ["публиковать"]                # ответ вне allow — отказ contract
    budget: {minutes: 120}                # срок ответа человека, а не расход дела

  - id: publish                           # agent: публикует профиль, движок проверяет
    role: publisher
    needs: [gate]
    workspace: worktree
```

| вид этапа | одним предложением |
|---|---|
| `agent` (умолчание) | движок поднимает процесс профиля `role`, попытка отчитывается `result.json`, гейт проверяет пакет — вся прежняя модель, спеки 0.0.4 без правок |
| `kind: shell` | этап-команда: движок запускает `cmd` в дереве этапа без роли и её токенов, судит по коду возврата `must` (иной код — отказ `contract` «код N, ждали M») и проверяет объявленные `artifacts`; публикующие команды (`git push`) запрещены |
| `kind: gate` | этап-вопрос: движок ничего не спавнит и лизинг не берёт, задаёт человеку вопрос `ask.q` с вариантами `ask.options` и ждёт ответа (срок — `budget.minutes`); ответ вне `allow` — отказ `contract`, истечение срока — парковка «гейт: человек не ответил за N» |
| `budget` в корне | потолок дела рядом с `repo`/`base`: расход считается по журналу (токены всех попыток и их минуты), исчерпан — попытка не поднимается, класс `capability` с числами «N/M токенов»; спека без него работает как в 0.0.4 |
| `publish-gate` | публикующий этап требует `kind: gate` с **объявленным** `allow` в предках: публикует профиль `publisher`, движок сверяет «одобрен commit X, в дереве Y» и подтверждает `published.sha` через `git ls-remote` |

Правила целиком — `docs/SPEC.md` («`kind`: `agent`, `shell` и `gate`», «`budget` в корне»,
«Гейт „публикация спрашивает человека“»), факты журнала — `docs/JOURNAL.md`.

**«Продолжить» в `hermes-tickets`.** Кнопка работает в режиме `deal` по умолчанию: заводит
дело по `duty.yaml` из корня рабочей ветки тикета (нет спеки или она не прошла
`spec check` — отказ с подсказкой, дело не заводится). Прежнее поведение 0.0.4
(lead-карточка канбана) осталось явным откатом — `continue_mode: card` в `settings.json`
плагина тикетов.

## Что уже работает (роуты и экраны)

Роуты (монтируются под `/api/plugins/hermes-duty`; чужие источники открываются только
на чтение, пишет плагин только в свою БД `duty/duty.db` — журнал событий и store своих
дел, по требованию и по явной мутации — и в пул `messaging/pool.db` единственным
каналом вопросов `ask()`):

| роут | что отдаёт | ошибки |
|---|---|---|
| `GET /health` | версия, корень Hermes, наличие store и пула, `journal: {events, deals}`, `mode` | — (`note` — причина, если журнал не открылся) |
| `GET /sources` | store дел, репозитории дел (`repos`: `list`/`without_repo`/`read`), пул по `origin × status`, список профилей, отдельной строкой — наблюдение за карточками kanban (`cards`) | — |
| `GET /cards` | наблюдение за карточками kanban: статусы, лизинг, последний ран, по базам (`databases`, `count`, `cards[]`). Это **не дела**: в `/now`, `/stats` и адресацию по id карточки не попадают | — |

Мутации своих дел отвечают той же формой, что `GET /deal` (дело + факты + таймлайн),
плюс блок `mutation: {events, idempotent}`: повтор того же вызова не плодит событий
(`events: 0`, `idempotent: true`), а «делать нечего» — это ошибка входа с причиной.
Контракт владения — `docs/OWNERSHIP.md`, правила журнала — `docs/JOURNAL.md`.

**Одно пространство id.** Дело — это только `d_<hex>`: своей карточки на доске у него
больше нет (0.0.6), поэтому и различать нечего. Карточки kanban (`t_<hex>`) делом не
бывают вовсе: их видно отдельным наблюдением `/cards`, и ни `/now`, ни `/stats`, ни
адресация по id в это наблюдение не ходят. Дела попадают в срез `/now` и в счётчики
репозиториев (`repos.list`, `repos.without_repo`) по своему `repo`, поэтому «сколько
дел» одно, а не два.

`waiting` в `/now` и `/deal` считается **fold'ом по своему журналу** (контракт
`docs/JOURNAL.md`): дело без событий получает `waiting.evidence` с прямым «событий
нет». `waiting.human_kind` отличает `question` (есть живой вопрос, на
него можно ответить) от `status` (человек нужен, вопроса нет). В шапке «Сейчас»
это двумя числами — `N вопросов + M блокировок`; вопрос задаётся явно,
`POST /ask/{deal_id}`, и он же единственное место, где плагин пишет в пул.

Экраны (детальная форма ответа и правила таксономии — `docs/DESIGN.md`):

Пять экранов, одни и те же в двух поверхностях — десктопе и браузере:

| экран | что показывает | откуда данные |
|---|---|---|
| **Сейчас** | таблица активных дел группами по `repo` («без репозитория» — отдельной группой и последней), фильтры (репозиторий, чипы состояний, поиск по `id`/заголовку/исполнителю/репозиторию), автообновление 10 с, подпись «обновлено N с назад» | `GET /now` |
| **Завершённые** | закрытые дела (`done`/`archived`) группами по `repo`, свежие сверху: `закрыто · дело · заголовок · статус · попыток · вопросов · длительность · причина · этапы · публикация`; по клику — в «Дело». Пусто — словами бэкенда | `GET /deals` |
| **Дело** | документы (описание и спецификация) слева и **один тонкий столбец этапов** (320 px) справа: строка этапа — имя, вид, число попыток, состояние словами; внутри этапа — строки попыток (номер, длительность, исход словами), раскрытые показывают доказательства (`exit N`, обрезанная команда с полной в подсказке, время), сводку и ошибку, а журнал — сводкой по видам; провал и живая попытка раскрыты без клика, провал отмечен и в графе; ожидание вопроса — видимой строкой со ссылкой на `/imsg`. Факты дела (попытка, лизинг, последнее действие, ожидание) — в шапке; таб открывает последнее дело, а без выбора — список активных. Адрес — `#/deal/<deal_id>`; прежний `#/deal/<board>/<id>` даёт экран-отказ | `GET /deal/{deal_id}` (`stages[]`) + `GET /duty/{deal_id}/attempts` |
| **Почему стоит** | карточки дел с доказательством словами бэкенда, группами по `waiting.state` — чтобы причину можно было проверить, а не поверить | `GET /now` (`waiting.evidence`) |
| **Здоровье** | дела с первой попытки, ожидание до неё распределением (p50/p90/p99, максимум, размер выборки), таксономия исходов, таблица по репозиториям с отдельной строкой «без репозитория» | `GET /stats` |

Где открыть:

- десктоп — пункт сайдбара **«Дела»** (роут приложения `/duty`, это не HTTP-путь);
- браузер — `http://127.0.0.1:18742/web/hermes-duty/` напрямую или
  `http://127.0.0.1:8360/duty` через Hub (прокси-роут `~/.hermes/dashboard/serve.py`);
  на главной Hub (`:8360`) есть карточка **«Дела»**: счётчики «сейчас / ждут
  ответа / репозиториев», первые пять дел со состоянием и доказательством в тултипе,
  ссылка в дело через `#/deal/<deal_id>`.

Веб-страница и десктоп делят один шейпер: веб импортирует `./model.js`, который
бэкенд отдаёт по `/web/hermes-duty/model.js` из `desktop/model.js`. Второй копии
таксономии, подписей и формулировок доказательств нет — иначе две поверхности
разъезжались бы молча. Экран «Дело» показывает шкалу времени дела — общая ось,
дорожка на этап и маркеры событий журнала (`shapeDealTime` в том же шейпере).

Недоступный store и упавшие источники видны в ответе (`repos.read`, `errors[]`)
и на экранах — жёлтой полосой и списком в пустом состоянии.

## CLI `bin/duty`

Тот же бэкенд, что у роутов, но из терминала: команды вызывают те же функции
(`dashboard/plugin_api.py`), а не ходят в HTTP и не пересчитывают состояния. `--json`
печатает ответ роута дословно — второй формы у CLI нет, поэтому «терминал сказал одно,
экран другое» невозможно по построению.

```bash
~/.hermes/plugins/hermes-duty/bin/duty now
# в профильной оболочке (HERMES_HOME=~/.hermes/profiles/<role>) журнала дел там нет — корень задаётся явно:
HERMES_HOME=~/.hermes ~/.hermes/plugins/hermes-duty/bin/duty now
# группировка — по репозиторию; пустая строка в --repo — это дела БЕЗ репозитория:
~/.hermes/plugins/hermes-duty/bin/duty now --repo '' --state wait_human
```

| команда | что делает |
|---|---|
| `duty now [--repo R] [--state S]` | таблица активных дел группами по репозиторию: `repo`, `id`, состояние (у `wait_human` — с `/human_kind`), ожидание, возраст, доказательство. `--repo <путь>` — один репозиторий, `--repo ''` — только дела без репозитория («без репозитория» — отдельной группой и последней) |
| `duty deal <deal_id>` | карточка дела (`d_<hex>`): те же факты плюс таймлайн попыток |
| `duty attempts <deal_id> [--json]` | только таймлайн попыток: этап · номер · исход (длительность) · причина, `base`/`commit` коротким sha, pid, число событий прогресса. `--json` — та же форма, что у роута `/duty/{deal_id}/attempts` |
| `duty stats [--repo R] [--since D]` | p50/p90/p99 ожидания, исходы попыток, доля этапов с первой попытки, таблица по репозиториям; `--repo <путь>` — один репозиторий, `--repo ''` — только без репозитория; `--since` — unix, `YYYY-MM-DD` или `YYYY-MM-DDTHH:MM` |
| `duty deals [--status done,archived] [--repo R] [--limit N]` | завершённые дела группами по репозиторию, свежие сверху: `закрыто`, `статус`, `id`, заголовок, попыток, вопросов, длительность, причина закрытия, пройденные этапы, публикация. Числа — те же, что у `duty deal <deal_id>`; `--limit` по умолчанию 50, не больше 500 |
| `duty why <deal_id>` | доказательство `waiting.evidence` словами бэкенда плюс факты, из которых оно собрано |
| `duty why <deal_id> <этап>` | то же плюс приговор последней попытки этапа: исход, класс отказа, первые `details` evidence-гейта |
| `duty run <deal_id> [--spec <duty.yaml>] [--max-steps N] [--json] [--once]` | довести своё дело: цикл «решение → шаг → перечитать журнал»; `--once` — один шаг, предел `--max-steps` (по умолчанию 20, дело при этом не меняется). Коды свои: `0` закрыто, `1` остановлено отказом, `2` припарковано, `3` ждёт (вопрос/`retry_at`/чужой лизинг/гейт — выход, а не петля), `4` предел шагов, `130` SIGINT |
| `duty spec check <file> [--json]` | спека дела **до запуска**: `OK` либо `file:line: правило: текст`; правила — `docs/SPEC.md`, ни одного процесса (кроме `git rev-parse` для `base`). Коды: `0` годна, `1` есть отказы, `2` спека не читается |
| `duty reap [--dry-run]` | закрыть осиротевшие попытки **своего** store: `attempt_started` без `attempt_ended`, лизинг истёк и возраст попытки больше `ttl + max(60 с, ttl/3)` → `attempt_ended` с `kind=infra` и `reaped: true`, лизинг умершей попытки отпускается. `--dry-run` показывает, что было бы закрыто, ничего не записывая. **Мёртвый pid закрывает попытку и при живом лизинге** (`os.kill(pid, 0)`, только своё дело, не раньше минуты жизни попытки; `PermissionError` — жив); чужой живой лизинг не трогается. Код `0` — «посчитано» (в том числе «убирать нечего») |
| `duty demo [--home DIR] [--keep]` | прогон одного дела по спеке на **песочном корне** (временный каталог): create → claim → ask → answer → gate → comment/attach → ingest → complete → late answer. Сам проверяет 7 инвариантов (вопрос уводит в `wait_human`, ответ возвращает в работу, гейт открывается завершением родителя, закрытое дело уходит из `/now`, поздний ответ не воскрешает, повторный ingest не плодит, `kanban.db` не изменился) и печатает границу «чего ещё нет до движка 0.1.0». Живые БД только читаются; `--keep` оставляет песочницу для разбора |

| `duty create --title "…" [--repo R] [--body-file F] [--assignee ROLE] [--spec duty.yaml] [--external-ref jira:RP-14080] [--parent d_…]…` | завести своё дело; `--repo` — репозиторий группировки (по умолчанию `repo` из спеки, иначе «без репозитория»); `--spec` — граф дела (путь разворачивается в абсолютный, иначе лента этапов молчит с названной причиной); `--external-ref` — внешнее имя: живое дело с этим именем не дублируется (ответ `created: false`/`existing: true`), закрытое не воскрешается; `--json` отдаёт `deal_id`, `created` и `status` для следующих команд |
| `duty comment d_… "текст" [--author …]` | комментарий в своё дело (`--author`, по умолчанию `max`) |
| `duty block d_… [причина] [--kind needs_input]` | заблокировать своё дело |
| `duty unblock d_…` | снять блокировку |
| `duty decide d_… continue` | решение человека по запаркованному делу: `unblocked` со `previous_kind='parked'`, счётчики класса сброшены; ответ в пуле решением не является |
| `duty decide d_… stop` | закрыть запаркованное дело решением человека: `completed` с `cause='stopped_by_human'`, причиной — текст ответа из пула (нет ответа — причина пустая, а не выдуманная) |
| `duty close d_… --reason "…"` | закрыть дело не решением, а по обстоятельствам: `completed` с `cause='closed_by_human'`; перезакрыть другой причиной нельзя |
| `duty claim d_… [--owner …]` | взять в работу (владелец — `--owner`, иначе `HERMES_PROFILE`, иначе пользователь ОС) |
| `duty complete d_… [--summary …] [--review] [--reviewer …]` | закрыть дело или сдать в ревью |
| `duty review d_… [--reviewer …] [--summary …]` | сдать в ревью |
| `duty changes d_… "причина" [--reviewer …]` | вернуть на доработку |
| `duty attach d_… FILE` | приложить файл (копия в `duty/attachments/<deal_id>/`) |
| `duty archive d_…` | `PATCH {status: archived}` — архив назван командой |

`duty demo` — не роут, а прогон модели труда: одна команда проходит дело от создания
до закрытия на песочном корне (временный каталог; из `~/.hermes` берётся только DDL схем,
данные не читаются), проверяет семь инвариантов учёта и печатает отчёт — шаги, журнал
дела, пул вопросов, проверки и блок «чего ещё нет». Спека-образец — `examples/demo.yaml`
(тот же текст печатается в отчёте): этапы и evidence-команды в нём есть, но `demo`
исполняет **учёт**, а не движок: файл остался от 0.0.3 и формату 0.0.4 не отвечает
(`bin/duty spec check examples/demo.yaml` даёт отказ на `questions` и на
`verdict.approve: done`). Спеку для `bin/duty run` пишут по `examples/duty-minimal.yaml`
или по `examples/duty.yaml` — оба `spec check` проходит. Тесты прогона —
`tests/test_demo.py` (9 кейсов).

Коды возврата: `0` — ответ получен целиком и `errors[]` пуст; `1` — дела нет
(404 роута); `2` — источники не прочитались (503/400 роута или непустой `errors[]`)
либо неверный вход мутации. `--json` работает и до команды, и после неё. У `duty run`
коды свои (`0/1/2/3/4/130`) — они перечислены в таблице выше и в `docs/RUNBOOK.md`:
`3` и `4` там означают «ждём» и «упёрлись в предел», а не ошибку входа.

Интерпретатор: `dashboard/plugin_api.py` импортирует `fastapi`, которого в системном
`python3` нет, поэтому `bin/duty` перезапускает себя интерпретатором агента
(`~/.hermes/hermes-agent/venv/bin/python3`, `~/.hermes/bvenv/bin/python3`). Свой путь —
`DUTY_PYTHON=/path/to/python`.

## Принципы P0

1. **Только чтение чужого.** Чужие источники открываются в режиме `?mode=ro`; плагин
   не пишет ни в `kanban.db`, ни в `state.db` (инвариант проверяется тестом по `mtime`).
   Что он пишет — только своё: БД `duty/duty.db` (журнал событий и store своих дел —
   по явным мутациям `/deals…`) и пул
   вопросов `messaging/pool.db` — и пул только через `ask()` (`dashboard/ask.py`), по
   явному `POST /ask/{deal_id}`.
2. **Источники не смешиваются с истиной.** Консоль не пересчитывает статусы карточек
   и не пытается «угадать» состояние — она показывает лизинг, процесс и последнее
   действие, как они записаны в источниках.
3. **Честная таксономия.** `wait_human`, `capability`, `dead_lease`, `crashed`,
   `working`, `no_signal`, `wait_slot`, `wait_gate` — восемь взаимоисключающих
   состояний по приоритету, а не «blocked»; каждый факт показывается
   доказательством, а дело без живого сигнала не выдаётся за работающее.
4. **Деградация вместо 500.** Нечитаемый store или пул вопросов попадают в
   `errors[]` при HTTP 200, а не превращаются в падение роута.
5. **Ничего не автозапускается.** Все процессы — внутри существующего жизненного
   цикла Hermes (бэкенд dashboard) и только по явной команде человека
   (`bin/duty run`), никаких новых launchd-джоб и своих планировщиков: движок не
   крутится в фоне и не поднимает попытку сам.

## Установка

Плагин ставится как обычный пользовательский плагин из каталога:

```bash
hermes plugins enable hermes-duty     # или Capabilities → Plugins в десктопе
```

Данные — вне плагина (`~/.hermes/`), при переустановке не теряются.

## Проверка

Из каталога плагина (`cd ~/.hermes/plugins/hermes-duty`):

```bash
~/.hermes/hermes-agent/venv/bin/python -m pytest tests/ -q  # 931 passed, 1 skipped
node --test tests/*.test.mjs                              # 177 pass (модель, поверхности, шейпер)
bin/duty-model-sync --check                                # OK
bin/duty-version check                                     # OK
HERMES_HOME=~/.hermes bin/duty now                         # таблица дел, код 0
HERMES_HOME=~/.hermes bin/duty demo                        # 7 проверок OK, код 0
HERMES_HOME=~/.hermes bin/duty spec check examples/duty.yaml  # OK, код 0
```

Живой рендер смотрится в приложении (после включения плагина) и в браузере —
`http://127.0.0.1:8360/duty`. Пошаговая проверка руками (включая «страница
пустая» и «store не прочитан») — `docs/RUNBOOK.md`.

Десктопная половина грузится как **ES-модуль**: загрузчик берёт `desktop/plugin.js`,
подменяет импорты и делает `import(blob)`. Поэтому файл нельзя проверять как
CommonJS — `node --check plugin.js` пропускает то, что валит парсер модуля (так в 0.0.3
плагин на день выпал из приложения из-за висячей запятой). Синтаксис проверяет
`tests/test_frontend_syntax.py`: он копирует `desktop/plugin.js` и
`dashboard/web/app.js` в `.mjs` и разбирает их парсером модуля.

## Статус

`v0.1.0` (в разработке) — **лид ведёт дело целиком**: начинает его планом, добавляет
и переставляет этапы, отвечает на вопросы этапов или переадресует их человеку и
закрывает дело по итогам ревью и проверок. Это тот шаг, который `docs/ENGINE-1.0.md`
называл «дело перестаёт быть спекой, написанной до начала».

`v0.0.9` (опубликована 09.11.2026) — **план дела растёт из журнала, и работа дела больше не
теряется**. В спеке появился блок `charter` (потолок графа, раунды реплана,
разрешённые роли и виды, порог вопроса человеку) с дефолтами, равными поведению
0.0.8; предложение плана (`plan_proposed`) не меняет граф — меняет только
`plan_accepted`, а валидируется оно тем же `spec.parse_plan`, что и `duty spec
check`. Живая проба: в файле спеки один этап, исполнено три. По дороге закрыты три
дефекта, каждый найденный живым делом и каждый стоивший работы: дерево упавшей
попытки больше не удаляется (раньше оно удалялось ровно тогда, когда коммита ещё не
было, — падение на 55-й минуте унесло 1300 строк), метка перезапуска CLI переехала
из окружения в argv (этап `check` падал кодом 2 не на своих командах), и коммиты
дела закрепляются веткой `duty/<deal_id>` (два коммита на 1576 строк висели без
ссылки — их пришлось закреплять руками, иначе первый `git gc` забрал бы работу).

`v0.0.8` (опубликована 09.11.2026) — **страница дела, которую видно**: она обновляется
сама (5 с на идущем деле, 30 с на закрытом, правкой узлов на месте — прокрутка, фокус и
раскрытые попытки переживают тик), долгий простой на шкале сжимается до 3 % ширины
(порог — 10 минут и 5 % оси), провал попытки читается на дорожке, а граф спеки красит
узел красным только по последней попытке с живой пульсацией идущего этапа. Дело больше
не висит `running`, когда движка уже нет: `dashboard/release.py` спрашивает журнал у
строки `running` без живого сигнала и материализует посчитанный ответ. Подсказки ушли в
свой слой в `body` (внутри дорожки их резал `overflow` панели), маркеры вывода стоят
перед своим моментом.

`v0.0.7` (опубликована) — **здоровье про дела, а не про карточки, и видимый конец работы**:
`/stats` и `bin/duty stats` больше не отдают блок карточек kanban (наблюдение осталось
одним роутом `GET /cards`), а завершённые дела появились списком — `GET /deals`,
`bin/duty deals` и пятый экран «Завершённые» в вебе и десктопе. Строка списка называет
записанный факт закрытия (`finished_at`, `cause`, `stages`) и числа журнала (`attempts`,
`questions`, `duration_sec`, `published`), посчитанные теми же функциями, что у карточки
дела, — поэтому список и `bin/duty deal <id>` об одном деле не спорят.

`v0.0.6` (опубликована) — **без досок**: дело адресуется только своим `d_<hex>`
(`/deal/{deal_id}`, `/duty/{deal_id}/attempts`, `POST /ask/{deal_id}`), группировка
списка и статистики — по `repo` («без репозитория» — отдельная группа и последняя на
всех поверхностях: CLI, веб, десктоп), `?board=`/`--board` — отказ с подсказкой про
`repo`, колонки `board` в журнале и в store больше нет (`LEGACY_BOARD_FIELD` в
`dashboard/journal.py` помнит её только как исторический факт в payload старых
событий), ingest из kanban удалён вместе с досками — карточки kanban видны отдельным
наблюдением `/cards`, которое не участвует ни в срезе, ни в статистике, ни в
адресации. Веб-адрес дела — `#/deal/<deal_id>`; прежний `#/deal/<board>/<id>` даёт
экран-отказ.

`v0.0.4` — **движок**: спека дела с валидатором (`dashboard/spec.py`,
`bin/duty spec check`), переход `transit.next_stage` (пять исходов, никакой модели),
исполнитель `runner.step` (лизинг, дерево попытки от коммита предшественника, контракт
файлом с `report_to`, спавн `hermes chat -p`, телеметрия `attempt_progress`),
evidence-гейт `evidence.verify`, адресация вопросов `routing.route`, классы отказа и
политика ретраев `failures.py` (исчерпание паркует дело), лента этапов `stagefeed.py`,
`external_ref` у дела, драйвер `dashboard/driver.py` (`bin/duty run`), дочитывание
ответов пула самим движком (`ask.sync_answers` на каждом шаге), уборка осиротевших
попыток `reaper.sweep` (`bin/duty reap`, `reaped: true`), база этапа
`runner.base_of_stage` (дерево от коммита предшественника, автокоммит принятой работы),
решение человека по делу (`bin/duty decide continue|stop`, `bin/duty close`) и закрытие
дела фактом журнала (`deals.close_stages_done`, `cause='all_stages_done'`). Регрессия
**767 pytest + 1 skipped**, **49 node** (37 + 12), `bin/duty demo` — 7/7.

`v0.0.3` — свой журнал событий (`state = fold(events)`, `journal` в
`/health`), единственный канал вопросов `ask()`, CLI `bin/duty` (чтение и мутации),
**владение делом** (свой store, мутации `/deals…`, id `d_<hex>`, контракт
`docs/OWNERSHIP.md`) и перцентили ожидания p50/p90/p99 в `/stats`. Регрессия
220 pytest + 37 node.

`v0.0.2` — четыре экрана (`Сейчас`, `Дело`, `Почему стоит`, `Здоровье`) в десктопе и
в браузере поверх роутов `/now`, `/deal/{deal_id}`, `/duty/{deal_id}/attempts`,
`/stats`; регрессия 42 pytest + 30 node.

`v0.0.1` (опубликована) — P0 в объёме «смотреть»: каркас плагина (манифесты),
backend на read-only источниках, агрегатор `/now` с таксономией ожиданий,
таймлайн попыток, desktop-страница `/duty`.

Дальше (не сделано): декомпозиция дела на подзадачи, затем фаза P5 — канбан в
архив. План по версиям — `docs/DESIGN.md`, раздел «Дальше».

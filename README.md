# Hermes Duty — desktop-плагин «Дела» (P0: наблюдаемость)

Плагин к Hermes Desktop: **дело** (duty) вместо карточки, **этап** вместо подзадачи,
**попытка** вместо рана. P0 — только чтение: собирает лизинги и события из живых
источников, показывает, кто что держит и что делает прямо сейчас. Ни одного файла
ядра Hermes, ни одного патча, ни одной записи в существующие БД.

## Зачем

Kanban-ядро смешивает три ответственности (хранилище карточек, планировщик со
spawn-RPC, политику workflow). Каждый новый баг лечится новой колонкой или новым
условием записи статуса, а наблюдаемость выводится из тех же изменяемых колонок и
врёт ровно тогда, когда сломано.

Duty выводит состояние из журнала (`state = fold(events)`), а не из колонок. Этим
плагином мы начинаем с самой дешёвой части: **смотреть, ни на что не влияя**.

Дизайн целиком (7 вкладок: диагноз, модель, этап изнутри, вопросы и адресация,
наблюдаемость, варианты, фазы) — `~/.hermes/widgets/duty-model.html`,
доктрина — скилл `agent-orchestration-design` (`references/duty-model.md`).

## Что уже работает (`v0.0.1`)

Роуты (все только чтение, монтируются под `/api/plugins/hermes-duty`):

| роут | что отдаёт | ошибки |
|---|---|---|
| `GET /health` | версия, корень Hermes, число БД и читаемых, строки `tasks`, наличие пула, `mode: "read-only"` | — |
| `GET /sources` | доски с размером и счётчиками, пул по `origin × status`, список профилей | — |
| `GET /board/{slug}/tasks` | сырой срез активных карточек доски (до 200) | 404 — доски нет |
| `GET /now?board=<slug>&state=<waiting.state>` | срез «сейчас»: лизинг, попытка, последнее действие, таксономия ожидания | 404 — доски нет; 400 — состояние не из таксономии |
| `GET /duty/{board}/{task_id}/attempts` | таймлайн попыток дела: раны, длительность, исход, ошибка, события | 404 — нет доски/дела; 503 — доска не читается |

Экраны (детальная форма ответа и правила таксономии — `docs/DESIGN.md`):

- страница **`/duty`** в десктопе (пункт сайдбара «Дела»): таблица активных дел
  группами по `waiting.state`, локальные фильтры (доска, чипы состояний, поиск по
  `id`/заголовку), правая панель с таймлайном попыток, автообновление `/now` раз в
  10 с с подписью «обновлено N с назад» и плашкой «повторить» при ошибке;
- недоступные доски и упавшие источники видны в ответе (`boards[].read`,
  `errors[]`) и на странице — жёлтой полосой и списком в пустом состоянии.

Экранов «Почему стоит» и «Здоровье» отдельными страницами нет: данные для них
(`by_state`, `waiting.evidence`) уже приходят в `/now`, группировка по состояниям
есть на `/duty`. Это план, а не сделанное.

## Структура

```
~/.hermes/plugins/hermes-duty/
  plugin.yaml            # метаданные пакета (manifest v2), номер версии
  __init__.py            # вход агентной половины (register(ctx)); P0 — no-op, __version__
  dashboard/
    manifest.json        # манифест dashboard-половины (api: plugin_api.py)
    plugin_api.py        # backend-роутер (FastAPI), только чтение
  desktop/
    plugin.js            # страница /duty + пункт сайдбара «Дела»
    model.js             # шейпер ответов /now и /attempts (чистые функции)
  bin/duty-version       # версия: check / bump / finalize
  bin/duty-model-sync    # вшить model.js в plugin.js (загрузчик не резолвит ./)
  docs/DESIGN.md         # контракт P0: источники, роуты, таксономия, деградация
  docs/VERSIONING.md     # контракт версий и ритуал bin/duty-version
  docs/RUNBOOK.md        # как проверить плагин руками
  tests/                 # pytest (агрегатор, контракт роутов) + node --test (шейпер)
```

## Принципы P0

1. **Только чтение.** Источники открываются в режиме `?mode=ro`; плагин не пишет ни
   в `kanban.db`, ни в `state.db`, ни в `pool.db`.
2. **Источники не смешиваются с истиной.** Консоль не пересчитывает статусы карточек
   и не пытается «угадать» состояние — она показывает лизинг, процесс и последнее
   действие, как они записаны в источниках.
3. **Честная таксономия.** `wait_human`, `capability`, `dead_lease`, `crashed`,
   `working`, `no_signal`, `wait_slot`, `wait_gate` — восемь взаимоисключающих
   состояний по приоритету, а не «blocked»; каждый факт показывается
   доказательством, а дело без живого сигнала не выдаётся за работающее.
4. **Деградация вместо 500.** Недоступная доска или пул вопросов попадают в
   `errors[]` при HTTP 200, а не превращаются в падение роута.
5. **Ничего не автозапускается.** Все процессы — внутри существующего жизненного
   цикла Hermes (бэкенд dashboard), никаких новых launchd-джоб.

## Установка

Плагин ставится как обычный пользовательский плагин из каталога:

```bash
hermes plugins enable hermes-duty     # или Capabilities → Plugins в десктопе
```

Данные — вне плагина (`~/.hermes/`), при переустановке не теряются.

## Проверка

Из каталога плагина (`cd ~/.hermes/plugins/hermes-duty`):

```bash
~/.hermes/bvenv/bin/python -m pytest -q     # 30 passed
node --test tests/model.test.mjs            # 23 pass
bin/duty-version check                      # OK
```

Живой рендер страницы смотрится в приложении после включения плагина; пошаговая
проверка руками (включая «страница пустая») — `docs/RUNBOOK.md`.

## Статус

`v0.0.1` — P0 в объёме «смотреть»: каркас плагина (манифесты), backend с
`/health`, `/sources`, `/board/{slug}/tasks` на read-only источниках, агрегатор
`GET /now` с таксономией ожиданий и фильтрами, таймлайн попыток
`GET /duty/{board}/{id}/attempts`, desktop-страница `/duty` поверх них, регрессия
(30 pytest + 23 node) и документация.

Дальше (не сделано): экраны «Почему стоит» и «Здоровье», CLI `bin/duty`, затем
P1 — собственный журнал плагина вместо чтения kanban. План по версиям —
`docs/DESIGN.md`, раздел «Дальше».

# Hermes Duty — desktop-плагин «Дела» (P0: наблюдаемость)

Плагин к Hermes Desktop: **дело** (duty) вместо карточки, **этап** вместо подзадачи,
**попытка** вместо рана. P0 — только чтение: собирает лизинги и события из живых
источников, показывает, кто что держит и что делает прямо сейчас. Ни одного файла
ядра Hermes, ни одного патча, ни одной записи в существующие БД.

## Зачем

Kanban-ядро смешивает три ответственности (хранилище карточек, планировщик со
spawn-RPC, политику workflow). Каждый новый баг лечится новой колонкой или новым
условием записи статуса, а наблюдаемость выводится из тех же изменяемых колонок и
врёт ровно тогда, когда сломано.

Duty выводит состояние из журнала (`state = fold(events)`), а не из колонок. Этим
плагином мы начинаем с самой дешёвой части: **смотреть, ни на что не влияя**.

Дизайн целиком (7 вкладок: диагноз, модель, этап изнутри, вопросы и адресация,
наблюдаемость, варианты, фазы) — `~/.hermes/widgets/duty-model.html`,
доктрина — скилл `agent-orchestration-design` (`references/duty-model.md`).

## Что уже работает (`v0.0.3`)

Роуты (монтируются под `/api/plugins/hermes-duty`; источники открываются только на
чтение, пишет плагин только в свой журнал `duty/duty.db` — и только по требованию):

| роут | что отдаёт | ошибки |
|---|---|---|
| `GET /health` | версия, корень Hermes, число БД и читаемых, строки `tasks`, наличие пула, `journal: {events, deals, drift: {empty_journal}}`, `mode` | — |
| `GET /sources` | доски с размером и счётчиками, пул по `origin × status`, список профилей | — |
| `GET /board/{slug}/tasks` | сырой срез активных карточек доски (до 200) | 404 — доски нет |
| `GET /now?board=<slug>&state=<waiting.state>&ingest=1` | срез «сейчас»: лизинг, попытка, последнее действие, таксономия ожидания; `?ingest=1` — сначала прогнать ingest в свой журнал | 404 — доски нет; 400 — состояние не из таксономии |
| `POST /ingest` | проход ingest: дописать в свой журнал недостающие события (`appended`, `events`, `deals`, отчёт по доскам, `errors[]`); повторный вызов — `appended: 0` | 503 — журнал не открылся |
| `GET /duty/{board}/{task_id}/attempts` | таймлайн попыток дела: раны, длительность, исход, ошибка, события | 404 — нет доски/дела; 503 — доска не читается |
| `GET /deal/{board}/{task_id}` | одно дело: элемент `/now` (если оно активно), `body` спецификации, `terminal` | 404 — нет доски/дела; 503 — доска не читается |
| `GET /stats` | здоровье: доля с первой попытки, распределение ожидания до неё (`waiting_sec`: p50/p90/p99, `count`, `max`), таксономия исходов по доскам и итогом | — (деградация в `errors[]`, неполная выборка — в `warnings[]`) |

`waiting` в `/now` и `/deal` считается **fold'ом по своему журналу** (контракт
`docs/JOURNAL.md`): дело без событий считается по kanban, и `waiting.evidence`
начинается с `journal: empty — состояние из kanban`. `journal.drift.empty_journal`
в `/health` — сколько активных дел журнал ещё не подобрал; `POST /ingest` доводит
это число до нуля, `waiting.human_kind` отличает `question` (ждёт ответа) от
`status` (ждёт решения по статусу).

Экраны (детальная форма ответа и правила таксономии — `docs/DESIGN.md`):

Четыре экрана, одни и те же в двух поверхностях — десктопе и браузере:

| экран | что показывает | откуда данные |
|---|---|---|
| **Сейчас** | таблица активных дел группами по `waiting.state`, фильтры (доска, чипы состояний, поиск по `id`/заголовку/исполнителю), автообновление 10 с, подпись «обновлено N с назад» | `GET /now` |
| **Дело** | спецификация карточки, факты (попытка, лизинг, последнее действие, ожидание) и таймлайн попыток рядом; таб открывает последнее дело, а без выбора — список активных | `GET /deal/{board}/{id}` + `GET /duty/{board}/{id}/attempts` |
| **Почему стоит** | карточки дел с доказательством словами бэкенда — чтобы причину можно было проверить, а не поверить | `GET /now` (`waiting.evidence`) |
| **Здоровье** | дела с первой попытки, ожидание до неё распределением (p50/p90/p99, максимум, размер выборки), таксономия исходов, срез по доскам | `GET /stats` |

Где открыть:

- десктоп — пункт сайдбара **«Дела»** (роут приложения `/duty`, это не HTTP-путь);
- браузер — `http://127.0.0.1:18742/web/hermes-duty/` напрямую или
  `http://127.0.0.1:8360/duty` через Hub (прокси-роут `dashboard/serve.py`);
  на главной Hub (`:8360`) есть карточка **«Дела»**: счётчики «сейчас / ждут
  ответа / досок», первые пять дел со состоянием и доказательством в тултипе,
  ссылка в дело через `#/deal/<board>/<id>`.

Веб-страница и десктоп делят один шейпер: веб импортирует `./model.js`, который
бэкенд отдаёт по `/web/hermes-duty/model.js` из `desktop/model.js`. Второй копии
таксономии, подписей и формулировок доказательств нет — иначе две поверхности
разъезжались бы молча.

Недоступные доски и упавшие источники видны в ответе (`boards[].read`, `errors[]`)
и на экранах — жёлтой полосой и списком в пустом состоянии.

## Структура

```
~/.hermes/plugins/hermes-duty/
  plugin.yaml            # метаданные пакета (manifest v2), номер версии
  __init__.py            # вход агентной половины (register(ctx)); P0 — no-op, __version__
  dashboard/
    manifest.json        # манифест dashboard-половины (api: plugin_api.py)
    plugin_api.py        # backend-роутер (FastAPI): роуты и kanban-факты
    journal.py           # свой журнал событий, fold и ingest (docs/JOURNAL.md)
  desktop/
    plugin.js            # четыре экрана (/duty) + пункт сайдбара «Дела»
    model.js             # шейпер ответов /now, /deal и /attempts (чистые функции)
  dashboard/web/
    index.html           # веб-версия тех же экранов (не-/api путь /web/hermes-duty/)
    app.js               # SPA: #/now, #/why, #/health, #/deal/<board>/<id>
    styles.css           # авто-тема (prefers-color-scheme), как у hermes-tickets
  bin/duty-version       # версия: check / bump / finalize
  bin/duty-model-sync    # вшить model.js в plugin.js (загрузчик не резолвит ./)
  docs/DESIGN.md         # контракт P0: источники, роуты, таксономия, деградация
  docs/VERSIONING.md     # контракт версий и ритуал bin/duty-version
  docs/RUNBOOK.md        # как проверить плагин руками
  tests/                 # pytest (агрегатор, контракт роутов) + node --test (шейпер)
```

## Принципы P0

1. **Только чтение чужого.** Источники открываются в режиме `?mode=ro`; плагин не
   пишет ни в `kanban.db`, ни в `state.db`, ни в `pool.db`. Единственный файл,
   который он пишет, — свой журнал `duty/duty.db`, и только по явному
   `POST /ingest` (или `GET /now?ingest=1`).
2. **Источники не смешиваются с истиной.** Консоль не пересчитывает статусы карточек
   и не пытается «угадать» состояние — она показывает лизинг, процесс и последнее
   действие, как они записаны в источниках.
3. **Честная таксономия.** `wait_human`, `capability`, `dead_lease`, `crashed`,
   `working`, `no_signal`, `wait_slot`, `wait_gate` — восемь взаимоисключающих
   состояний по приоритету, а не «blocked»; каждый факт показывается
   доказательством, а дело без живого сигнала не выдаётся за работающее.
4. **Деградация вместо 500.** Недоступная доска или пул вопросов попадают в
   `errors[]` при HTTP 200, а не превращаются в падение роута.
5. **Ничего не автозапускается.** Все процессы — внутри существующего жизненного
   цикла Hermes (бэкенд dashboard), никаких новых launchd-джоб.

## Установка

Плагин ставится как обычный пользовательский плагин из каталога:

```bash
hermes plugins enable hermes-duty     # или Capabilities → Plugins в десктопе
```

Данные — вне плагина (`~/.hermes/`), при переустановке не теряются.

## Проверка

Из каталога плагина (`cd ~/.hermes/plugins/hermes-duty`):

```bash
~/.hermes/hermes-agent/venv/bin/python -m pytest -q        # 42 passed
node --test tests/model.test.mjs tests/web.test.mjs        # 30 pass
bin/duty-model-sync --check                                # OK
bin/duty-version check                                     # OK
```

Живой рендер смотрится в приложении (после включения плагина) и в браузере —
`http://127.0.0.1:8360/duty`. Пошаговая проверка руками (включая «страница
пустая» и «доска недоступна») — `docs/RUNBOOK.md`.

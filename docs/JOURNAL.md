# Журнал дел: контракт 0.0.3

Спека W1. Пока этот документ не сойдётся с кодом, `docs/DESIGN.md` остаётся контрактом
поверхности (роуты, таксономия, форма ответов), а журнал живёт здесь.

## Зачем

До 0.0.2 состояние дела **выводилось из изменяемых колонок** kanban (`status`,
`claim_lock`, `claim_expires`, `task_runs`). Это тот же дефект, из-за которого мы
затевали проект: колонка отвечает и за факт, и за политику, поэтому врёт ровно тогда,
когда сломана, а «почему дело стоит» приходится восстанавливать догадкой.

В 0.0.3 состояние считается из **своего журнала**: `state(deal) = fold(events)`. Журнал
принадлежит плагину, живёт отдельно от kanban и не переписывается задним числом.

## Хранилище

```
$HERMES_HOME/duty/duty.db          # свой журнал, plugin-owned
```

- `journal_mode=WAL`, `busy_timeout=2000`, `synchronous=NORMAL`.
- Файл создаётся при первом запуске; отсутствие файла — не ошибка, а «журнала ещё нет».
- Чужие БД (`kanban.db`, `state.db`, `pool.db`) открываются **только** `mode=ro`,
  кроме пула вопросов: в `pool.db` плагин пишет через `ask()` (разрешено Max 03.11).

```sql
CREATE TABLE IF NOT EXISTS events (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  ts              INTEGER NOT NULL,          -- unix seconds, момент факта
  recorded_at     INTEGER NOT NULL,          -- unix seconds, момент записи
  deal_id         TEXT    NOT NULL,          -- d_<hex>: адрес дела (доски нет с 0.0.6)
  kind            TEXT    NOT NULL,          -- см. набор ниже
  payload         TEXT    NOT NULL DEFAULT '{}',  -- JSON, только факты источника
  source          TEXT    NOT NULL,          -- ingest | ask | cli | api | engine | shell
  idempotency_key TEXT    NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS events_idem ON events(idempotency_key);
CREATE INDEX IF NOT EXISTS events_deal ON events(deal_id, id);
```

`payload` — сырые факты, а не выводы: `{"run_id": 41, "pid": 991, "status": "blocked",
"kind": "needs_input", "reason": "…"}`. Никаких вычисленных состояний в журнале: состояние
всегда пересчитывается fold'ом, иначе в журнале появится вторая правда.

Четыре вида плана заведены движком 1.0 (`docs/ENGINE-1.0.md`, раздел 8): файл
`duty.yaml` остаётся seed-ом, а принятый план живёт фактами и переживает реплей.
Внутри плана порядок причинный: `plan_proposed` → `plan_gate` → `plan_accepted`
или `plan_rejected`. Все четыре идут **после** `attempt_ended` той попытки,
которая принесла предложение: решение по плану — суд над отчётом, а не пролог
попытки (`journal.KIND_ORDER`). Обратный порядок стирал отказ: `plan_rejected`
возвращал этап плана в работу, а следующий в том же пакете `attempt_ended(done)`
снова закрывал его — дело `d_1cae95b3` закрылось «все этапы пройдены» через 39
секунд, не запустив ни одного предложенного этапа. Внутри плана порядок остался
прежним: обратный («решение до гейта») при равном `ts` вернул бы уже решённый
план в ожидание человека. Следующей попытке граф всё равно виден: она начинается
своим фактом с бо́льшим `ts`, а не тем же пакетом.

Граф дела читается **одной функцией** (`transit.graph`): seed-спека плюс этапы
принятой ревизии, повторно проверенные `spec.parse_plan` (журнал не второй
валидатор: мусор в `plan_accepted` граф не вырастит). Предложение (`plan_proposed`)
граф не меняет — оно предложение. Запись ревизии с `id` уже существующего этапа —
**перестановка**: у неё берутся только `needs`/`parallel_with`, и граф получает
новые рёбра этого этапа; переставлять можно только неначатый этап (отказ
`plan.reorder` пишет движок в момент предложения, по фактам попыток журнала).
Этапы seed, у которых в `needs` стоит этап
плана (`close`, `needs: [plan]`), получают ещё и «последние» этапы плана: иначе
закрытие стало бы готово сразу после принятия плана и закрыло бы дело до работы,
которую план объявил. Этап, объявленный планом параллельным такому этапу seed, в
его `needs` не попадает: объявленная параллель не превращается в ожидание. Отказ
(`plan_rejected`) возвращает этап плана в работу,
считает раунд и пишет причину с `issues[]`; сверх `charter.max_rounds_replan`
этап кончается `failed(contract)`. Принятие закрывает этап плана — он предложил
план и закрылся им.

Восемь видов (`review_requested`, `changes_requested`, `collected`, `gate_opened`,
`gate_closed`, `patched`, `commented`, `attached`) заведены вместе с W5 — владением
своим делом (`docs/OWNERSHIP.md`). Их пишут только мутации своих дел; ingest их не
создаёт: у kanban-карточки нет вердикта ревьюера, который duty считал бы своим
фактом. `gate_closed` пишет мутация **родителя**, а событие ложится в журнал ребёнка —
тем же действием и той же транзакцией, иначе переход ребёнка остался бы молчаливым.
У `gate_opened` два писателя: та же мутация родителя и `create` — когда ребёнок заводится
при уже закрытых родителях, переход пишется сразу (`cause: "created"`), иначе снимок
`created` выглядел бы как незакрытый гейт.

Фаза `say` (0.1.0) — кусок текста агента между инструментами. Поток отдаёт
`text` по дельте на токен, поэтому раннер копит дельты и пишет **один** факт на
фразу: `duration_ms` (сколько длился кусок) и `preview` (первая строка, ≤ 120
символов). Смысл ровно один: отличить «модель думала и говорила» от «двадцать
минут ничего не приходило». Превью — слова самого агента, а не содержимое
файлов: журнал отвечает «думал или молчало», а не пересказывает работу.
`say` двигает живость попытки (`progress.last_at`), но не счётчик инструментов.

`attempt_progress` заведён движком 0.0.4 (`dashboard/runner.py`): по каждому
`tool_use`/`tool_result` потока попытки пишется один факт. Без него по журналу видно
только «попытка была», а не «что она делает», и разбор зависаний снова требует `ps` и
хвостов логов. Набор при этом остаётся закрытым: расширение — одно слово и одно правило
fold (14), а не второй вид на каждое событие попытки.

`published` заведён движком 0.0.5 и входит в `NON_STATE_KINDS` (правило 12): он не
меняет ни состояние этапа, ни закрытость дела — этап закрыт своим `attempt_ended`, а
публикация это факт о дереве. Пишет его только движок и только после сверки с origin:
исполнитель заявляет `published` в `result.json`, но заявка без подтверждения даёт
отказ класса `contract` («публикация заявлена, но не найдена»), а не факт журнала.

`released` заведён движком 0.0.8 (`dashboard/release.py`) и, наоборот, **state-changing**:
он ставит строке дела `ready`/`todo` и потому в `NON_STATE_KINDS` не входит. Дело он при
этом не закрывает: `completed` — единственный факт закрытия (`_closed_kind`), поэтому
после `released` `fold` честно отвечает `no_live_fact`, а поверхность показывает
`wait_slot` («идущей попытки нет, следующего шага движка не было»), а не `no_signal`.
Пишется он ровно там, где ответ `transit` — `run` или `wait(retry)`: если журнал говорит
`done`, `failed` или `park`, факт называется своим словом (`completed`, `blocked`), и
`released` вместо них был бы вторым мнением о том, что решил граф.

### Вид этапа и расход попытки: поля 0.0.5

Вид этапа **не заводит новых событий**: `kind: shell` и `kind: gate` пишут те же
`attempt_started`/`attempt_ended`, а вид у них читается из `stage_kind`. Где ключ
действительно есть (`dashboard/runner.py`, `dashboard/stagefeed.py`):

| факт | `stage_kind` | `source` | почему так |
|---|---|---|---|
| `attempt_started` этапа `kind: shell` | `shell` | `shell` | попытку исполнила команда, а не профиль: по `source` видно писателя, по `stage_kind` — вид |
| `attempt_started` этапа `kind: agent` | **ключа нет** | `engine` | отсутствие `stage_kind` читается как `agent` (`stagefeed.py:223`): старые записи 0.0.4 остаются верными без миграции |
| `attempt_ended` этапа `kind: shell` | `details.stage_kind` нет; вид виден по `source: shell` | `shell` | у попытки-команды свой набор `details` (ниже) |
| `attempt_ended` этапа `kind: gate` | `details.stage_kind: gate` | `engine` | `attempt_started` у гейта нет вовсе: он не работает, а ждёт |
| `attempt_ended` отказа движка (`refused: true`) | `details.stage_kind` — вид этапа | `engine` | отказ бюджета или публикации пишется без начала |

`details` попытки-команды (`kind: shell`, `attempt_ended`) — измеренное, а не
сказанное:

| поле | что это |
|---|---|
| `cmd` | строка `cmd` из спеки — та же, что в `shell_cmd` у `attempt_started` |
| `exit_code` | код возврата процесса (`null` — код неизвестен) |
| `duration_sec` | сколько шла команда, секунды с одним знаком (`round(..., 1)`); по нему считаются минуты бюджета дела |
| `must` | обязательный код из спеки: с ним сверяется `exit_code` |
| `timed_out` | остановила ли команду наша собственная рука по сроку этапа |
| `stdout_tail` / `stderr_tail` | последние 20 строк вывода: журнал отвечает «чем кончилось» |
| `stdout_path` / `stderr_path` | полные логи файлами (`.duty/stdout.log`, `.duty/stderr.log` в каталоге попытки): файл отвечает «что было написано» |

`details` гейта (`kind: gate`, `attempt_ended`) — **вопрос, ответ и правило**:
`stage_kind: gate`, `question_id`, `answer` (цитата ответа человека, до 80 знаков —
целиком ответ живёт в пуле и в `question_answered`), `allow` (список, с которым
сверяли). В `payload.result` гейт ничего не пишет — отчёта у него нет. Вид и
закрытие называет **строка шага** (то, что вернул `runner`: `stage_kind: gate`,
`closed`), и драйвер кладёт их в `steps[i]` отчёта прогона — `--json` тоже
(см. «Закрытие — факт журнала»).

`usage_tokens` — расход попытки в токенах, пишет движок по потоку процесса
(`attempt_ended.details.usage_tokens` у `agent`). У `shell`-попытки ключа нет:
команда токенов не тратит, её расход — минуты по `duration_sec`. Если у
`agent`-попытки телеметрии нет, бюджет дела берёт `result.usage.total_tokens` —
слово исполнителя в том же событии (`dashboard/budget.py:_tokens_of`), а нет ни
того, ни другого — ноль, и это тоже факт, а не догадка.

Отказ по бюджету дела — `attempt_ended` **без** `attempt_started`:
`kind: capability`, `details.refused: true`, `details.stage_kind` (вид этапа) и
`details.budget: {kind, used, limit}` — единица (`tokens`/`minutes`), расход и
потолок числами; причина «бюджет дела исчерпан: N/M токенов». Рядом — `blocked`
с `block_kind: capability` и теми же числами, чтобы поверхность показывала
`capability`, а не «running без живого факта».

Отказ публикации без «ок» — та же форма: `attempt_ended` без начала,
`kind: contract`, `details.refused: true`, `details.publish: {gate, question_id,
approved_commit}`.

Набор закрыт: новый `kind` добавляется вместе с правилом fold и тестом, а не «по пути».
Закрытость держится кодом, а не дисциплиной: `append()` отвергает `kind` вне набора
(`ValueError`) до записи, поэтому «почти записанной» пачки в журнале не остаётся.

### Что читает экран «Здоровье» (0.0.6)

`/stats` и `bin/duty stats` считают **дела движка**, а не карточки kanban, и берут все
числа из этого журнала — окно по умолчанию сутки, границу называет `?since=`/`--since`.

| метрика | какие факты нужны | чего не хватает, если факта нет |
|---|---|---|
| этапы с первой попытки | `attempt_started` (пара `deal_id` + `stage`) и закрывающий `attempt_ended` с `outcome=done`; повторный `attempt_started` того же этапа убирает его из числителя | этап без закрытой попытки в знаменатель не идёт; знаменатель 0 — доля `null`, а не «100 %» |
| ожидание человека | `question_asked` и `question_answered` с общим `question_id` | вопрос без ответа — не «ждали 0», его в выборке нет; вопрос роли (1.0, без `question_id`) в эту метрику не входит: ждали роль, а не человека |
| ожидание до первой попытки этапа | `attempt_started.ts` и `created_at` дела (`created`) | нет `attempt_started` — ожидания нет, а не «ноль секунд» |
| отказы контракта | `attempt_ended` с классом `contract` в `kind` (старые записи — `details.class`) и текстом `reason` | без `reason` и `details.rule` правило ответа — `без правила` |
| токены за окно | `attempt_ended.details.usage_tokens` (`agent`-попытки; у `shell` его нет по устройству) | ни одной записи — `tokens.total = null` и `warnings`, а не 0 |
| таксономия исходов и классов | `attempt_ended.outcome` и `attempt_ended.kind` | попытка без `attempt_ended` — `живая`/`мёртвая` (`stagefeed`), в исходы окна не входит |

Карточки kanban в эти числа не входят ни одним полем: их статусы и исходы ранов живут
в `kanban.db` и видны только наблюдением `GET /cards` — в `/stats` и `bin/duty stats`
их нет вовсе (0.0.7). У карточки нет ни этапов, ни отказов контракта, ни токенов —
считать по ней здоровье значило бы мерить чужой объект.

## Идемпотентность

`idempotency_key` — строка, уникальная для факта источника:

- ingest: `ingest:<deal_id>:<kind>:<stable>` где `stable` — идентификатор факта
  источника (например `sha1(claim_lock|claim_expires)`), а не время. Прохода ingest
  из kanban больше нет (0.0.6): правило оставлено для журналов, заведённых до 0.0.6;
- ask: `ask:<question_id>:<kind>`;
- cli: `cli:<deal_id>:<kind>:<sha1(аргументы)>`;
- api: `api:<deal_id>:<kind>:<sha1(тело запроса)>` — мутации своих дел по HTTP
  (`docs/OWNERSHIP.md`). Один и тот же вызов второй раз даёт 0 новых строк, чем бы
  он ни пришёл; что CLI, что API пишут в один модуль (`dashboard/deals.py`).

Повтор того же факта обязан быть no-op: `INSERT OR IGNORE` по уникальному индексу.
Тест: два прогона подряд → число строк не меняется, `fold` даёт тот же результат.

## Закрытие — факт журнала

Дело закрыто тогда и только тогда, когда в журнале есть `completed`. Это один
предикат (`journal.closed_fact`, он же правило 2 `fold`) на все поверхности: `deal`,
`why`, `run` и ответ API (`closed`) называют причину и время из журнала, а не из
строки `status`. Отдельного отбора «только `completed` без `stage`» нет намеренно:
человеческое закрытие (`close`, `decide stop`) называет в payload этап, на котором
стояло дело, и такой факт закрывает **дело**; смешением этого с «закрыт этап» и
разъезжались поверхности — одна говорила «закрыто», другая «живо».

Причины (`payload.cause`):

| `cause` | кто пишет | что значит |
|---|---|---|
| `all_stages_done` | движок (`deals.close_stages_done`) | `transit` ответил `done` — все этапы графа пройдены, закрывающего этапа в графе нет |
| `lead_closed` | движок (`deals.close_stages_done`) по приговору лида | в графе есть закрывающий этап (`spec.CLOSE_STAGE`), и лид вынес `approve`: дело закрыл он, итог — в `payload.summary` (`docs/ENGINE-1.0.md`, раздел 9) |
| `stopped_by_human` | человек (`bin/duty decide <дело> stop`) | решение остановить: запаркованное дело или бегущее без живого драйвера |
| `closed_by_human` | человек (`bin/duty close <дело> --reason …`); движок — когда гейт перед публикацией получил ответ «не публиковать» | дело закрыто решением человека, а не ходом движка |
| *(нет `cause`)* | `complete`, сдача в ревью | дело сдано как `done` (внешнего закрытия «на доске» больше нет: доск нет) |

`payload.stage` у человеческого закрытия — адрес (`где стояло дело`), а не признак
«это факт этапа»: принадлежность событию решает `kind`, а не наличие `stage`.
`transit` читает `completed` со `stage` как закрытие этапа, поэтому прогон
спрашивает `journal.closed_fact` **до** первого шага: закрытое человеком дело
попыток не поднимает (иначе следующая попытка воскресила бы его).

**«Все этапы пройдены» — факт, а не строка вывода.** До 0.0.4 прогон печатал «итог:
дело закрыто» и не писал ничего: живой прогон `d_6e764042` прошёл три этапа, а дело
осталось `status='running'` без `completed` — `/now` показывал `no_signal`. Теперь
`completed` и строка дела пишутся **одной транзакцией**, а итог печатается по записи.
Повторный прогон на закрытом деле второго `completed` не пишет и строку не трогает
(`already: true`, `at` — из журнала), поэтому «уже закрыто» не выдаётся за новое
закрытие.

Движок не закрывает дело, которое держит человек: открытый `blocked` (без `unblocked`),
`review` или `archived` — отказ, и прогон говорит «все этапы закрыты, но дело не
закрыто» с причиной. Иначе первый же шаг движка стирал бы ожидание вердикта или блок
человека — ту же подмену, только в другую сторону.

`stopped_by_human` на бегущем деле разрешён, только если работу некому вести: строки
лизинга нет либо её срок прошёл. Снятие протухшего лизинга идёт той же транзакцией,
что и `completed`; живой лизинг — отказ и ни одной записи (чужую работу не рвём).

**Закрытие гейтом видно прогону отдельным флагом.** Ответ «не публиковать» — это
`attempt_ended` этапа-гейта с `kind=contract` **и** `completed` того же шага, поэтому
строка шага несёт `closed: true` (`--json`: `steps[i].closed`, у остальных шагов
`false`). Без него прогон прочитал бы отказ гейта как отказ попытки и напечатал бы
«попытки исчерпаны» поверх записанного `completed` — поверхность говорила бы о сбое
там, где человек сказал ровно то, что хотел.

## Fold

`fold(events) -> waiting` — чистая функция без I/O, живёт в `desktop/model.js`-подобном
модуле на стороне бэкенда (`dashboard/journal.py`), чтобы UI ничего не пересчитывал.

Правила:

1. События применяются в порядке `id`.
2. Если последнее **state-changing** событие — `completed` (архив приходит тем же
   видом со `status="archived"` в payload), дело не активно, в `/now` не попадает.
   Закрытость считается по последнему факту, менявшему состояние, а не по последней
   строке журнала: виды из набора `journal.NON_STATE_KINDS` — `commented`, `attached`,
   `patched`, `question_answered` — состояние не меняют (правило 12) и закрытость не
   снимают. Иначе дело «воскресало» бы на экране: комментарий или поздний ответ на
   вопрос после `completed` возвращали его в состояние ожидания. Набор назван в одном
   месте кода, а не разбросан по `if` в вызывающих.
3. `blocked` без последующего `unblocked` → `wait_human` с `evidence` из payload.
   Исключение — доступ и права: `block_kind='capability'` (или причина блока со словом
   из `CAPABILITY_WORDS`) даёт состояние `capability`, а не `wait_human`: человек тут
   не решает, а даёт доступ. Таксономия — `docs/DESIGN.md`.
4. `claimed`, за которым нет `attempt_started`, и у которого в журнале записан срок
   (`claim_expires`) и этот срок уже прошёл, → `dead_lease`. «Протух» — свойство
   срока: `claimed` без срока (своё дело — `duty claim` пишет `claim_expires: null`)
   `dead_lease` не даёт никогда, сколько бы времени ни прошло.
5. `attempt_started` без `attempt_ended`, pid мёртв → `crashed`; pid не читается →
   `no_signal` (tri-state, как в 0.0.2). Правило остаётся срезом, но вечно висеть такой
   попытке больше не даёт `reaper.sweep`: после истечения лизинга и запаса
   `ttl + max(60 с, ttl/3)` он пишет настоящий `attempt_ended` (`kind=infra`,
   `reaped: true`), и дело уходит по обычной политике ретраев. Срок — не единственный
   факт (0.0.7): мёртвый pid закрывает попытку и при живом лизинге, иначе убитый
   рестартом воркер висит «попытка идёт» до конца лизинга. Свой pid (`os.kill(pid, 0)`)
   спрашивается только у своего дела и не раньше минуты жизни попытки; чужой живой
   лизинг не трогается — движок может быть на другой машине или в другом namespace
   (`docs/PROBES.md`).
6. `question_asked` без `question_answered` → `wait_human` с `human_kind="question"`;
   это и закрывает п.5 заметки 0.0.2: «ждёт ответа» считается по вопросам, а блокировка
   без вопроса имеет `human_kind="status"`. У вопроса роли (1.0) номера пула нет, и
   пара «вопрос → ответ» закрывается **по порядку журнала**: ответ без `question_id`
   снимает последний открытый такой вопрос. Иначе вопрос, на который роль уже
   ответила, висел бы «без ответа» до конца жизни дела, и `wait_human` стал бы
   постоянным.
7. Журнал без единого события по делу (события есть у других дел, а у этого нет) →
   состояние берётся из `deals.status` поверхностью (`OWN_WAITING_FALLBACK`), а
   `evidence` честно говорит, что живых фактов журнала нет. Прохода из kanban,
   который «подобрал» бы такие дела, с 0.0.6 нет: карточки — наблюдение, а не факты
   журнала.
8. От дела остался только снимок `created` (последнее state-changing событие —
   `created`), и в нём есть родители → `wait_gate`. Комментарий или правка
   спецификации снимок не отменяют: они входят в набор `journal.NON_STATE_KINDS` и
   состояние не меняют (правило 12).
   Закрытие родителей видно в их собственных событиях, а не в этих, поэтому факт
   назван снимком («родители на момент created»), а не сегодняшним состоянием графа.
   Правило 8 — расширение таксономии `docs/DESIGN.md`, не отмена правил 1–7.
9. `review_requested` без последующего `collected`/`changes_requested` →
   `wait_human` с `human_kind="status"`: сдано в ревью, вердикта нет. Это тот же
   смысл, которым статус `review` уже назван в `WAITING_FALLBACK` («ждёт вердикта
   ревьюера»), — человеку нужно решение, а не ответ на вопрос. `reviewer` из
   payload попадает в `evidence`.
10. `changes_requested` без последующей сдачи → `wait_slot`: дело возвращено на
    доработку, и ждёт оно исполнителя, а не решения — решение человек уже принял.
    Причина берётся из payload и попадает в `evidence`. Состояние `wait_human`
    здесь было бы ложью в другую сторону: оно перебивает `claim` и попытку по
    приоритету и висело бы на деле, которое уже в работе. Взятое после возврата
    дело (`claimed` позже `changes_requested`) этот факт снимает: причина возврата
    остаётся в таймлайне, но «ждёт исполнителя» про такое дело уже неправда.
    Ожидание снимается новой сдачей (`review_requested`), `collected`, `completed`
    или `claimed`, а не временем: необработанный возврат обязан быть виден.
11. Гейт по родителям: `gate_closed` без последующего `gate_opened` → `wait_gate`:
    родителя вернули из закрытого статуса, и ребёнок снова ждёт. `parent` и `to` из
    payload попадают в `evidence`. Это тот же `wait_gate`, что у снимка `created`
    (правило 8), но по последнему известному факту, а не по снимку: переход назван
    событием, а не выведен из колонки. Обратный факт `gate_opened` ожидание снимает.
12. Виды из набора `journal.NON_STATE_KINDS` — `commented`, `attached`, `patched`,
    `question_answered`, `attempt_progress`, `lead_started`, `lead_exited` — **не
    создают состояния** и в `WAITING_PRIORITY` не участвуют: «оставил комментарий»,
    «поправил title», «пришёл ответ на вопрос», «попытка вызвала инструмент» или
    «лид поднят/вышел» — не ожидание. Это виды, которые закрывают или дополняют, но
    не открывают: ответ на вопрос снимает `wait_human`, а не заводит новое ожидание.
    У лида то же самое: подъём сессии не меняет, чего дело ждёт (ведёт его лид или
    никто — это вопрос сторожа, а не состояния), а выход лида по уже запаркованному
    делу не воскрешает его и не снимает ожидание человека. Эти факты живут в
    таймлайне дела, и вторая правда о состоянии из них не выводится. Тем же набором
    считается и закрытость: закрытое дело после них остаётся закрытым (правило 2), и
    `lease_lost` по такому делу на ingest не пишется. Правило названо явно, чтобы
    отсутствие этих видов в fold не читалось как забытая ветка.
13. `collected` состояние не поднимает: вердикт снял ожидание ревью, и дело
    возвращается к тому, что говорит его `status` (своё дело — `deals.status`).
14. `attempt_progress` не меняет состояние, но **копится в срезе** счётчиком:
    `progress = {tools, last_tool, last_at}` — сколько инструментов вызвала попытка,
    какой последний и когда был последний факт телеметрии. Это то, что читает консоль:
    «что делается прямо сейчас» берётся из журнала, а не из `ps` и хвостов логов.
    `tools` считает `tool_use` (вызов), а не `tool_result`: один вызов — один
    инструмент. В payload нет ни текста команд, ни содержимого файлов — журнал не
    заменяет лог. Неизвестная фаза и мусорный payload пропускаются: сверка не падает
    от чужой строки.


## Синк ответов пула

Отдельного прохода ingest из kanban больше нет (0.0.6: доск нет, ingest удалён вместе
с ними). Остался ровно один синк — ответы пула (`ask.sync_answers` →
`question_answered`): иначе отвеченный вопрос навсегда остался бы живым фактом
ожидания. Его зовёт драйвер перед каждым решением (`bin/duty run`, `--once`); ни
один роут синк не делает — срез только читает.
Одно и то же событие пишется один раз — идемпотентность по
`ask:<question_id>:question_answered`. Инварианты:

- kanban не меняется ни в каком виде: плагин его только читает (`/cards`), и это
  проверяется тестом по mtime;
- синк не «додумывает»: нет строки в пуле — нет события;
- вопросов синк не создаёт: единственный канал вопросов — `ask()` по явному
  запросу `POST /ask/{deal_id}`;
- ошибка пула не валит ответ: она попадает в `errors[]` как в 0.0.2.

## `ask()`

Единственный канал вопросов. Пишет в `messaging/pool.db` (схема imessage-gateway):
`session_key=t_d_<deal_id>`, `origin='duty'`, `kind='decision'`, `text` — краткая строка,
`text_full` — развёрнутая с фактами дела, `options_json` — варианты, если заданы.
Код — `dashboard/ask.py`; остальной плагин пул только читает (`mode=ro`).

- Перед созданием ищет живой вопрос по делу (`session_key=t_<id>`, статус `sent`
  **или** `pending` — второй означает «вопрос создан, но демон моста ещё не отправил
  его в iMessage»; без него два вызова подряд в эти секунды дали бы два вопроса):
  есть — возвращает его, дубль не создаёт. Дальше два случая, и они разные:
  живой вопрос **своего** продюсера (`origin='duty'`) получает факт `question_asked`
  идемпотентно (так журнал узнаёт о вопросе, созданном до включения журнала); живой
  вопрос **чужого** продюсера (`origin != 'duty'`, например вопрос сканера карточек)
  возвращается только своим id — в журнал по нему не пишется ничего. Причина: журнал
  `duty/duty.db` наш, чужому продюсеру писать в него некуда, а значит факт «ответ
  получен» для чужого вопроса принципиально нечем снять — записанный `question_asked`
  висел бы в fold вечно и дело навсегда «ждало ответа». Поверхность такой вопрос и
  так видит напрямую в пуле (см. ниже) и поднимает состояние до `wait_human` честной
  пометкой. В ответе роута подхват отличается полем `adopted: true`, а не молчит.
- У подхваченного вопроса аргументы вызова (`text`, `text_full`, `options`,
  `critical`) не применяются: вопрос уже задан, и его факты (`critical`, `timeout`,
  `created_at` → `ts` события) берутся из строки пула. Явный `critical` важнее
  расчёта **только при создании** вопроса.
- `critical=1` ставится, когда дело в `wait_human` дольше `ASK_CRITICAL_SEC` (дефолт
  7200) — критичность считается по `ts` открытого блока в журнале, а не по возрасту
  карточки. У некритичного вопроса задан срок `ASK_TIMEOUT_HOURS` (24 ч), у
  критичного `timeout IS NULL` (не истекает). Явный `critical` вызывающего важнее
  расчёта.
- Дедуп неатомарен (SELECT живого вопроса, затем отдельный INSERT, без транзакции):
  уникального индекса в чужой схеме пула нет и заводить его мы не вправе, поэтому два
  одновременных `ask()` теоретически могут дать две строки. Цена известна и принята:
  второй вопрос виден в пуле как дубль, а не теряется.
- Ответ и **истечение срока** читаются по `question_id`; при первом из них пишется
  `question_answered`, вопрос закрывается штатным путём пула (не руками в SQL).
  Читает `sync_answers(conn, home)` — только свои вопросы (`origin='duty'`) в статусе
  `answered` **или** `expired`, идемпотентно по ключу
  `ask:<question_id>:question_answered`. Зовёт его драйвер перед каждым решением
  (`bin/duty run`, `--once`); ни один роут синк не делает — прохода ingest больше нет.
- `expired` — это не ответ: пул переводит протухшую строку (некритичный вопрос
  старше `timeout`) в этот статус, не заполняя ни `answered_at`, ни `answered_via`.
  Факт закрытия пишется как `question_answered` с `answered_via="expired"` и
  `answer_len=0`, а `ts` = момент, когда закрытие увидела duty (момент истечения в
  пуле не записан). `answer_len=0` для `expired` — намеренно: `answer` у протухшей
  строки пул не заполняет, а если что-то в этой колонке и осталось, это не ответ по
  вопросу, и выдавать длину этого текста за длину ответа значило бы соврать. Если пул
  причину назвал сам (например `answered_via="card"` —
  условие алерта исчезло), в факте остаётся его причина: подменять её на «истёк
  срок» значило бы соврать. Без этого факта неотвеченный вопрос с истёкшим TTL
  оставался бы в журнале открытым навсегда — второй триггер того же «вечно ждёт
  ответа».
- Адрес вопроса (кому задан и почему) лежит **вложенным** ключом
  `payload.routing = {target, reason, stage, attempt}` и только когда вопрос
  адресовал движок (`dashboard/routing.py`): верхний уровень `payload` — словарь
  пула, а `stage` верхнего уровня значил бы «событие относится к этапу» и увёл бы
  `question_asked` из ветки вопроса дела. В пул адрес не пишется: у пула своя
  схема, а этап и попытка — свойство журнала; второй канал («роль отвечает прямо в
  пуле») не заводится — ответ роли это новая попытка, а не строка пула.
- Создание вопроса фиксируется в журнале **после** успешной вставки в пул; при сбое
  пула событие не пишется, ошибка уходит в `errors[]`. Сбой журнала после успешной
  вставки — `AskError` «вопрос создан, факт журнала не записан (идемпотентный повтор
  лечит)», а не 500 без подробностей: строка пула уже есть, и это должно быть сказано.
  Нулевой `question_id` от вставки — тоже `AskError`: ключ `ask:0:*` в журнале
  заглушил бы все будущие `question_asked`.

### Вопрос роли (1.0): журнал вместо пула

Фактовый вопрос этапа (`ask.allowed`, разметка `kind: fact`) пул не трогает вовсе:
строку вопроса создаёт не `ask()`, а движок (`runner.ask_role`) — сначала факт
`question_asked` без `question_id`, потом спавн роли, потом её ответ фактом
`question_answered` с `by=<роль>` и `hops=<n+1>`. Это те же два вида событий и та
же пара, что у человеческого вопроса, — «второй канал» не появляется, а
`question_answered` у ответа роли закрывает вопрос **по порядку журнала** (номера
нет, потому что нет строки). Пул остаётся единственным каналом для человека, и
`ask()` — единственный, кто в него пишет.

- `authority: true` в ответе роли — «это не мне решать»: передача закрывается
  `question_answered` с `answered_via="redirected"` и причиной, а тот же текст
  уходит человеку обычным `question_asked` с причиной `role_redirected`;
- провал попытки ответа (`infra`/`contract`) — `answered_via="failed"` с причиной
  отказа и вопрос человеку с причиной `role_answer_failed`: вопрос не сгорает;
- движок, ушедший между вопросом и ответом, — тот же `answered_via="failed"`, но
  причину называет восстановление: `runner.recover_role_questions` (вызывается
  драйвером перед решением) закрывает передачу и уводит вопрос человеку, а не
  ждёт ответа, которого уже не будет;
- `redirected`/`failed` — **не срок**: `transit._expired` читает пустой
  `answer_len` как `expired` только у ответа человека, иначе переадресованный
  вопрос читался бы как истёкший и дело парковалось бы мимо живого вопроса;
- `text` вопроса у роли живёт в журнале (`payload.text`) — в контракт роли он
  попадает оттуда же, и разбор «что спросили и что ответили» не требует пула.

В ожидание человека (`waiting_human_sec` в `/stats`) вопросы роли не входят: пара
без `question_id` в выборку по номеру пула не попадает, и это правда — ждали
роль, а не человека. Остаток пар в списке дел (`questions.waiting`) считает оба
вида: порядок пар не зависит от номера.

Кто и когда зовёт: явный путь `POST /ask/{deal_id}` (тело
`{"text", "text_full", "options", "critical"}`) — вопрос задаёт человек или
координатор, когда дело в `blocked`/`needs_input` стоит без вопроса. Синк вопросов
**не** создаёт: пул решений наполняется осознанным действием, а не проходом по срезу.
Так закрывается п.5 заметки 0.0.2: дело без вопроса больше не выдаёт себя за «ждёт
ответа» — у него `waiting.human_kind="status"`, а после `ask()` — `"question"`.

Живой вопрос пула, о котором журнал ещё не знает (вопрос задал другой продюсер пула,
`sync_answers` до него ещё не дошёл), тоже считается фактом: поверхность
поднимает дело до `wait_human` с `human_kind="question"` и пишет в `evidence`, что
факт из пула, а не из журнала («в журнале вопроса нет»). Это не вторая правда о
состоянии, а честно подписанный источник факта — иначе вопрос без ответа выглядел бы
как «человеку ничего не нужно».

## Evidence-гейт (0.0.4, `dashboard/evidence.py`)

`attempt_ended` с `outcome=done` пишется **только** когда пакет попытки принят:
движок зовёт `evidence.verify(result, stage, workdir, attempt_started_at, now)`
после смерти процесса и **до** записи факта. Отказ гейта — тот же
`attempt_ended`, но `outcome=failed` и `kind` из вердикта; первые три отказа
лежат в `reason`, полный список — в `details.verdict.details`. Второго вида
события на это нет: «попытка не принята» — свойство того же конца попытки.

Слой ничего не запускает (команды из `evidence` уже выполнил исполнитель), в сеть
не ходит и тексту `summary` не верит. Порядок проверок — от «что заявлено» к
«чем подтверждено»:

| шаг | что сверяется | правило отказа | класс |
|---|---|---|---|
| 1 | `status` ∈ {`done`, `blocked`, `refused`}; для `done` есть свидетель этапа (`commit`\|`artifacts`, `verdict` или `published` — по `evidence.witness`), `evidence`, `summary`; лишнее поле — предупреждение | `status`, `required`, `extra` | `contract` |
| 2 | артефакт: относительный путь внутри дерева попытки, файл есть, `sha256` полный и совпадает; отказ называет мерку («искали относительно дерево/каталог попытки») и подсказывает `workspace: worktree`, если файл нашёлся в дереве попытки | `artifact.path`, `artifact.missing`, `artifact.sha256` | `contract` |
| 3 | `git rev-parse --verify <commit>^{commit}` в дереве; коммит не предок базы (предок = «принёс чужое готовое») | `commit.resolve`, `commit.foreign`; `commit.base` — предупреждение, если база не резолвится | `contract` |
| 4 | по каждой `{cmd, must}` из `stage.evidence` есть запись с тем же `cmd`, `exit == must` и `started_at` ≥ начала попытки (и не позже «сейчас») | `evidence.missing`, `evidence.exit`, `evidence.stale`, `evidence.future` | `contract` |
| 5 | `cmd` совпадает со спекой посимвольно после нормализации пробелов: «почти та же команда» | `evidence.substituted` | `contract` |
| 6 | `usage.total_tokens` больше `stage.budget.tokens` — работа сделана, но за рамками | `budget.tokens` | `capability` |

Классы: `contract` для шагов 1–5, `capability` для 6. `infra` гейт не выдаёт
никогда — «процесс не дожил» остаётся фактом движка (таймаут, код выхода,
отсутствие отчёта). Если пакет не сходится **и** бюджет превышен, класс —
`contract`: подлог в отчёте важнее рамок.

Схема отчёта уходит исполнителю в файл контракта (`report_schema` в
`attempt_started.contract`): гейт, о правилах которого узнают только из отказа, —
не контракт, а ловушка. Требуемый свидетель (`required_for_done`) берётся из той же
функции, что и проверка, — `evidence.witness(stage)`: `commit|artifacts` у обычного
этапа, `verdict` у этапа с приговором, `published` у публикующего
(`docs/SPEC.md`, «Свидетель этапа»).

Принятый свидетель называется в самом факте: `attempt_ended.details.witness`
(`commit|artifacts` / `verdict` / `published`, `null` — пакет не принимался) и рядом
`details.verdict.witness`. По журналу видно не только «принято», но и чем этап
назвал работу — без этого разбор отказа идёт по коду плагина.

Что гейт **не** делает: не запускает объявленные команды повторно, не считает
дело закрытым (`fold` читает факт), не ставит ретраи — это `transit`/`failures`
по классу из `attempt_ended.kind`.

## Классы отказа и политика ретраев (0.0.4, `dashboard/failures.py`)

Класс отказа — **политика**, а не подпись в логе: единственное место, где он
определён, — `dashboard/failures.py` (`CLASSES`), и `attempt_ended.kind` пишется
оттуда. Класс выводится только из четырёх источников: `result.json`, код выхода
процесса, наличие файла отчёта и `Verdict.kind` гейта. Разбора текста ошибки
регулярками нет и не будет — если для класса не хватает источника, это
`contract` с цитатой в `reason`.

| источник | класс | повторяется по умолчанию | что видно человеку |
|---|---|---|---|
| таймаут попытки | `infra` | да, `max: 1` | `attempt_ended.kind=infra`, `reason` с пределом времени |
| код выхода ≠ 0 без `result.json` | `infra` | да, `max: 1` | `kind=infra`, `reason` с кодом выхода |
| спавн вернул ошибку (нет процесса) | `infra` | да, `max: 1` | `kind=infra`, текст ошибки спавна |
| код 0 и `result.json` нет | `contract` | нет | `kind=contract`, где искали файл |
| `status: "refused"` | `contract` | нет | `kind=contract`, `summary` исполнителя |
| схема/артефакты/коммит/evidence не сходятся (гейт) | `contract` | нет | `details.verdict.details`, первые три отказа в `reason` |
| `usage.total_tokens` больше бюджета этапа | `capability` | нет | `kind=capability`, `budget.tokens` в `details` |
| потолок дела (`budget` в корне спеки) исчерпан по журналу | `capability` | нет | `kind=capability`, `attempt_ended` без начала с `details.refused: true` и `details.budget`, плюс `blocked` с `block_kind=capability`; причина «бюджет дела исчерпан: N/M токенов» |
| нужна роль/доступ, которых нет | `capability` | нет | `kind=capability`, вопрос человеку |
| класс не определён | `UNCLASSIFIED` | нет | `kind` пуст: честное «класса нет», а не догадка |

Лимиты — в спеке этапа: `retry: {max: N, on: [infra, contract]}`; умолчание
`{max: 1, on: [infra]}` (`docs/SPEC.md`). Счётчик — **на этап и на класс**:
два отказа `contract` не съедают лимит `infra`. Исчерпание даёт `failed(kind)` в
срезе и **парковку** дела, а не новый круг.

**Пауза между попытками** — экспоненциальная от 30 с с потолком 5 мин
(`failures.backoff`). Пауза не блокирует движок: `transit` видит `retry_at` и
отвечает `wait("retry", retry_at)` — дело просто ждёт, этап не входит в ready,
пока `now < retry_at`.

**Парковка** (попытки исчерпаны или предохранитель на дело) выражается
существующими фактами, без нового вида события:

- `blocked` с `block_kind: "parked"` и payload `{kind, stage, attempts, limit,
  park_reason, question_id}` — «попытки исчерпаны, решает человек»;
- вопрос через `ask()` (адрес `human`, опции `continue`/`stop`) — властный, а не
  фактовый: движок не спрашивает модель, продолжать ли;
- `park_reason`: `retries_exhausted` (класс не повторяется или лимит класса
  исчерпан) либо `too_many_failures` (`max_rounds_per_deal = 6` упавших попыток
  за дело — защита от `gave_up`-класса).

Девятого состояния ожидания нет (`docs/DESIGN.md`): запаркованное дело — это
`wait_human` с причиной, и в срезе `transit` тоже `wait(parked)` — ожидание того
же человека. Ответ в пуле попытку **не** поднимает (`sync_answers` даёт
`question_answered`, а дело остаётся запаркованным). Подъём — только явное
решение человека: `unblocked` со `previous_kind: "parked"`, и оно сбрасывает
счётчики класса, иначе первый же новый отказ снова упёрся бы в исчерпанный лимит.

## Инварианты (проверяются тестами)

1. Ни одной записи в `kanban.db`/`state.db`: mtime до и после сценария совпадает.
2. `pool.db` пишется только по пути `ask()`; в остальных сценариях — `mode=ro`.
3. Повторный `append` с тем же `idempotency_key` не плодит событий (идемпотентность).
4. `fold` не читает БД: на вход только список событий.
5. В `/health` есть `journal: {events, deals}` — сколько строк в журнале и у скольких
   дел они есть. Расхождения «журнал против kanban» с 0.0.6 нет: карточки kanban —
   отдельное наблюдение (`/cards`), и считать их делами значило бы вернуть доски через
   чёрный ход. Нечитаемый журнал добавляет `note` с причиной, а не нули без объяснения.
6. Второй `ask()` по тому же делу не создаёт второй строки в пуле: возвращается
   `question_id` живого вопроса. Для своего вопроса (`origin='duty'`) в журнале
   остаётся одно событие `question_asked`; для подхваченного чужого — ни одного
   (роут говорит `adopted: true`), иначе факт нечем снять.
7. Сбой пула (нет файла / только на чтение) не пишет события и уходит в `errors[]`;
   `sync_answers` дважды даёт одно событие `question_answered`.

## Что НЕ входит в 0.0.3

- Свой планировщик и spawn воркеров (это уже замена kanban целиком, следующий шаг).
- Запись в kanban-колонки: duty по-прежнему ничего там не меняет.
- Миграция исторических событий задним числом: журнал начинается с момента включения.

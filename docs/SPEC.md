# Спека дела — контракт `duty.yaml`

Формат файла, которым описывается одна настоящая работа: из каких этапов она
состоит, кто их исполняет, что считается доказательством, куда возвращается
приговор и куда уходит вопрос. Файл лежит в репозитории дела, читается движком
до запуска и **проверяется правилами, а не глазами**: каждое правило ниже —
отказ, который случается раньше первого процесса.

Реализация — `dashboard/spec.py` (`load_spec()`, `validate_spec()`,
`check_base()`), тесты — `tests/test_spec.py`, проверка из терминала —
`bin/duty spec check <file>`. Образцы — `examples/duty.yaml` (полный вид из
спеки-источника) и `examples/duty-minimal.yaml` (минимум, при котором дело уже
имеет смысл).

Почему это отдельный слой. В канбане дисциплина «публикация гейтится ревью, а не
реализацией» жила в 60-килобайтном скилле: её знал тот, кто прочитал скилл, и
нарушалась она молча. Здесь то же правило — `verdict.changes` указывает только
на предшественника — стало ошибкой запуска: неправильный гейт не запускается
вообще.

## Путь к спеке

Путь всегда **абсолютный**. `duty.yaml` лежит в репозитории дела, а читает его
движок из `~/.hermes`; относительный путь не даёт восстановить в журнале,
откуда взялась спека. `load_spec()` на относительном пути отказывает
(правило `path`); CLI (`bin/duty spec check`) разворачивает путь сам и печатает
в ответе тот файл, который действительно проверен.

Спека дела записывается в журнал при создании: `duty create --spec duty.yaml`
кладёт путь в `created.payload.spec` (тоже абсолютным путём). Оттуда её берёт лента
этапов на экране «Дело» (`GET /deal` → `stages[]`, `docs/DESIGN.md`): экран не
угадывает граф и не ищет `duty.yaml` рядом с делом, а читает тот файл, по которому
дело заводили. Дело без спеки — законное: лента пуста, а `stages_note` называет
причину.

## Минимум

```yaml
duty: fix-typo-in-header
stages:
  - id: impl
    role: implementer

  - id: review
    role: reviewer
    needs: [impl]
    verdict: {approve: next, changes: impl, max_rounds: 1}
```

Годная спека: единственный вход `impl`, `review` достижим от него, приговор
возвращает назад к предшественнику. Ни `repo`, ни `evidence`, ни `ask` не
обязательны — обязательны `duty` и `stages`.

## Полный вид

`examples/duty.yaml`, ровно пример из спеки-источника
(`~/.hermes/widgets/duty-model.html`, раздел «Как выглядит спека на настоящем
деле»):

```yaml
duty: sx-widgets-tristate
repo: ~/GolandProjects/sx-widgets-api
base: origin/master
stages:
  - id: impl
    role: implementer
    workspace: worktree
    evidence:
      - {cmd: "go build ./...", must: 0}
      - {cmd: "go test ./widget/...", must: 0, timeout_sec: 600}
    retry: {max: 2, on: [infra, contract]}
    budget: {tokens: 200000, minutes: 30}
    ask:
      allowed: [researcher, planner]
      to_human: decisions_only
      max_hops: 2
  - id: verify
    role: tester
    needs: [impl]
  - id: review
    role: reviewer
    needs: [verify]
    verdict: {approve: next, changes: impl, max_rounds: 2}
  - id: publish
    role: publisher
    needs: [review]
    ask: {q: "Публикуем diff?", options: ["пушить", "стоп"], risky: true}
  - id: docs
    role: documenter
    needs: [review]
    parallel_with: [publish]
```

## Поля верхнего уровня

| Поле | Обязательно | Смысл |
|---|---|---|
| `duty` | да | имя дела, уникальное в пределах репозитория |
| `repo` | при `workspace: worktree` | репозиторий дела; абсолютный путь, `~` разворачивается |
| `base` | при `workspace: worktree` | база **дела**: rev, который резолвится в `repo`, — от него отводится дерево первого этапа. Этап с `needs` отводится от коммита предшественника, а не от `base` (движок фиксирует принятую работу коммитом в дереве попытки) |
| `budget` | нет | `{tokens, minutes}`: потолок **на дело целиком**, суммарно по всем этапам и попыткам. Нет поля — потолок только этапный, как в 0.0.4 |
| `charter` | нет | границы роста графа (1.0): `{max_stages, max_rounds_replan, allowed_roles, allowed_kinds, plan_gate}`. Нет блока — дефолты, то есть поведение 0.0.8 (см. «`charter`: границы плана») |
| `stages` | да | непустой список этапов |

Неизвестный ключ верхнего уровня — отказ (`unknown-key`): иначе `repository:`
вместо `repo:` выглядел бы как «repo не задан».

### `budget` в корне: потолок на дело

Этапный `budget` ограничивает **одну попытку**: `tokens` сверяется с расходом
попытки (`dashboard/evidence.py`), `minutes` держит срок лизинга. Дело из пяти
этапов с ретраями укладывалось в каждый этапный потолок и при этом жгло сколько
угодно — поэтому у дела есть свой потолок.

    budget:
      tokens: 200000     # сумма attempt_ended.details.usage_tokens по всем попыткам
      minutes: 40        # сумма длительностей всех попыток

- **Учёт — только по журналу** (`dashboard/budget.py`): расход это сумма фактов
  `attempt_ended` дела, а не счётчик в памяти движка. Поэтому потолок переживает
  рестарт: перезапуск продолжает дело с тем же расходом.
- **Минуты** считаются по паре `attempt_started` ↔ `attempt_ended` (`ts`), у
  `kind: shell` — по `details.duration_sec`. Shell токенов не тратит, минуты тратит.
- **Незакрытая попытка** расхода не тратит: её расход ещё не факт журнала.
- **Исчерпан** — значит «места больше нет»: расход, равный потолку, тоже
  остановка, потому что следующая попытка его пробьёт.
- **Отказ** — класс `capability` с причиной «бюджет дела исчерпан: N/M токенов»
  (или минут). Попытка не поднимается вовсе: лизинг не берётся, процесса нет,
  в журнале остаётся `attempt_ended` с `outcome: failed` и `details.refused: true`
  плюс `blocked` с `block_kind: capability`. `capability` по умолчанию не
  повторяется, так что ретраи здесь не помогают — и не должны.
- **Спека без верхнего `budget`** ведёт себя как раньше: никаких «умолчаний на
  дело» нет, потолок появляется только там, где его объявили.

Проверка на `spec check`: потолок дела не меньше суммы этапных (гейт не
считается — его `budget.minutes` это срок ответа человека, а не расход).
Красный пример — отказ с `file:line` числа дела:

    budget: {tokens: 500}
    stages:
      - {id: impl, role: implementer, budget: {tokens: 400}}
      - {id: check, role: tester, needs: [impl], budget: {tokens: 400}}

    duty.yaml:5: budget: этапы просят больше, чем есть у дела:
      сумма budget.tokens этапов 800 больше бюджета дела 500


### `charter`: границы плана (1.0)

Хартия — вторая половина спеки: `stages` объявляет seed-граф, а `charter` говорит,
насколько этот граф вправе вырасти по ходу дела (`docs/ENGINE-1.0.md`). Принятый
план живёт фактами журнала (`plan_proposed`/`plan_accepted`/`plan_rejected`), а не
этим файлом: движок `duty.yaml` не переписывает никогда.

    charter:
      max_stages: 12          # потолок графа: seed + принятые планом этапы
      max_rounds_replan: 3    # сколько отказов плана переживает этап `plan`
      allowed_roles: [researcher, implementer, tester, reviewer, documenter]
      allowed_kinds: [agent, shell, gate]
      plan_gate: {min_stages: 6, budget_share: 0.6}

- **Нет блока** — годная спека с дефолтами: `max_stages: 12`,
  `max_rounds_replan: 3`, `allowed_roles: []`, `allowed_kinds: [agent, shell, gate]`,
  `plan_gate` выключен (`min_stages: 0`, `budget_share: 0`). Это поведение 0.0.8:
  старые спеки и старые дела работают без правок файла.
- **`max_stages`** ≥ 1 — потолок **всего** графа (`spec.parse_plan` считает seed
  вместе с предложением). Предложение сверх потолка отклоняется (`plan_rejected`) —
  дело не растёт «на посмотреть».
- **`max_rounds_replan`** ≥ 0 — сколько раз этап `plan` переоткрывается отказом;
  сверх — `failed(contract)`, как у `verdict.max_rounds`.
- **`allowed_roles`** — роли, которыми плану разрешено добавлять этапы. Пустой
  список хартию не ограничивает: роль проверяется профилями Hermes (правило `role`).
  Каждая объявленная роль обязана существовать — иначе хартия обещает роль,
  которой движок не поднимет (`charter.allowed_roles`).
- **`allowed_kinds`** — виды этапов, которые план вправе добавить; значения из
  `agent`/`shell`/`gate`.
- **`plan_gate`** — порог вопроса человеку: план больше `min_stages` этапов или
  забирающий больше `budget_share` бюджета дела уходит в пул вопросов (`ask()`,
  варианты `принять`/`урезать`/`остановить`), до ответа дело стоит в `wait_human`.
  Доля считается по цене, которую план назвал сам (`cost.tokens` в предложении), а
  этапные бюджеты — фолбэк: план, который стоит дорого, спрашивает человека, даже
  если его этапы объявлены дешёвыми. Зеро в поле — гейт по этому признаку выключен;
  `min_stages` выше `max_stages` — отказ (такой план отклоняется раньше, чем дойдёт
  до вопроса).

**Что план добавить не может** (`spec.parse_plan`, те же правила, что у `spec check`):
публикующий этап (`role` из `PUBLISHING_ROLES`) и команду `git push` — публикация
объявляется в seed-спеке и требует ревью в предках; этап, который что-то
производит, без `evidence` с командой; `needs`/`parallel_with` на несуществующий
этап и цикл внутри предложения (в том числе замкнутый перестановкой через уже
существующие этапы).

### Что план вправе сказать про этап, который уже есть (1.0)

Запись предложения с `id`, который уже есть в графе, — **не** новый этап, а
**перестановка**: у неё читаются только `needs` и `parallel_with`, и граф дела
получает новые рёбра этого этапа (`transit.graph`, `_relinked`). Любое другое поле
(`role`, `kind`, `evidence`, …) — отказ `plan.id`: этап объявляется спекой, и
переписывать его план не вправе.

    plan:
      stages:
        - {id: check, needs: [plan]}              # check едет перед impl
        - {id: docs, role: documenter, needs: [impl], parallel_with: [impl],
           evidence: [{cmd: "ls docs", must: 0}]}
      cost: {tokens: 40000}                       # цена предложения
      reason: скоуп выяснился по ходу

- **Переставлять можно только неначатый этап.** У этапа, у которого в журнале есть
  попытка (`attempt_started`/`attempt_ended`), перестановка отклоняется правилом
  `plan.reorder` («этап уже начат»): возвращать сделанное в работу вправе приговор
  ревью (`verdict.changes`), а не план. В контракте этапа плана у каждого этапа
  графа есть `started` — лид видит это до отказа, а не после.
- **`parallel_with` план объявляет** — так же, как спека: этап, объявленный
  параллельным готовому, запускается с ним в одном шаге (`transit._batch`), и таких
  этапов в шаге не больше `MAX_PARALLEL` (см. «Два этапа одновременно»).
  Параллель, объявленная планом, не превращается в ожидание: этап seed, ждавший
  план, не получает добавленный этап в `needs`, если тот идёт «вместе с» ним.
- **`cost: {tokens}`** — цена предложения: только она участвует в пороге
  `plan_gate.budget_share`. Не названа — порог считается по этапным бюджетам.
  `tokens` не положительное число или лишний ключ — отказ `plan.cost`.


## Поля этапа

| Поле | По умолчанию | Смысл |
|---|---|---|
| `id` | — (обязательно) | имя этапа, на него ссылаются `needs`/`parallel_with`; уникально. `close` — не просто имя, а закрывающий этап (см. «`close`: дело закрывает лид») |
| `kind` | `agent` | кто исполняет этап: `agent` — процесс профиля `role`, `shell` — команда `cmd`, `gate` — никто: этап спрашивает человека (см. «`kind`: `agent`, `shell` и `gate`») |
| `role` | — (обязательно у `agent`) | профиль Hermes, который исполнит этап |
| `workspace` | `worktree` у этапа с `needs`, `none` у входа | `worktree` — своё дерево от базы этапа (первый этап — `base`, следующий — коммит предшественника); `dir` — каталог дела; `none` — только чтение и приговор |
| `needs` | `[]` | этапы-предшественники: этап начинается, когда они закончены |
| `parallel_with` | `[]` | этапы, которые можно вести одновременно (порядок не задаёт); сразу идут не больше `MAX_PARALLEL` (2) — см. «Два этапа одновременно» |
| `evidence` | `[]` | список `{cmd, must, timeout_sec}`: что движок проверит сам |
| `retry` | `{max: 1, on: [infra]}` | `{max, on}`: сколько раз повторять и на каких классах отказов (`infra`, `contract`, `capability`). Класс без объявления не повторяется; `max: 0` — повторов нет, первый отказ паркует дело (`docs/JOURNAL.md`) |
| `budget` | нет | `{tokens, minutes}`: бюджет одной попытки (у дела — свой потолок, см. «`budget` в корне») |
| `ask` | нет | адрес вопросов: `{allowed, to_human, max_hops}` либо `{q, options, risky}` (у `gate` — только `{q, options}`) |
| `allow` | все `ask.options` | только `kind: gate`: ответы, которые считают этап продолжением; ответ вне списка — отказ `contract` |
| `verdict` | нет | приговор ревью: `{approve, changes, max_rounds}` |
| `cmd` | — (обязательно у `shell`) | только `kind: shell`: команда этапа |
| `must` | `0` | только `kind: shell`: обязательный код возврата команды |
| `artifacts` | `[]` | только `kind: shell`: пути, которые команда обязана предъявить (внутри дерева этапа) |

Значения по умолчанию — часть контракта, а не удобство реализации.

### `kind`: `agent`, `shell` и `gate`

У этапа три вида. `agent` — умолчание и вся прежняя модель: движок поднимает
процесс профиля `role`, попытка отчитывается `result.json`, гейт проверяет
пакет. `shell` — этап-команда: движок запускает `cmd` и судит по коду возврата.
`gate` — этап-вопрос: движок ничего не запускает, задаёт человеку вопрос
`ask.q` с вариантами `ask.options` и ждёт ответа. Спеки 0.0.4 без `kind`
читаются как прежде: умолчание не изменилось.

Что каждый вид принимает и что запрещает — одна матрица (правила печатаются из
`dashboard/spec.py`: `_check_kind`, `_check_shell_kind`, `_check_gate_kind`).
Отказ, а не тихий игнор: объявленное и не прочитанное — ложь спеки.

| поле этапа | `agent` (умолчание) | `shell` | `gate` |
|---|---|---|---|
| `id`, `needs`, `parallel_with` | да | да | да |
| `budget` | потолок попытки | потолок попытки | `budget.minutes` — **срок ответа человека**, в сумму бюджета дела не входит |
| `role` | **обязательно**: без него отказ `role` («профиля нет в Hermes») | отказ `kind.role` | отказ `kind.role` |
| `workspace` | `worktree`/`dir`/`none` | `worktree`/`dir`/`none` | всегда `none`; объявленный `workspace` — отказ `kind.workspace` |
| `cmd` | отказ `kind.cmd` | **обязателен**, иначе `kind.cmd` | отказ `kind.cmd` |
| `must` | отказ `kind.must` | `0` по умолчанию, не целое — `kind.must` | отказ `kind.must` |
| `artifacts` | отказ `kind.artifacts` | `[]` по умолчанию, не пути — `kind.artifacts` | отказ `kind.artifacts` |
| `ask` | `{allowed, to_human, max_hops}` или `{q, options, risky}` | отказ `kind.ask` | **обязателен** `{q, options}`; `ask.allowed`/`ask.to_human`/`ask.max_hops`/`ask.risky` — отказ `kind.ask` |
| `allow` | отказ `kind.allow` | отказ `kind.allow` | `[]` = все `ask.options`; ответ вне `ask.options` — отказ `allow` |
| `verdict` | да (роль ревьюера) | отказ `kind.verdict` | отказ `kind.verdict` |
| `retry` | да, повтор по классу отказа | отказ `kind.retry`: у команды политика повтора — `must` | отказ `kind.retry` |
| `evidence` | да, гейт проверяет пакет | **не проверяется**: предупреждение `kind.evidence`, договор — `must` + `artifacts` | предупреждение `kind.evidence`, договор — вопрос и ответ |
| публикующая команда в `cmd` | — (`cmd` не поле вида) | отказ `cmd.forbidden` (`git push`, `git commit`, `rm -rf`, `sudo`) | — (`cmd` не поле вида) |

```yaml
stages:
  - id: impl
    role: implementer                    # kind: agent — можно не писать

  - id: check
    kind: shell
    cmd: "~/.hermes/hermes-agent/venv/bin/python -m pytest tests/ -q"
    must: 0                              # умолчание: сходилась — это код 0
    artifacts: [report.xml]              # необязательно: что команда предъявляет
    needs: [impl]                        # дерево этапа — как у агента
```

`kind: shell` **не принимает** `role`, `ask`, `verdict`, `retry` — это отказы
(`kind.role`, `kind.ask`, `kind.verdict`, `kind.retry`), а не тихий игнор. Роль у
команды означала бы процесс профиля, которого никто не поднимает; `ask` — вопрос
человеку, которого команда задать не может (вопрос приходит отчётом агента);
`verdict` — приговор, которого некому вынести; `retry` обещал бы повтор класса
отказа, а политика повтора у команды выражена кодом возврата `must`. По той же
причине отказывают поля команды у `agent` (`kind.cmd`, `kind.must`,
`kind.artifacts`): объявленное и не прочитанное — это ложь спеки, а не запас на
будущее. `evidence` у `shell` — **предупреждение** (`kind.evidence`): гейт его не
проверяет, договор команды — `must` и `artifacts`.

**Договор результата — код возврата и артефакты, а не `result.json`:**

| что произошло | исход попытки |
|---|---|
| команда дошла до конца с кодом `must` | `done` |
| код другой | `failed(contract)`, причина «код N, ждали M», хвост stderr — в событии |
| команда не дожила (таймаут этапа, сигнал) | `failed(infra)` — как у агента |
| объявленных `artifacts` нет или путь вне дерева | `failed(contract)`, отказы гейта `artifact.path` / `artifact.missing` / `artifact.sha256` |

Артефакты проверяет тот же `dashboard/evidence.py`, что и пакет агента: путь
относительный и внутри дерева этапа, файл есть, `sha256` — по содержимому. Хеш
считает движок сразу после команды и кладёт пакет в
`attempt_ended.payload.result`; следующий этап читает его тем же способом, что
отчёт агента, поэтому `shell`-этап в цепочке ничем не выделяется.

**Публикующие команды запрещены.** `cmd` проходит ту же проверку
`FORBIDDEN_CMD_PREFIXES`, что `evidence.cmd`: `git push`, `git commit`, `rm -rf`,
`sudo` — отказ `cmd.forbidden`. Решение прямое: публикация — дело роли
`publisher`, и второй путь к ней (командой этапа) сделал бы гейт «публикация
после ревью» обходимым. Этап-команда существует, чтобы **прогонять проверки**, а
не менять мир.

**Окружение** — как у попытки, но без роли и её токенов: команда не действует от
имени профиля, поэтому переменные роли (`HERMES_PROFILE`, `HERMES_ROLE`) и любые
`*_TOKEN*` в неё не передаются. Остальное окружение наследуется — команде этапа
нужны `PATH`, `HOME` и то, чем она собирается.

**`workspace: none` у команды — пустой каталог попытки**, а не репозиторий
(`runner.prepare_tree`: «дерева нет, cwd — сам каталог попытки»): кода и тестов там
нет, и `pytest tests/ -q` падает `rc 4` («file or directory not found»). Команде,
которой нужен код, объявляют `workspace: worktree` — дерево этапа от базы дела.

**Журнал.** Вид этапа не заводит новых событий: попытка пишется теми же
`attempt_started`/`attempt_ended`, но с `source: "shell"` — по нему видно, что
этап исполнила команда, а не профиль. В `attempt_ended.details` едут `cmd`,
`exit_code`, `duration_sec`, `must`, `timed_out`, хвосты `stdout`/`stderr`
(последние 20 строк) и пути полных логов (`.duty/stdout.log`,
`.duty/stderr.log` в каталоге попытки): журнал отвечает «чем кончилось», файл —
«что было написано».

### `kind: gate` — остановка на человеке как этап

Гейт — не парковка и не сбой, а **этап**: он ничего не исполняет, а спрашивает.
Обязательные поля — `ask.q` (текст вопроса) и `ask.options` (варианты ответа):

```yaml
stages:
  - id: impl
    role: implementer

  - id: release
    kind: gate
    ask: {q: "Выкатываем в прод?", options: [да, нет]}
    allow: [да]                          # умолчание — все options
    budget: {minutes: 60}                # умолчание — ASK_TIMEOUT_HOURS
    needs: [impl]

  - id: check
    kind: shell
    cmd: "true"
    needs: [release]
```

- **Процесса нет.** Лизинг не берётся, `attempt_started` не пишется: гейт не
  работает, а ждёт. Факты журнала — `question_asked` (его пишет `ask()`) и один
  `attempt_ended` с исходом по ответу.
- **Дерева нет.** У гейта `workspace` остаётся `none` даже при `needs`: ему
  нечего исполнять и нечего наследовать.
- **`allow`** сужает продолжение до перечисленных вариантов (по умолчанию — все
  `ask.options`). Ответ **вне** `allow` — отказ класса `contract` («ответ вне
  allow», с цитатой ответа), а не продолжение и не повтор.
- **Срок** ответа — `budget.minutes` (умолчание — `ASK_TIMEOUT_HOURS` в
  `dashboard/ask.py`). Истёкший вопрос — это «человек не ответил», и дело
  паркуется с причиной «гейт: человек не ответил за N»; вопрос о том же второй
  раз не задаётся.
- **Чужие поля отказывают**: `role`, `workspace`, `verdict`, `retry`, `cmd`,
  `must` и поля команды у гейта — ошибки валидации (`kind.role`, `kind.workspace`,
  `kind.verdict`, `kind.retry`, `kind.cmd`, `kind.must`), как и `allow` у
  `agent`/`shell` (`kind.allow`). У `ask` гейт берёт **только** `q` и `options`:
  `ask.allowed`, `ask.to_human`, `ask.max_hops` и `ask.risky` отказывают
  (`kind.ask`) — маршрут вопроса и его риск гейт не объявляет, он спрашивает
  человека напрямую. Объявленное и не прочитанное — ложь спеки.
- **Видимость**: ожидание называется `wait_human` с номером вопроса и вариантами
  ответа (`/now`, `bin/duty deal`, `bin/duty why`); парковка гейта не показывает
  «0/0» — класса отказа и счётчика попыток у неё нет.

### Умолчание `workspace`: почему у этапа с предшественником `worktree`

| Этап | Умолчание | Почему |
|---|---|---|
| `needs: []` (вход) | `none` | наименьшее право: этап, который ничего не просил, ничего не меняет; отводить дерево не от чего — база у входа `base`, и её отсутствие законно |
| `needs: [...]` (продолжение) | `worktree` | цепочка «сделал → проверил → принял» иначе неисполнима: проверяющему нужны артефакты предшественника, а они есть только в дереве, отведённом от его коммита. Каталог попытки таких файлов не содержит, и гейт честно отказывает `artifact.missing` |

«Дерева нет» у этапа с предшественником стало **явным** `workspace: none`: молчание
больше не означает «работаю в пустом каталоге». Живой прогон `d_221d021a` (04.11)
сломался ровно на этом: `verify` не объявлял `workspace`, работал в каталоге попытки,
прогнал тесты по скопированному руками дереву и получил отказ гейта на верном отчёте.

Умолчание печатается: `bin/duty spec check` называет дерево каждого этапа и
помечает взятое по умолчанию (`workspace: impl=worktree · verify=worktree (по
умолчанию)`). Явный `workspace: none` у этапа с `needs` и `evidence` — законен, но
получает предупреждение `artifacts-without-tree` (см. ниже): этап, который что-то
прогоняет и предъявляет, без дерева предшественника проверить не на чем.

Без `repo`/`base` этап с предшественником теперь **невалиден** (`workspace`):
умолчание `worktree` требует, чтобы дерево было от чего отвести. Спека, которой
дерево не нужно, говорит `workspace: none` у такого этапа — отказ называет это
прямо («дерево не нужно — укажи workspace: none»).

### База этапа: от чего отводится дерево

`base` верхнего уровня — база **дела**, то есть база только первого этапа. У этапа с
`needs` база другая: это то, что произвёл предшественник (`runner.base_of_stage`,
`dashboard/runner.py`). От этого правила зависит, что вообще увидит исполнитель, поэтому
оно записано в контракт спеки, а не осталось деталью движка:

| этап | база дерева этапа | почему |
|---|---|---|
| `needs: []` (вход) | `base` дела | начинать больше не с чего: дерево отводится от ветки, названной в спеке |
| `needs: [x]`, `x` произвёл коммит | `attempt_ended.payload.commit` последней успешной попытки `x` | принятую работу фиксирует движок (`runner.commit_tree`: `git add -A` + коммит `duty: <дело> <этап> attempt <n>`, detached HEAD), поэтому следующий этап видит ровно принятое, а не «дерево, которое кто-то оставил» |
| `needs: [x]`, `x` ничего не произвёл (`workspace: dir`/`none`) | `base` дела | делиться нечем — это не отказ |
| `needs: [x, y]`, коммиты расходятся (нет общего потомка) | отказ `failed(contract)` с названными sha | дерево от одного молча потеряло бы работу другого |

Живой прогон `d_6e764042` (04.11) показывает правило в журнале: `attempt_started.base`
у `impl` — `8d31ede`, у `verify` и `review` — `abdc475`, то есть коммит, который движок
записал за `impl`. До правки дерево **каждого** этапа отводилось от `spec.base`, и
цепочка `impl → verify` была неисполнима: прогон `d_a2a26b55` получил `verify` на чистом
дереве и отказ `artifact.missing` на файле, который сделал `impl`.

### Два этапа одновременно: `parallel_with` и предел пачки (1.0)

Одновременно движок ведёт только то, что спека **объявила** параллельным: этапы без
`parallel_with` запускаются по одному, иначе слой придумывал бы параллелизм, которого
никто не просил. Объявление одностороннее — `docs.parallel_with: [impl]` и
`impl.parallel_with: [docs]` значат одно и то же.

    stages:
      - {id: impl, role: implementer, workspace: worktree}
      - {id: docs, role: documenter, needs: [impl], parallel_with: [impl]}

- **Шаг запускает пачку.** `transit._batch` берёт первый готовый этап и всех, кто
  объявлен с ним параллельным, а `runner.step` поднимает **все** попытки пачки и только
  потом следит за каждой. Поэтому у каждого этапа свой лизинг, свой процесс и свой факт
  `attempt_started`/`attempt_ended`, а «шаг закрыт» — это столько закрытий, сколько
  попыток в решении.
- **Предел — `MAX_PARALLEL` = 2** (`dashboard/transit.py`, рядом с остальными лимитами
  слоя). Объявленный параллельным третий этап ждёт своей пачки: пачка — это два процесса
  модели и два дерева на один шаг, и предел назван числом, а не надеждой.
- **Лизинг соседа не протухает.** Пока движок читает поток первого процесса, heartbeat
  продлевает и лизинги остальных попыток пачки (`runner.follow(..., others=…)`): живую
  попытку не должен забирать соседний движок только потому, что за ней ещё не смотрят.
- **Падение одной не отменяет вторую.** Попытки уже подняты, и каждая закрывается своим
  фактом; отказ одного этапа останавливает дело решением `transit`, а не убийством соседа.
- **Срез и лента показывают оба.** Две открытые попытки в журнале и есть «два этапа идут»:
  `transit.stage_states` и `stagefeed.stages` отвечают `running` у обоих, а решение
  ждёт их, а не запускает заново.

### `evidence`

```yaml
evidence:
  - {cmd: "go build ./...", must: 0}
  - {cmd: "go test ./widget/...", must: 0, timeout_sec: 600}
```

- `cmd` — непустая строка, команда **доказательства**;
- `must` — целое: обязательный код возврата (`must: true` целым не считается);
- `timeout_sec` — от 1 до 3600 (по умолчанию 3600).

Команда доказательства не может начинаться с `git push`, `git commit`,
`rm -rf`, `sudo`: это действия, а не доказательства. Спека принимает только то,
что проверяется повторным запуском, — поэтому такой `cmd` отказывает **до**
запуска, а не после публикации.

### `ask`

Два вида, оба законны:

```yaml
ask: {allowed: [researcher, planner], to_human: decisions_only, max_hops: 2}
ask: {q: "Публикуем diff?", options: ["пушить", "стоп"], risky: true}
```

- `to_human` ∈ {`decisions_only`, `never`}: властный вопрос идёт в пул, фактовый
  — роли из `allowed`;
- `max_hops` ≥ 0: сколько раз вопрос может уйти по цепочке.

Адрес считает `dashboard/routing.py` — **без модели**, по этим объявлениям и по
разметке самого вопроса в `result.json` (`kind: fact | authority`, `risky: true`,
`default`). Фактовый вопрос уходит роли из `allowed` в порядке объявления;
`risky` — всегда человеку; неразмеченный вопрос считается властным (безопасная
сторона); исчерпанный `max_hops` и пустой/незнакомый `allowed` — человеку (второй
случай с причиной `routing_failed`). Поля `ask.default` в формате нет: значение
объявленного дефолта несёт вопрос, а спека решает, спрашивать ли человека.

**Вопрос, адресованный роли, задаёт движок, а не пул** (`runner.ask_role`): у
такого вопроса нет строки пула, дело не паркуется, а ответ роли — такой же факт
журнала, как ответ человека, только с автором (`question_answered` с `by` и
`hops`). Вопрос пишется фактом **до** спавна: пока роль отвечает, дело стоит в
`wait_human` с ожиданием вопроса — отдельного вида ожидания нет. Ответ роли —
вход **новой** попытки того же этапа (`answer_this_attempt`), а не продолжение
упавшей.

- `authority: true` в ответе роли — «это не мне решать»: тот же вопрос уходит
  человеку через пул с причиной `role_redirected`;
- упавшая попытка ответа (`infra`/`contract`: роль не поднялась, не ответила за
  срок, отчёт без `answer.text`) вопрос не сжигает — он идёт человеку с причиной
  `role_answer_failed` и текстом отказа в `reason`;
- исчерпанный `max_hops` человека не обходит: проверка стоит в `routing.route`
  до спавна, поэтому второй вопрос идёт человеку с причиной `hops_exhausted`
  вовсе без роли;
- властный или неразмеченный вопрос роли не задаётся никогда: разметка вопроса
  сильнее объявленного `allowed`.

Ответ роли приходит одним вызовом движка, поэтому открытый вопрос роли в журнале
означает, что движка, который его задал, уже нет. Такой вопрос тоже не сгорает:
проход `runner.recover_role_questions` (в драйвере — перед каждым решением, сразу
после ответов пула) закрывает передачу фактом `question_answered` с
`answered_via='failed'` и уводит тот же вопрос человеку с причиной
`role_answer_failed`; строка `! вопрос роли: …` в выводе и ключ `recovered` в
`--json` называют этап, попытку, роль и номер вопроса в пуле. Переадресованный
(`redirected`) и проваленный (`failed`) вопрос ждёт **человека**, а не срок:
`transit` читает пустой `answer_len` как `expired` только у ответа человека.

Контракт отвечающей роли — не контракт попытки: `question` (текст вопроса),
`asked` (отчёт спросившей попытки — `summary` и её `result.json` целиком) и
`answer_report` со схемой `{answer: {text, authority}}` при пустом
`evidence_to_produce`: роль ничего не сдаёт, она отвечает. Рабочий каталог
ответа — `<каталог попытки>/ask`.

### `verdict`

```yaml
verdict: {approve: next, changes: impl, max_rounds: 2}
```

- `approve` — `next` или `id` существующего этапа;
- `changes` — **обязательно предшественник** (транзитивно по `needs`); иначе
  возврат на доработку перескочил бы проверку, и такая спека не запускается;
- `max_rounds` ≥ 1.

**Приговор пишется отчётом, а не словом.** У этапа с `verdict` в `report_schema`
появляется поле `verdict: {action, target, reason}`: `action` — `approve` или
`changes`, `target` — `next`, `id` этапа или пустая строка (по умолчанию:
`approve` → `next`, `changes` → `verdict.changes` спеки), `reason` — одна строка
«почему». По этому полю движок (`runner.report_verdict`) в той же транзакции, что и
`attempt_ended`, пишет **факт уровня этапа** — `collected` при `approve`,
`changes_requested` при `changes`, payload `{stage, target, reason, attempt}`.
Без этого факта следующий этап не двигается: правило 2 гейта ждёт приговор, а
`attempt_ended` им не является. Отказ класса `contract` (а не тишина) — у `done` без
поля `verdict`, у неизвестного `action`, у `target`, которого нет в спеке
(`file:line` спеки в причине), и у возврата сверх `max_rounds`.

Гейт «публикация не обгоняет ревью» — правило `review-gate`: этап, чья `role`
входит в набор публикующих (`publisher`, `deployer`) или у которого
`ask.risky: true`, обязан иметь в транзитивных `needs` этап с `role: reviewer`.
`verdict.changes` бережёт возврат на доработку, `review-gate` — сам приговор
между реализацией и публикацией: «PUB после RV, а не после IMP» проверяется до
запуска, а не выводится из кода. Список публикующих ролей — одна константа
(`PUBLISHING_ROLES` в `dashboard/spec.py`).

Гейт «публикация спрашивает человека» — правило `publish-gate` (0.0.5): у этапа с
ролью из `PUBLISHING_ROLES` в транзитивных `needs` обязан быть этап `kind: gate`,
и у него обязан быть **объявлен** `allow` с утвердительным вариантом. Без `allow`
продолжением считается любой ответ из `ask.options` (`runner.gate_allow`) —
включая «не публиковать», и публикация поехала бы на отказе человека.

Гейт перед публикацией — не отдельный вид этапа и не `ask.risky`: он ставится
между ревью и `publisher` обычным этапом `kind: gate`, а его вопрос несёт то, что
иначе человек искал бы руками, — короткий `commit` (база публикующего этапа, то
есть ровно то, что уйдёт в origin), `git show --stat` этого коммита, путь к
`result.json` ревьюера-предка и его вердикт словами (`runner.publish_facts`).

Публикует роль, а не движок: `git push` в `cmd`/`evidence` — отказ
`evidence.forbidden`, у публикации нет второго пути мимо этапа. Движок делает две
проверки (правило живёт в `dashboard/publish.py`, без git и без часов):

1. **до спавна** — гейт-предок задал вопрос человеку, человек ответил вариантом из
   `allow`, и с момента **вопроса** дерево не менялось. Иначе отказ класса
   `contract`: «одобрен commit X, в дереве Y»;
2. **после отчёта** — заявка `published: {sha, branch, mr_url}` сверяется с origin
   через `git ls-remote` **по префиксу** (сокращённый sha законен, пока однозначен;
   в событии `published` `sha` — полный из `ls-remote`, заявка рядом в `claimed_sha`).
   Нет заявленного sha в origin — `contract` «публикация заявлена, но не найдена»;
   sha подходит к нескольким коммитам — `contract` «подходит к нескольким ссылкам»;
   sha есть, но не равен одобренному — «ушло не то дерево». Подтверждённый факт
   пишется событием `published`.

Одобренный коммит фиксируется в момент **вопроса** (`question_asked.payload.routing.
approved_commit`), а не ответа: ответ приходит позже, и к этому времени дерево уже
могло измениться. Ответ «не публиковать» — решение, а не сбой: гейт закрывает дело
причиной `человек не дал ок`, и публикующий этап не поднимается вовсе.

`retry.on: [capability]` — **предупреждение**, а не отказ: `capability` обычно не
рассасывается повтором; если это осознанно — оставь как есть (движок решает по
политике, валидатор осознанный выбор не запрещает).

### `close`: дело закрывает лид (1.0)

```yaml
  - id: close
    role: lead
    needs: [review, docs]
    workspace: none
    verdict: {approve: next, changes: impl, max_rounds: 1}
```

Этап с `id: close` — не обычный этап, а **закрывающий** (константа
`spec.CLOSE_STAGE`): дело закрывает лид, и закрытие — его приговор, а не
пройденный граф и не код возврата команды (`docs/ENGINE-1.0.md`, разделы 9 и 10).
Три правила, и все — отказы `spec check` до запуска, а не в момент закрытия:

- `close.role` — роль обязана быть `lead` (`spec.CLOSE_ROLE`). Хартия
  `allowed_roles` этого не расширяет: `close` объявляется в seed-спеке, планом его
  не добавляют;
- `close.kind` — вид только `agent`: у команды (`shell`) договор — `must`, у гейта
  (`gate`) — ответ человека, приговора нет ни у того, ни у другого;
- `close.verdict` — приговор объявлен: без него этап «просто закончится», и дело
  останется `running` при формально пройденном графе.

Отчёт этапа — обычный: `summary` (итог дела словами лида) плюс уже знакомое поле
`verdict: {action, target, reason}`. `approve: next` значит «дело закрыто»:
`transit` отвечает `done`, и писатель закрытия (`driver._closure` в прогоне,
`release._closed` в проходе отпускания) пишет `completed` с `cause='lead_closed'` и
`summary` лида из `result.json` — итог дела, а не текст движка. `changes: <этап>`
возвращает дело на названный этап того же графа: дело не закрыто, работа
начинается заново. «Все этапы пройдены» дело с `close` не закрывает —
`deals.close_stages_done` с `cause='all_stages_done'` поверх такого графа
отказывает (`DealError`), а граф для этого решения берётся из журнала, где есть и
этапы, добавленные принятым планом.

## Контракт попытки: что этап получает и куда пишет

Спека описывает работу, а попытке нужен ещё и вход. Он приходит **файлом**, а не прозой
в командной строке: `<workdir>/.duty/in-<этап>-<попытка>.json`, который движок пишет до
спавна и передаёт процессу через `--query-file` (`runner.build_contract`,
`runner.write_contract`; каталог попытки — `~/.hermes/kanban/boards/<board>/workspaces/<дело>-<этап>-<n>`).

| поле контракта | смысл |
|---|---|
| `deal`, `stage`, `attempt`, `role` | что за работа, какой этап, какая попытка и под каким профилем |
| `workdir`, `tree` | каталог попытки и дерево, если этап его просил (`null` у `workspace: none`) |
| `goal` | заголовок дела плюс его тело — формулировка работы, а не пересказ спеки |
| `boundaries` | границы словами: куда можно писать, где отчёт, чем пишется отчёт, как размечать вопрос |
| `previous[]` | отчёты предшественников: `commit`, `artifacts[]`, `summary`, `verdict` |
| `evidence_to_produce` | объявленные в спеке команды и обязательные коды |
| `report_schema` | схема отчёта (`evidence.report_schema`): исполнитель видит требования до работы, а не узнаёт их из отказа |
| `questions` | адрес вопросов: `allowed`, `to_human`, `max_hops`, `risky`, `default` |
| `report_to` | **файл отчёта**: `<workdir>/.duty/result.json` (`runner.result_path`) |
| `deadline_sec` | бюджет времени попытки в секундах |
| `answer_this_attempt` | только у попытки, поднятой после ответа: человека (строка пула) или роли (текст из журнала — у вопроса роли пула нет) |
| `session_id` | id сессии, если попытка продолжает уже начатую (`--resume`) |

### Свидетель этапа: чем «готово» доказывается

`status: done` принимается только вместе со **свидетелем** — тем, что этап по своей
природе может предъявить. Одно требование на все виды было внутренне противоречиво:
от `publish` и `review` оно требовало дерева, которого те не меняют, и отказывало
каждой честной попытке (живой прогон TF3-c: `publish · failed(contract)`,
`result.json:artifacts: required: status: done без commit и без artifacts`).

Свидетеля выбирает одна функция — `evidence.witness(stage)`; по ней же строится
`report_schema.required_for_done`, чтобы контракт и гейт требовали одного и того же.

| вид этапа | свидетель | что принимается |
|---|---|---|
| `agent`/`shell` без `verdict` и без публикующей роли | `commit\|artifacts` | коммит (резолвится в дереве и не предок базы) или список артефактов с полным `sha256` |
| этап с `verdict` в спеке (ревьюер) | `verdict` | `verdict: {action, target, reason}` — приговор, по которому движок пишет факт графа (`runner.report_verdict`) |
| публикующий этап: `role` из `spec.PUBLISHING_ROLES` | `published` | `published: {sha, branch}`, который движок сверяет с origin (`runner.published_claim`, `git ls-remote`) — строже дерева |

Признаки берутся у самой спеки, новых флагов нет: «публикует» — та же константа
`PUBLISHING_ROLES`, что у валидатора и движка; «выносит приговор» — наличие
`verdict`. Хотя бы один свидетель обязателен: `done` без свидетеля своего вида —
отказ `contract`, и он называет, что принимается **у этого** этапа («этап
публикации: нужен published {sha, branch}; commit/artifacts не требуются»). Гейт не
ослаблен и остальным: обычный этап без `commit|artifacts` отказывает прежним
текстом, `done` без `summary` и без `evidence` — тоже; `blocked`/`refused` пакета
не предъявляют и свидетеля не требуют.

`kind: gate` через эту проверку не проходит вовсе: у вопроса человеку нет отчёта
исполнителя, его факты пишет движок (`runner.run_gate_stage`).

### Отчёт — файл, а не текст в ответе

`report_to` — единственный адрес, по которому движок ищет результат. Отчёт пишется
инструментом `write_file` (валидный JSON по `report_schema`); текст в ответе модели
движок не читает — `runner.read_result` открывает ровно `result.json` и различает «файла
нет», «не читается», «не разбирается» и «не объект» словами, а не молчанием. Нет отчёта —
`attempt_ended` с `outcome=failed`, `kind=contract` и причиной `result.json нет: <путь>`.
Поэтому контракт говорит это исполнителю дважды — в `boundaries` и полем `report_schema`:
схема, о которой узнают только из отказа, — не контракт, а ловушка.

### Право записи: read-only роль пишет только отчёт

У профиля с read-only ролью (`READONLY` в guard: `lead`, `researcher`, `reviewer`, `ops`)
единственная разрешённая запись — этот файл. Guard `role-access`
(`~/.hermes/plugins/role-access/__init__.py`) пропускает `write_file`/`patch` только
тогда, когда сходится вся связка: сессия называет этап, номер и каталог; движок записал
этот же контракт в `<workdir>/.duty/in-<этап>-<n>.json`; в файле совпадают роль, этап,
номер, `workdir`; `report_to` — ровно `<workdir>/.duty/result.json`; каталог попытки лежит
под `~/.hermes/kanban/boards/**`. Любое расхождение — отказ
`role-access: роль read-only; разрешена запись только отчёта попытки: <путь>`; без
контракта — `…но контракта попытки с report_to у сессии нет`. Репозиторий, `tree/` и
`.git` для read-only роли закрыты на запись при любом контракте. Права ролей целиком —
`docs/PROBES.md`, раздел «Права ролей: что можно роли и что режет `role-access`».

Живой прогон `d_6e764042` (04.11): у попытки `review#1` (роль `reviewer`) в журнале
`attempt_progress` только `search_files` (14), `read_file` (10) и `write_file` (1) — ни
одного `terminal`; на диске после неё остался отчёт
`…/d_6e764042-review-1/.duty/result.json`, по которому гейт и принял этап.

Каждое правило — отдельный тест в `tests/test_spec.py`. Отказ печатается как

`capability` и `artifacts-without-tree` — этап с `needs`, `workspace: none` и
`evidence` с командами (`none` бывает осознанным: этап только спрашивает человека,
и это остаётся его правом).

### Профили роли

Список профилей — снимок каталога `~/.hermes/profiles/*` плюс `default`, один
раз на процесс (`known_profiles()`). `hermes profiles list` не вызывается:
проверка спеки не должна стоить процесса, а ответ CLI — не контракт каталога.
Профиль существует, если существует его папка; `default` есть всегда.

Корень каталога — `$HERMES_HOME/profiles` (на Windows home Hermes вне `~`). Если
сам `HERMES_HOME` — профиль (`<root>/profiles/<role>`, как в профильной оболочке),
каталог профилей лежит на уровень выше: иначе `$HERMES_HOME/profiles` не
существует, и спека с ролями отказывала «профиля нет в Hermes», хотя профили есть.

### `base` и машина, на которой нет репозитория

`base` проверяется через `git rev-parse --verify --quiet <base>^{commit}` в
`repo` — это единственное место слоя, которому нужен процесс, поэтому оно живёт
отдельной функцией `check_base()` с подставляемой проверкой rev.

Если репозитория дела на этой машине нет (спека лежит в `~/.hermes`, дерево — в
рабочем каталоге), это **предупреждение** (`severity: warning`), а не отказ:
спека годна, а факт «base резолвится» проверяется там, где дерево есть.
Предупреждение печатается и при `OK`.

## Адресация дела (0.0.6)

Дело называется **своим id** — `d_<hex>`, и ничем больше: досок в duty нет, сегмента доски в
адресах не осталось. Группировка дел — по `repo` из спеки дела (`repo:`, см. «Поля верхнего
уровня»); дело без `repo` попадает в группу «без репозитория», и это законное состояние,
а не ошибка.

Подпись репозитория в **списках** — последний сегмент пути (`payout-sx-widgets-api`):
абсолютный путь в заголовке группы читается как шум, а имя ищут глазами. Полный путь
остаётся в `repo` (по нему фильтруют и группируют) и в подсказке заголовка, а на
**странице дела** стоит целиком — там человек смотрит одно дело, и адрес репозитория
для него факт. Колонки списка заданы долями (`NOW_COLS`/`FINISHED_COLS`): у каждого
репозитория своя таблица, и без явных ширин браузер считает их по содержимому —
колонки групп съезжали друг относительно друга (09.11).

```
GET /deal/{deal_id}                 карточка дела
GET /duty/{deal_id}/attempts        таймлайн попыток
GET /now?repo=<path>                дела сейчас, фильтр по репозиторию
GET /deals?status=done,archived&repo=&limit=<N>&cursor=<at>:<id>  завершённые дела (0.0.7; курсор и `repos` — 0.0.9)
GET /spans?ids=<id>,<id>             границы этапов нарисованных дорожек (0.0.9)
GET /stats?repo=<path>              здоровье, фильтр по репозиторию
```

### Экран «Дела»: одна страница вместо трёх (0.0.9)

Вкладки «Сейчас», «Завершённые» и «Дело» — одна страница. Причина: «Сейчас» и
«Дело» без выбранного дела показывали одно и то же (список), а «Завершённые»
требовали переключения ради справки. Страница сверху вниз:

1. **поиск** — единственный фильтр (id, заголовок, исполнитель, этап). Чипы
   состояний и селект репозитория убраны: состояние и репозиторий видны в строках
   и группировке, а «где это дело» закрывает поиск;
2. **мини-таймлайн дел** — «сосиска» на дело: активные тянутся до `now`,
   завершённые — до своего `finished_at` (09.11, Макс: «показывать и
   завершённые»). Окно выбрает человек: в шапке таймлайна стоят пресеты
   `1ч / 3ч / 12ч / 1д / 7д` (по умолчанию сутки) и поле ввода, которое понимает
   `45m`, `12h`, `2d`, `90 мин`, `1 день` и голое число как часы. Границы ввода —
   от 5 минут до 30 суток; непонятный ввод не применяется (поле краснеет, окно
   остаётся прежним) — молча подставлять своё значение нельзя, иначе человек
   читает не тот период, который выбрал. Выбор переживает перезагрузку
   (`localStorage: duty:tlWindow`). Ось строится по фактическим делам (пустые часы
   слева растянули бы сосиски в нитки), но левая граница никогда не уходит
   дальше `now − окно`. Дело, начавшееся раньше окна, не пропадает:
   сосиска начинается у левого края, её левый конец срезан (`clipped`); дело без
   записанного начала рисуется полупрозрачной сосиской (`exact: false`). Потолок
   строк — `TL_MAX_ROWS = 14`, остальное названо числом («ещё N не показано»).
   Геометрия — `dealTimeline` из шейпера: веб и десктоп рисуют одну картину.
   Мини-таймлайн есть **на обеих поверхностях**: веб рисует его на «Сейчас» над
   списком, десктоп — там же, над группами дел (`DutyMiniTimeline`), с той же
   сеткой, шкалой и правилом клика;

   **Одна сетка, тела дел поверх.** Сетка — отдельный слой под всеми делами:
   вертикали общие, у строки нет ни своей рамки, ни своего фона, ни своей сетки
   (09.11, Макс: «у нас должен быть нарисован общая сетка, на которой дела
   появляются едиными сосисками»). Дело — одна фигура на этой решётке: одно
   небольшое скругление (3 px) на всю сосиску, этапы внутри стыкуются вплотную
   (скругление держат крайние этапы: тело дела не обрезает своих детей, иначе
   внешнее свечение срезалось бы по краю), и
   границей этапа служит только цвет — отдельных капсул у этапов нет (09.11,
   Макс: «сосиску ты конечно слишком закруглил»). Шаг делений выбирается по длине
   окна: 5 минут на часе, 15 минут на трёх, 30 минут на шести, час до суток,
   6 часов на трёх сутках, 12 часов на неделе и сутки дальше — суточное окно с
   шагом в три часа не отвечало на «когда это было», а недельное с часовым
   превращалось в частокол. На окнах длиннее суток отсчёт идёт от местной
   полуночи, и полночь подписана датой, а не временем.
   Подписи стоят в тех же колонках, что и дорожки, и центрируются на своём
   делении, поэтому время не съезжает относительно сетки. Линия «сейчас» — правый край
   сетки;

   **Этапы внутри сосиски.** Полосы берутся из журнала (`GET /spans`, пара
   `attempt_started` ↔ `attempt_ended`) и считаются в долях сосиски, а не оси:
   этап не может вылезти за тело дела. **Заливка полосы — роль этапа**
   (`stageRole`): планировщик фиолетовый, имплементер синий, документатор
   бирюзовый, тестер оранжевый, ревьюер розовый, публикатор зелёный, всё
   незнакомое — серое. Соответствие постоянное и общее для обеих поверхностей:
   имплементер всегда один цвет, ревьюер всегда другой, в любом деле и в любой
   теме (09.11, Макс: «настрой соответствия: имплементер — всегда один цвет,
   ревьюер — другой»). Роль, а не порядковый слот: `impl_core`, `implement`,
   `code` — одна краска, потому что это одна работа.
   **Состояние этапа — штрихование, а не краска.** Пройденный этап своей отметки
   не имеет: он виден цветом роли и местом на шкале. Отказ — красное диагональное
   штрихование поверх цвета роли (09.11, Макс: «уберем подсветку по краям,
   сделаем штрихование красным в случае неудачного этапа»): роль остаётся
   узнаваемой, а «здесь упало» читается рисунком, а не вторым оттенком. Края
   этапов не подсвечиваются вовсе — ни внутрь, ни наружу.
   **Пульс — у дела, а не у этапа**: вокруг всей сосиски дела, которое ещё идёт
   (`is-live`, 2.8 с), мягкий ореол акцентом — «идёт прямо сейчас» относится к
   делу, а какой именно этап работает, видно по правому краю полосы. При
   `prefers-reduced-motion` пульс заменяется ровным ореолом: состояние не должно
   пропадать вместе с движением. Пустое место внутри сосиски — пауза между
   попытками (факт, а не дефект рисунка). Под таймлайном — легенда: у отказа
   образец штрихованный, у «в работе» — пульсирующий, как у самого дела.

   **Сжатый простой на оси.** Пустое время между этапами сжимается (порог —
   и по длительности, и по доле оси), иначе дело с четырёхчасовой паузой
   выглядит двумя тонкими полосками по краям. Сжатие нарисовано как разрыв
   шкалы, а не как дыра в данных: промежуток занимает 5 % оси (все вместе — не
   больше 24 %), залит диагональной штриховкой, гаснущей к краям, а посередине — пилюля со
   временем (`≈ 4,8 ч`; 1 ч 20 м показывается как «1,3 ч», минуты — как «45
   мин»). Пилюля ставится только если промежуток её вмещает — на узком срезе
   остаются штриховка и подсказка. Подсказка называет границы, точное время и
   где простой стоит: «до старта», «между этапами», «после финиша» (09.11, Макс:
   «давай его как-то получше рисовать, чтобы было понятно, что таймлайн тут
   схлопывается»). Двойные наклонные засечки по границам промежутка убраны: крупные и
   грязные, штриховка справляется одна (09.11, Макс). Без границ (журнал не ответил) сосиска
   заливается нейтрально-серым;

   **Что нажимается.** Дело и его название — ссылки; длительность, состояние и
   подпись проекта — показания, а не кнопки (09.11, Макс: «кликабельным должно
   быть только дело на таймлайне и его название — не вся строка»). Курсор
   `pointer` только у сосиски, строка не подсвечивается на наведении;

   **Подписи.** Проект — мелко и тихо (хвост пути), заголовок дела — крупно; в
   подсказке полное название, id, полный путь, состояние, длительность и разбор
   по этапам («impl 30 мин · review 1 ч»);
3. **строки дел по репозиториям** — как были: id, заголовок, исполнитель, этап,
   попытка, лизинг, действие, состояние. Идущий этап подсвечен акцентом и точкой;
   исполнитель — `assignee` дела, а если он не записан, роль текущего этапа
   (44 из 53 дел на 09.11 созданы без `--assignee`, и пустая колонка читалась
   как «никто»);
4. **завершённые** — блок в подвале экрана «Сейчас» на **обеих** поверхностях:
   отдельной вкладки на десктопе больше нет (09.11, Макс: «так же как и на вебе
   убираем отдельную страницу»). Вкладок на десктопе осталось три — «Сейчас»,
   «Почему стоит», «Здоровье»: «Дело» открывается кликом по делу, как и на вебе
   (09.11, Макс: «есть вкладка "Дело", которую мы убирали с веба»). **Сворачивания нет** — блок всегда раскрыт, по
   пятёрке на проект он занимает немного места; шапка блока — обычный заголовок
   панели с числом «N из M» и подписью «по 5 на проект».
   **Листается по проектам**: индекс (`/deals?limit=1`) называет, сколько закрытых
   дел у каждого репозитория (`repos[].total`), и на проект показываются первые
   пять. Кнопка «ещё 5 · осталось N» стоит **по центру под таблицей группы** — там, где
   появятся новые строки, а не в шапке, и выделена акцентной рамкой: это
   единственный способ получить следующие строки (09.11, Макс: «в центре и
   позаметнее»). Ответ без `repos` (бэкенд ещё поднимается) и ответ с `errors`
   (store не прочитался) — не «завершённых дел нет»: страница пробует трижды, а
   потом показывает причину в баннере — пустой список не должен врать про факт.
   На десктопе история читается одним запросом (`/deals?limit=200`) и делится по
   `repo` в памяти: ключ `repos` появился только в 0.0.9, а живой бэкенд может
   держать прежний модуль, и тогда постраничный список проектов собрать не из
   чего. Листание по пятёрке — тоже в памяти, без сети. Кнопка в подвале тянет по пятёрке во всех группах сразу. Пока идёт подгрузка, после показанных строк стоят скелетоны той
   же геометрии и держатся минимум `SKELETON_MIN_MS = 260` мс (локальный ответ
   приходит быстрее глаза, и без этого «разворачивание» не увидеть). Смещения нет: курсор — ключ
   `finished_at:id`, поэтому новое закрытие не сдвигает окно и не повторяет
   строку, а группы не мешают друг другу. Группа с одним закрытым делом сразу
   говорит «всё». Вход групп играет **один раз** — на первом кадре с данными;
   дальше блок меняется на месте (morph переиспользует строки по `data-key`), и
   подгрузка показывает скелетоны, а не перерисовывает весь список: раньше каждое
   «ещё» моргало всем блоком (09.11, Макс). При `prefers-reduced-motion` анимации
   выключены. Ошибка одной группы остаётся в её шапке и не гасит остальные.

### `GET /spans` — границы этапов для нарисованных сосисок (0.0.9)

`?ids=d_a,d_b,…` (до `SPAN_MAX_DEALS = 40`) — одним запросом на все сосиски:
запрос на дело превратил бы верхушку страницы в 14 запросов. Ответ —
`{"now": …, "spans": {"d_a": [{stage, role, attempt, start, end, outcome, kind}]},
"missing": [...]}`. Пара ищется по `run_id`; конец без начала пропускается,
незакрытая попытка едет с `end: null` (поверхность тянет её до `now` сама —
«кончилась сейчас» было бы догадкой). `missing` называет дела, которых в store
нет: пустая дорожка не должна выглядеть как «дел не было».

`#/deals` больше не вкладка, но остался адресом: он открывает ту же страницу с
раскрытым блоком завершённых. `#/deal/<id>` — страница дела, как и было.

### Завершённые: курсорная пагинация (0.0.9)

`GET /deals?cursor=<finished_at>:<id>` отдаёт дела **строго после** названного
ключа (`-finished_at, id` — тот же порядок, в котором список отсортирован), а
`next_cursor` в ответе называет ключ последней строки страницы; `null` — страница
последняя. Смещение (`offset`) не заводится намеренно: список живёт во времени, и
новое закрытие между запросами сдвинуло бы окно — страница «2» по смещению
показала бы повтор или пропуск. `total` остаётся числом дел под фильтром целиком,
поэтому «20 из 52» читается как «страница, а не весь список». Кривой курсор — 400
с форматом, а не пустая страница.

### Таймлайн попыток: вызовы инструментов (0.0.8)

`GET /duty/{deal_id}/attempts` отдаёт попытку не только числами (`progress`,
`tools`), но и **списком вызовов**: без него экран «Дело» может нарисовать полосу
попытки, но не может ответить, что она делала.

| поле попытки | что это | источник в журнале |
|---|---|---|
| `calls[]` | вызовы инструментов по порядку: `{seq, name, at, ms}` | пара `attempt_progress` с `phase=tool_use` ↔ `phase=tool_result` того же `(stage, attempt)` |
| `calls[].at` | начало вызова: `ts` результата минус `duration_ms` | у `tool_use` длительности нет — она приходит только с результатом |
| `calls[].ms` | длительность в миллисекундах, `null` — результат не пришёл | `duration_ms` результата |
| `calls_omitted` | сколько вызовов не поместилось под потолок `MAX_CALLS=800` | `dashboard/stagefeed.py` |

Три правила, которые нельзя «улучшить» молча:

- **Пара ищется по имени, а не по соседству.** У событий прогресса нет `run_id`,
  поэтому склейка идёт по `(stage, attempt)` и ближайшему незакрытому вызову с тем
  же `name`; повтор имени подряд (`read_file` дважды) не склеивает их крест-накрест.
- **`ms: null` — это факт**, а не ноль: попытка оборвалась посреди вызова.
  Показывать `0 мс` значило бы утверждать, что вызов мгновенный.
- **Потолок называется числом** (`calls_omitted`), а не прячется: обрезанный
  список без этой цифры читался бы как «столько и было». На экране подпись
  попытки называет **суммарное число вызовов** (`показано + calls_omitted`, с
  выделением, если часть не нарисована) и `(показано N)` в сводке дорожки;
  тултип называет причину словами. Сколько чипов легло друг на друга из-за
  нехватки уровней раскладки — свойство рисунка, а не работы: на экран это
  число не выносится (09.11, было `⋯M` — Макс: «мне эта информация зачем»).
- **Фазы вне `tool_use`/`tool_result` вызовов не описывают.** `attempt_progress`
  пишет и `thinking`/`message`; считать их результатом значило бы съедать
  открытый вызов и рисовать несуществующий. Результат, чьего имени нет среди
  открытых, — сирота: он получает своё имя и посчитанное начало, а не забирает
  чужой вызов.

**Масштаб оси заморожен на «вьюпорт = час»** (09.11, Макс: «максимальную ширину
таймлайна в час. если больше сделай просто стильную горизонтальную прокрутку,
пока мы должны висеть на правой границе»). `axis.zoom` — ширина дорожки в
экранах (`spanSec/3600`, минимум 1); при `zoom > 1` колонка шкалы получает
`overflow-x: auto`, дорожки растягиваются до `zoom × 100%`, подписи попыток
прилипают к левому краю (`position: sticky`), скроллбар тонкий и тематический.
Прокрутка живая: пока человек не уехал влево сам, каждый тик дожимает скролл к
правой свежей кромке; уехал — шкала ждёт, вернулся к краю — снова висит на
«сейчас». Обе поверхности (веб и десктоп), арифметика — `axis.zoom` в шейпере.

**Центр палки — точно на своём моменте** (09.11, Макс: «центр палочки должен
быть точно на таймлайне»). Прежние сдвиги якорей (вывод — перед моментом,
вопрос — после) оставляли щели: из под палок выглядывала кромка полосы. Все
палки, включая `anchor-start`/`anchor-end`, центрируются (`translateX(-50%)`);
`anchor` остался семантикой события, на геометрию больше не влияет.

**Палитра инструментов: интеграции и служебные не серые** (09.11, Макс: «ща
много серого»). Серый — только «не знаю» (`other`): добавлены два семейства —
`mcp` («интеграции»: коннекторы `mcp__…`, jira/gitlab/confluence/goland) и
`meta` («служебные»: поиск и разбор инструментов, состояние сессии). Тона —
teal и pink, на обеих поверхностях; в легенде семь строк.

**Ширина чипа: свёрнутая строка — линейная, развёрнутая — логарифм.** В нахлёсте
уровней нет, и плотность цвета — единственная правда строки: линейная ширина
(`widthLinPct` — доля дорожки между началом и концом вызова на карте оси) читается
как реальное время, потраченное на вызов (Макс, 09.11: «в свернутом виде рисовать
тулы линейно»). При развороте строка возвращается к логарифму
(`3 + 11·log₁₀(1 + ms/100)/log₁₀(1 + 12000/100)`): линейная посадка превратила бы
136 мс в точку. Переключение — CSS-переменными `--w-lin`/`--w-log` на чипе.

**Чипы вызовов без рамки; свёрнутая строка — нахлёст** (09.11, Макс: «уберем
границу, а в свернутом виде будем рисовать все квадратики с наложением…
прозрачностью»). Рамка `inset` снята: перекрытие читается плотностью цвета. В
свёрнутой строке все чипы — на одной линии (`top: 0`), вполсилы (45 %):
глубокие уровни не прячутся, а лежат поверх — плотность работы, и тик не
перерисовывает квадратики заново. Наведение раскрывает строку, чипы доезжают
на свои уровни; живой (незавершённый) вызов и выбранный — в полную силу.

**Появление, уход и переезд анимированы** (09.11, Макс: «этапы
удалять/обновлять/добавлять с анимацией… плавное расширение таймлайна»). Тик
приходит раз в 5 с; без движения шкала дёргалась бы на каждом тике. Движение
отдано CSS, поверхностям остаётся не терять узлы: веб патчится на месте
(`morph`), свежие узлы помечаются `is-new` (вход), ушедшие доигрывают
схлопывание `is-gone` (высота замораживается инлайном, класс гасит её), а
перестановка дорожек доезжает FLIP-сдвигом (`flipBefore`/`flipPlay` в
`patchDeal`). Десктоп — React: чипы keyed id вызова (а не позицией), метки
оси — моментом времени, ушедшие этапы блока «этапы» держатся снимком с
`is-leaving` 380 мс. Ключи устойчивые: метка оси ключуется моментом (`at` из
шейпера), а не процентом — при расширении оси она доезжает, а не считается
новой. `prefers-reduced-motion` гасит всё: движение — украшение, не содержание.

**Дорожки шкалы — в порядке работы** (09.11, Макс: «располагай на шкале
времени этапы в порядке их работы, как на графе спеки»). Дорожка этапа встаёт
по моменту его первой попытки, а не по порядку перечисления в спеке;
параллельные этапы с равным стартом и никогда не работавшие — в порядке графа.
Дорожек столько же, сколько этапов: «ещё не начинался» остаётся видимым фактом.

**Числа попытки — подробностями в блоке «этапы», не значком на шкале** (09.11,
Макс: «эту стату писать в подробностях в блоке ЭТАПЫ только»). В гуттере
шкалы значок «136 вызовов · 11 646 133 токена» не влезал и обрезался. Теперь
раскрытая попытка в «этапах» несёт строку подробностей: вызовы (показанные
плюс отрезанные потолком), фразы, токены, шаги, код выхода, pid —
`compactAttemptView.statsText`; усечение потолком жёлтым, с точным числом в
подсказке (`statsNote`). Слияние записи этапа с лентой дела — общее
`stageColumnBars` в модели: лента приходит и шейпнутой, и сырой (`run_id`), и
не узнав вторую форму, слияние молча теряло вызовы. Значка на строке шкалы
больше нет.

Геометрия таймлайна (ширина чипа по логарифму длительности, раскладка по уровням)
и **вид** строки (`attemptView`, `laneView`: подпись, склонения) считаются
шейпером `desktop/model.js` — одним на веб и десктоп. Поверхности только рисуют: разъехавшиеся формулы дали бы два несравнимых
рисунка одного дела. Свёрнутая строка попытки — 20 px, раскрытие — CSS по
`:hover`/`:focus-within`, высота приходит переменной `--tl-full`.

Старый адрес с доской (`/deal/<board>/<id>`, `#/deal/<board>/<id>`) — **отказ с объяснением**,
а не алиас: два способа назвать одно дело дают две правды. Фильтр `?board=` отвечает `400` с
подсказкой про `?repo=`. В CLI то же: `bin/duty create` принимает `--repo` и не принимает
`--board`; остальные команды берут только `<deal_id>`.

Неизвестный `?repo=` — это фильтр, а не ресурс: `/now`, `/deals` и `/stats` отвечают `200` с пустым
результатом (а не `404`), потому что репозиторий — свойство дела, а не адрес.

`repo` вычисляется при создании дела (из спеки либо из явного `--repo`) и руками не правится:
это свойство дела, а не настройка.

## Здоровье: метрика → источник в журнале (0.0.6)

Экран 4 спеки меряет **дела движка**, а не карточки kanban: у карточки нет ни этапов, ни
отказов контракта, ни токенов. Поэтому источник у `/stats` один — свой журнал
(`$HERMES_HOME/duty/duty.db`), а окно по умолчанию — сутки; `?since=`/`--since` называет
границу явно.

| метрика ответа `/stats` | что это | источник в журнале |
|---|---|---|
| `totals.first_try` | доля этапов, закрытых **с первой попытки** | этап = (`deal_id`, `stage`); один `attempt_started` → `attempt_ended` с `outcome=done`; повторный `attempt_started` у этапа убирает его из числителя |
| `totals.stages` | сколько этапов в окне и у скольких есть закрытая попытка (знаменатель доли) | `attempt_started.stage` плюс закрывающий `attempt_ended` |
| `totals.waiting_human_sec` | медиана ожидания **человека** (p50/p90/p99, `count`, `max`) | `question_answered.ts − question_asked.ts` по `question_id` |
| `totals.waiting_sec` | ожидание **до первой попытки этапа** — очередь движка, а не человек | `attempt_started.ts` минус `created_at` дела |
| `totals.contract_refusals` | отказы контракта числом и разбивкой по правилу | `attempt_ended` с классом `contract` (`kind` события, старые записи — `details.class`); правило — `details.rule`, иначе код причины (`artifact.missing`), иначе первая фраза `reason` |
| `totals.attempts_by_outcome`, `totals.attempts_by_class` | таксономия исходов и классов отказов | `attempt_ended.outcome` и `attempt_ended.kind` |
| `totals.tokens` | токены за окно | `sum(attempt_ended.details.usage_tokens)`; ни одна попытка не записала — `null` и `warnings`, а не 0 |

Правила, которые нельзя перепутать местами:

- **`null` вместо нуля.** Пустая выборка (`count: 0`) — это «считать не по чему», а не
  «0 секунд», «0 %» и «0 токенов»: нули здесь были бы выдумкой.
- **Две величины ожидания.** `waiting_human_sec` — сколько ждал человек;
  `waiting_sec` — сколько этап ждал очереди движка. Подменять одну другой нельзя, и
  на экране «Здоровье» подписаны обе.
- **Карточки — не здоровье.** Карточек kanban в ответе `/stats` нет ни одним полем:
  у карточки нет этапов, отказов контракта и токенов, а здоровье обязано отвечать про
  **дела**. Наблюдение за карточками осталось одним роутом `GET /cards`, и `?board=`
  по-прежнему `400`.
- **`first_try` — историческое имя** доли этапов с первой попытки. Ключ не переименовывался,
  чтобы поверхности (`dashboard/web/app.js`, `desktop/plugin.js`) не разъехались с бэкендом,
  но метрика всегда считалась по этапам журнала, а не по карточкам.

## CLI

```
bin/duty spec check <file>            # OK либо file:line: правило: текст
bin/duty spec check <file> --json     # {ok, path, duty, stages, workspaces[], errors, warnings, issues[]}
```

Коды возврата:

- `0` — спека годна (предупреждения не мешают);
- `1` — есть отказы правил;
- `2` — спека не читается вовсе (путь, YAML, нет `duty`/`stages`) или не указана
  подкоманда.

`--json` печатает тот же ответ, что и человеческий вывод: `issues[]` —
`{path, line, rule, message, severity}`, `workspaces[]` — `{id, workspace,
default}`, поля верхнего уровня — счётчики.
Исключение по форме (не по содержанию) одно: у нечитаемой спеки есть
`unreadable: true`.

**Тот же отказ у `bin/duty run`.** Прогон не исполняет спеку, которую `spec check`
назвал бы отказом: `drive()` зовёт `validate_spec()` + `check_base()` до первого
процесса и отказывает теми же строками `file:line: правило: текст` и теми же
кодами (`1` — отказы правил, `2` — спека не читается; `--json` кладёт строки в
`errors[]`). Иначе цикл в графе дал бы вечный `wait("gate")` вместо отказа, а
`verdict.changes` не на предшественника проходил бы молча — то, ради чего эти
правила и заведены (`dashboard/driver.py`, `_checked_spec()`).

Строка `workspace:` называет дерево каждого этапа и помечает взятое по умолчанию:

```
$ bin/duty spec check duty.yaml
OK /…/duty.yaml · дело sx-widgets-tristate · этапов 3
workspace: impl=worktree · verify=worktree (по умолчанию) · review=worktree (по умолчанию)
```

Так молчание в спеке перестаёт быть догадкой: видно и что этап получит, и что
этого в спеке не написано.

## Что этот слой не делает

- не запускает этапы, не берёт лизинги, не спавнит роли, не пишет в журнал и в
  БД — это слой описания, а не исполнения;
- не проверяет, что `role` действительно умеет то, что от неё ждут, что
  `evidence` проходит, и что `budget` достаточен — это работа движка и попытки.

## Особенности YAML, о которых стоит знать

- `retry: {max: 2, on: [...]}` — ключ `on` в YAML 1.1 разбирается как `True`.
  Загрузчик возвращает ему контрактное написание (`_canonical_key`), поэтому
  `retry.on` читается как `on`, а не как «неизвестный ключ `True`».
- Значения читаются только `yaml.safe_load`: конструкторы объектов не
  вызываются. Позиции ключей для `file:line` берутся отдельно из `yaml.compose`
  с тем же `SafeLoader` — это разбор структуры, а не сборка объектов.

# Версии — контракт

Один и тот же контракт у `hermes-tickets`, `imessage-gateway` и `hermes-duty`.

## Где живёт номер

Ровно в трёх местах, всегда совпадают:

| файл | строка |
|---|---|
| `plugin.yaml` | `version: "X.Y.Z"` |
| `dashboard/manifest.json` | `"version": "X.Y.Z"` |
| `__init__.py` | `__version__ = "X.Y.Z"` |

Проверка и правка — только через `bin/duty-version` (см. ниже). Руками номер не
правится: рассинхрон трёх файлов — это баг, который видно в UI и в манифесте по-разному.

## Ветки

```
main                 стабильная линия: ровно то, что опубликовано (последний тег)
release/vX.Y.Z       рабочая вершинка: версия в разработке, сюда идут все коммиты
```

- Работа идёт **только** в `release/vX.Y.Z`. В `main` попадают лишь финализации.
- Ветка создаётся в момент старта версии: `git switch -c release/v0.0.2` + bump-коммит,
  который ставит номер `0.0.2` во все три файла.
- Пока версия не финализирована, номер в рабочей ветке — **этой** версии (не следующей).

## Финализация версии

Делается по команде человека (не по расписанию и не по «наработке объёма»):

```bash
bin/duty-version check            # три файла совпадают, ветка соответствует номеру
bin/duty-version finalize         # печатает план: ff main → tip, тег vX.Y.Z
bin/duty-version finalize --push  # выполняет план: ff main, tag, push main + tag
```

`finalize` отказывается работать, если дерево грязное, ветка не `release/vX.Y.Z`,
номер в файлах не совпадает с веткой или тег `vX.Y.Z` уже существует.

После финализации сразу заводится следующая версия:

```bash
git switch -c release/v0.0.2 && bin/duty-version bump 0.0.2 && git push -u origin release/v0.0.2
```

## Нумерация до 1.0

Проект pre-1.0: третья цифра — работа, вторая — момент, когда контракт плагина
(схема журнала, API, CLI) впервые объявляется стабильным.

| изменение | версия |
|---|---|
| новая функциональность, правки поведения | +patch (`0.0.1 → 0.0.2`) |
| изменение контракта (журнал, API, CLI) | +minor (`0.0.x → 0.1.0`) |
| P0 целиком работает, ядро kanban не нужно | `1.0.0` |

## Правила

1. Коммиты в рабочей ветке — `[HD-x.y.z]: <laconic English subject>`; Jira-ключей у
   проекта нет, номер версии выполняет роль области.
2. Тег ставится только на финализированную версию, только на `main`.
3. `main` никогда не опережает теги: нет тега — нет коммита в `main` (кроме первого
   скелета до первой финализации).
4. CHANGELOG заполняется по ходу работы, секция версии — `## [X.Y.Z] — в разработке`,
   при финализации меняется на дату.

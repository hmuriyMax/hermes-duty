# Версии — контракт

Один и тот же контракт у `hermes-tickets`, `imessage-gateway` и `hermes-duty`.

## Где живёт номер

Ровно в трёх местах, всегда совпадают:

| файл | строка |
|---|---|
| `plugin.yaml` | `version: "X.Y.Z"` |
| `dashboard/manifest.json` | `"version": "X.Y.Z"` |
| `__init__.py` | `__version__ = "X.Y.Z"` |

Четвёртая копия в бэкенде не читается из кода: `dashboard/plugin_api.py`
поднимает номер из `plugin.yaml` (`_plugin_version()`), поэтому `/health`
всегда показывает то, что записано в манифесте.

Проверка и правка — только через `bin/duty-version` (см. ниже). Руками номер не
правится: рассинхрон трёх файлов — это баг, который видно в UI и в манифесте по-разному.

## Ветки

```
main                 стабильная линия: ровно то, что опубликовано (последний тег)
release/vX.Y.Z       рабочая вершинка: версия в разработке, сюда идут все коммиты
```

- Работа идёт **только** в `release/vX.Y.Z`. В `main` попадают лишь финализации.
- Ветка создаётся в момент старта версии: `git switch -c release/v0.0.2` + bump-коммит,
  который ставит номер `0.0.2` во все три файла.
- Пока версия не финализирована, номер в рабочей ветке — **этой** версии (не следующей).

## Команды `bin/duty-version`

| команда | что делает |
|---|---|
| `bin/duty-version check` | сверяет номер в трёх файлах между собой и с веткой `release/vX.Y.Z`; печатает примечание, если тег `vX.Y.Z` уже стоит, и подсказку на `main` (сверяйте с тегом) или на ветке не `release/*`; последняя строка — `OK` (код 0) или `ЕСТЬ РАСХОЖДЕНИЯ` (код 1) |
| `bin/duty-version bump X.Y.Z` | ставит номер во все три файла и заводит в `CHANGELOG.md` секцию `## [X.Y.Z] — в разработке`, если её ещё нет |
| `bin/duty-version finalize` | печатает план финализации: ff `main` → tip рабочей ветки, тег `vX.Y.Z`, push. Ничего не выполняет |
| `bin/duty-version finalize --push` | выполняет план целиком |
| `bin/duty-version --help` | та же справка по командам |

### `check`

Проверяет только чтение, ничего не меняет. Выход 1, если хотя бы один файл
расходится с `plugin.yaml` или ветка `release/vX.Y.Z` требует другого номера.
`main` и ветки не из семейства `release/*` — не ошибка, а примечание в выводе.

### `bump`

- `bump` без аргумента или с не-`X.Y.Z` номером падает с `✗` и кодом 1;
- `bump` тем же номером, что уже стоит, — no-op («версия уже X.Y.Z»);
- `bump` на номер, чей тег `vX.Y.Z` уже существует, отказывается: номер не
  переиспользуется;
- пустая секция `## [X.Y.Z] — в разработке` добавляется в CHANGELOG только если
  такой секции ещё нет; дальше она заполняется руками.

### `finalize`

Перед печатью плана отказывается работать, если:

- дерево грязное по **отслеживаемым** файлам (`git status --porcelain
  --untracked-files=no`; новые неотслеживаемые файлы финализацию не блокируют);
- ветка не `release/v<номер из файлов>`;
- номера в трёх файлах расходятся;
- тег `v<номер>` уже существует;
- в `CHANGELOG.md` нет секции `## [<номер>]`.

Дальше проверяется, что `origin/main` — предок tip рабочей ветки. Если нет,
печатается `✗ origin/main не предок рабочей ветки — сначала подтяните main`,
план всё равно показывается, но команда возвращает 1 и ничего не выполняет даже
с `--push`.

Без `--push` печатается только план (три команды с tip-хэшем) и ничего не
меняется. С `--push` выполняются ровно эти шаги:

```bash
git switch main && git merge --ff-only release/vX.Y.Z
git tag -a vX.Y.Z -m 'hermes-duty X.Y.Z'
git push origin main && git push origin vX.Y.Z
```

после чего печатается подсказка про старт следующей версии.

## Финализация версии

Делается по команде человека (не по расписанию и не по «наработке объёма»):

```bash
bin/duty-version check            # три файла совпадают, ветка соответствует номеру
bin/duty-version finalize         # печатает план: ff main → tip, тег vX.Y.Z
bin/duty-version finalize --push  # выполняет план: ff main, tag, push main + tag
```

После финализации сразу заводится следующая версия:

```bash
git switch -c release/v0.0.2 && bin/duty-version bump 0.0.2 && git push -u origin release/v0.0.2
```

## Нумерация до 1.0

Проект pre-1.0: третья цифра — работа, вторая — момент, когда контракт плагина
(схема журнала, API, CLI) впервые объявляется стабильным.

| изменение | версия |
|---|---|
| новая функциональность, правки поведения | +patch (`0.0.1 → 0.0.2`) |
| изменение контракта (журнал, API, CLI) | +minor (`0.0.x → 0.1.0`) |
| P0 целиком работает, ядро kanban не нужно | `1.0.0` |

## Правила

1. Коммиты в рабочей ветке — `[HD-x.y.z]: <laconic English subject>`; Jira-ключей у
   проекта нет, номер версии выполняет роль области.
2. Тег ставится только на финализированную версию, только на `main`.
3. `main` никогда не опережает теги: нет тега — нет коммита в `main` (кроме первого
   скелета до первой финализации).
4. CHANGELOG заполняется по ходу работы, секция версии — `## [X.Y.Z] — в разработке`,
   при финализации меняется на дату.
5. `docs/` — часть релиза: секции CHANGELOG, роуты в README и таксономия в
   `docs/DESIGN.md` правятся до `finalize`, иначе тег фиксирует неверный объём.
